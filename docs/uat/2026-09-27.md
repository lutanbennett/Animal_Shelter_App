### The role-switching mechanic

One account changes role between passes rather than six accounts existing. That
works because **the app reads the role fresh on every server render** —
`current_user_role()` is a database function called per request, not a claim
baked into the sign-in token. So:

1. **Two browser profiles, side by side.** Profile A signed in as the admin who
   changes roles. Profile B signed in as the test account, which stays signed in
   all day.
2. In A: **Settings → Security**, find the test account, set its role.
3. In B: **hard refresh** (Ctrl-F5). No sign-out, no re-sign-in. Next.js caches
   rendered segments client-side, so an ordinary refresh can show you the last
   role's page.
4. **Confirm the switch before testing anything** — the menu is the tell. Each
   pass below opens with what the menu must look like.

Two things to know rather than discover:

- **Never change your own account's role away from `admin`.** Security is
  admin-only; you would lock yourself out of the page that undoes it. That is
  why there are two accounts.
- Writes to `user_roles` need a 2-step-verified session under `0100`, but the
  Security page writes through the service-role client, which bypasses RLS. Role
  changes work today. If one is refused, that is a **finding**, not expected
  behaviour — log it and say so.

**Expected to resolve on Thursday, when the Pi joins the solution** (Lutan).
That matches the mechanism: `ORIGIN_HOST` is `""` in every environment in
`wrangler.jsonc`, so today every page renders inside the Worker on the
CPU-limited path, and `docs/release-smoke-test.md` records that the edge cache is
the only thing keeping public pages off it. Bringing up the Pi as the origin
(`docs/pi-hosting.md`, and the backlog item "Bring the Suphan Buri Pi up as the
production origin") sets `ORIGIN_HOST` and moves rendering off the Worker, which
removes the limit this is hitting rather than working around it.

**A probe from another machine is not evidence either way, and one was misread
here.** Unauthenticated requests from a development machine returned 200 for every
public route in about a second, which was reported mid-session as the site having
recovered. It had not. Workers CPU limits and the edge cache are both per data
centre, so requests from outside Thailand land in a different colo, and an
unauthenticated request skips the signed-in chrome (`AppHeader`, `NavPane` with
its role RPC and two count queries) that a real page load renders on top. Check
this from the affected session, or against Worker CPU metrics — not with curl.
