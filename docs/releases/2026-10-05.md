### CI never fired, and `CLEAN` was misleading

The cut PR was opened and **no workflow ran at all**:

```
no checks reported on the 'claude/cut-release-0-19-2' branch
```

The usual explanation for silent CI is that the PR has become `CONFLICTING`.
That was ruled out rather than assumed: the branch was pushed, the PR's
`headRefOid` matched the local HEAD exactly, and GitHub reported `MERGEABLE` /
`CLEAN`. Actions was healthy — #380's run had completed twenty minutes earlier,
and the workflow's `pull_request: branches: [main]` trigger covers this PR.

**`mergeStateStatus: CLEAN` reads the same when no checks exist as when they all
pass.** That is the trap: the status that usually means "ready" meant "nothing
has looked at this".

The CI workflow has no `workflow_dispatch`, so there was no way to run it on
demand. Closing and reopening the PR fires a `reopened` event, which the default
`pull_request` types include, and that worked — two runs queued, the workflow's
`concurrency` with `cancel-in-progress` cancelled the older, and the survivor
came back `completed / success` with all six checks green. The merge went on
that run's conclusion.

Not established: **why** the original `opened` event produced no run. It
happened once, to one PR, and nothing in the repo changed to explain it.
