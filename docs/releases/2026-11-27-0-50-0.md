## The headline corrects this record's predecessor

**`0.49.3`'s record says the DNS blackout on this machine lasts "under a second". It does not. Today
it lasted at least 23 seconds**, and the retry that `0.49.3` asked for — built and merged the same
day, as #1916 — **fired, retried twice, and was not enough.**

### What was measured

The UAT Worker deploy failed after a complete build. `scripts/lib/wrangler-net-trace.cjs` and the new
`DNS-RETRY` lines caught the whole episode, from the deploy's own log:

```

[deploy net-trace] DNS lookup FAILED: host=api.cloudflare.com     … at=2026-11-27T16:19:25.607Z

[deploy net-trace] DNS lookup FAILED: host=api.cloudflare.com     … at=2026-11-27T16:19:34.920Z

[deploy net-trace] DNS lookup FAILED: host=sparrow.cloudflare.com … at=2026-11-27T16:19:41.263Z
[deploy net-trace] DNS lookup FAILED: host=api.cloudflare.com     … at=2026-11-27T16:19:44.483Z
deploy: DNS-RETRY: gave up after 2 retries (#dnsgp).
```

**Three attempts, 5 seconds apart, every one refused, spanning 22.8 seconds** — and each individual
lookup still failed in 0–4 ms, which is the signature `0.49.3` read correctly: this is not a timeout,
it is a resolver answering *no* instantly. By 16:23:26Z, about four minutes later, all three hosts
resolved in 24–55 ms.

### What that changes, and what it does not

- **The mechanism stands.** Instant `ENOTFOUND` across Cloudflare and non-Cloudflare hosts alike,
  recovering on its own, is still a machine-wide resolver failure and not a Cloudflare problem.
- **The duration was wrong, and it was wrong in the direction that matters.** `0.49.3` saw six
  lookups inside 250 ms and inferred a sub-second outage. That inference is what sized #1916's retry
  at 2 attempts 5 seconds apart — about 10 seconds of cover against an episode that ran to 23.
  **Two data points, two very different durations: the honest reading now is that the duration is
  unknown and 23 seconds is a floor, not a figure.**
- **The retry is still worth having, and this release is the proof it works.** It fired, it named
  itself, it told the release manager to write it down, and it did not rebuild. Its window is the
  only thing that was short.
- **Still not established:** why the resolver fails. The NordLynx inference from `#wgdns` is
  untouched by today — Lutan's production deploy succeeded first time with the VPN up, as `0.49.3`'s
  did.

**The remedy used, and why it was safe rather than assumed.** `node scripts/deploy.mjs --env uat
--no-mail --skip-build` succeeded in about a minute. The runbook forbids `--skip-build` unless the
leftover `.open-next` **can be shown** to belong to this environment, so it was shown: UAT's project
ref appears in 20 files, production's in **none**, the file timestamps are UAT's own build, and the
five hits for the dev ref are a hard-coded comparison in the app's own code
(`"https://fsjagxmxjosauwmxwype.supabase.co".startsWith("https://qxkmhwybjggxvsfxsxbd.")?"dev":…`),
not a stale bundle. Reading that took about two minutes and replaced a guess with a proof.
