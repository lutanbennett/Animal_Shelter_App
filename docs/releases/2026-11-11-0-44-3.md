### A prediction of mine that did NOT land, and why it was wrong

The cut plan predicted `role-cells` would move, because `0355` changes what the Bills card grants.
**It did not, and the prediction was the error, not the result.** `0355`'s grant change lives in
`src/lib/cards.ts` and `catalogue.ts` — application code — so it takes effect at the **deploy**, not
at the migration, and stored cells change only when a role's cards are next saved. The card checks
were therefore re-run **after** the production deploy, which is their proper place, and both are
clean there.

### A phantom regression I nearly recorded

`table-policy-commands` looked like it had fallen from 77 lines to 74. It had not: the previous
records count **total output lines** and I had counted only the `no policy` lines. The file is
**77 lines**, identical to `0.44.2`. Before concluding it had moved I checked that this release's
six migrations create **zero policies** and that the check's own code was untouched by them — both
true, which is what made the figure suspect rather than the database.

## The deploys, and the fault that cost two of them

Production's Worker deploy **failed twice** before succeeding. Both failures were the same fault and
it was not Cloudflare.

The wrangler log names the failing call: the **first** API request of the deploy, a
`GET …/workers/services/lanna-animal-care` before any upload, dying after **10.8 s** with
`errorType: ConnectionTimeout`. Measured against that: a **cold DNS lookup of `api.cloudflare.com`
took 12.1 s** on this machine, twice over, while every other host resolved in under 70 ms and the
link itself ran at 24 MB/s down and 7.8 MB/s up with a ~40 MB payload. **12.1 > 10, so the first
call could never connect** — which is also why nothing was ever part-uploaded and why the Worker
still answered `0.44.2` after both failures.

The same resolver fault explains the six Supabase read timeouts and the migration dry-run timeout
earlier in the release, against two unrelated hosts. **`check-public-views` fails with zero
assertions and exit 1 when it bites**, which would read as catastrophic to anyone who copied the
count without the exit code.

- **The third attempt warmed the cache first** (`Resolve-DnsName api.cloudflare.com`) and went
  through: asset upload 1.87 s, `Uploaded lanna-animal-care (17.91 sec)`.
- **It reused the first attempt's build** (`--skip-build`), so the retry was a 20-second upload
  rather than another ~40-minute build. The reuse was safe because `builtKeyProblem` still asserts
  the bundle carries production's Server Actions key, and it printed the same `cbd55beae8d8` both
  times; separately, only the production Supabase project appears anywhere in the static bundle.
- **The durable fix is Lutan's and was left alone:** the NordLynx adapter is up advertising Nord's
  DNS servers with NordVPN not running, which is how a lookup goes from 4 ms to 12 s. Changing it is
  a system network setting.

### `main` moving and `npm ci` are why the UAT Worker needed two starts

The first UAT attempt exited 1 with `Cannot find module 'wrangler/package.json'`. The daily
`guarded-install.mjs` was running `npm ci` in the main checkout at that moment and had `node_modules`
down to **109 entries**; it finished at 486 with `.package-lock.json` present. **This is the
2026-11-03 race, met for real, and the response was to wait rather than install over the top of it.**

## Defects and avoidable costs

- **My own worst call: I handed Lutan a retry without diagnosing the failure.** I told him the
  network was flaky and running it again was the right response. That was a guess presented as a
  diagnosis, and it cost him a second failed press. The cause was a specific measurable mismatch
  that one log read and one timed lookup would have found — and did find, after his second failure
  rather than before his first.
- **I opened the release asserting there was probably nothing to ship.** 34 PRs had merged and
  `unreleased` already held five notes. "Nothing to do" needs evidence like any other claim.
- **I predicted `role-cells` would move** and recorded above the reason it could not.
- **I nearly reported `table-policy-commands` as a regression** on my own miscount, above.
- **I nearly reported `--env uat` as half-built** after two UAT check failures, having briefly read
  exit codes through a pipe — this runbook's own trap. Read properly, every check answers on UAT, and
  the feature from `#rv4qk` is complete; this release used it for a real UAT before-picture.
