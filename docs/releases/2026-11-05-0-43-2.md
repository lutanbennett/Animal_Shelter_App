## THE THING TO READ BEFORE THE NEXT RELEASE

**He asked for "a minor release no email to be sent". On that `main`, that was a domain cutover.**

#1295 — the cutover commit, whose own title says `DO NOT MERGE YET` — had merged into `main` at 13:47Z, about seven hours before the release was asked for. **Merging deployed nothing**, exactly as `docs/decisions/2026-11-06-cutover-commit.md` promises, and the live site went on serving `0.43.1`. But **every deploy from that `main` performs the cutover**. A release manager reading only the words *"minor release"* would have run `deploy.mjs --env production` — which is step **5** of a thirteen-step runbook — on its own and out of order: no freeze, no fresh backup, the Pi still built for the old host, the tunnel still presenting the old host, and the Supabase Site URL still pointing at `lannacare.org`. Sign-in and every Server Action would have broken on the live site, during the working day, with no rehearsal and a rollback the runbook itself calls **not rehearsed**.

**What caught it was `git log --oneline -1` before cutting. No check catches this.** `check-site-hosts.mjs` prints `all right` **because the cutover state is internally consistent** — it is designed to pass once the cutover commit is in, so it is the opposite of a warning. CI was green. The gates were green. The only signals were the commit's own title and its decision file.

**So: read the top of `git log` and the decision file for anything unfamiliar, every release, before the cut.** It costs one command.

It was put to Lutan before anything was cut, with the alternative of cutting today and deploying tomorrow in the runbook's order. **He reaffirmed: *"Cut now and we are deploying straight after"*.** His call, recorded as his.

No email therefore means `0.43.2`, not `0.44.0`. **Said to him in one line rather than left to be discovered from a tag.**

### The Pi cannot resolve the new domain, and it is not the app

`scripts/pi/check-assets.mjs` still fails on the Pi with `getaddrinfo ENOTFOUND lannacareforanimals.org`, **even now the host is live**. Diagnosed rather than left open: the Pi's resolver is the router at `192.168.50.1`, which **cached the NXDOMAIN from the lookups the deploy itself made while the domain did not yet exist**. The tell is that **`www.lannacareforanimals.org` DOES resolve from the Pi** — that name was never queried early, so it was never negatively cached. **Serving is unaffected**, because cloudflared dials outbound. Verified from the release machine instead: home page 15,680 bytes, first hashed chunk `200 text/javascript`, `www` 200.

**And there is a control, from the same Pi, in this same release:** the **test** Pi build ran the identical script against `test.lannacare.org` and printed `check-assets: ok /_next/static/chunks/08jd_4rzxu020.css — 99018 bytes, identical to the build`. So `check-assets.mjs` is not broken and the Pi's networking is not broken — **only the one hostname that was queried while it did not exist is affected.** It should clear itself; **re-run the Pi-side check next release rather than treating it as a standing fault.**

## Avoidable costs, and the touches this release actually took

**The target is two. This one took four, and three of them are properties of the cutover rather than of the release.**

1. **The email answer** — given unprompted in the request. Cost nothing.
2. **Confirming the staff freeze** — asked for deliberately. A peer session reported he had told it the freeze was in place; **that is not his approval**, and a step that assumes nobody is saving is not one to take second-hand. He confirmed it himself.
3. **The Pi tunnel change — NOT in the runbook as his, and it should be.** `/etc/cloudflared/config.yml` is root-owned and `sudo systemctl restart cloudflared` is **not** in the Pi's passwordless sudo list. That list is exactly four commands: `systemctl restart lanna-care`, `restart lanna-care-test`, and `is-active --quiet` for each. So the Pi **build and app restart are Claude's**, as `release-procedure.md` says, but **the tunnel half cannot be**. **Established by reading `sudo -n -l` BEFORE the deploy** rather than by hitting a password prompt with the site half-moved and the staff frozen out. `release-procedure.md` lists only *"a `sudo` password on the Pi, which only an already-broken clone should need"* as an exception; this clone is not broken, the config is simply root's. **Section E step 4 should name him for the tunnel half, and `release-procedure.md`'s exception list should say so too.**
4. **The production Worker deploy** — his one standing job.
5. **The Supabase Site URL (5a)** — already his in the runbook.

**What kept it to four rather than more:** every command handed to him was verified first. The tunnel `sed` was tested against the live file with `diff` (one line changed, the test ingress untouched) and then wrapped in a self-verifying script on the Pi so his step was one short, PowerShell-safe command; the production deploy was `--plan`-ed before it was handed over; the UAT deploy's secrets were resolved with `--plan` while his build ran, so step 7 could not stall.
