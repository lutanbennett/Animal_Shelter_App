### Why minor, and why that was the right call

`0.36.1`, not `0.37.0`. Three genuinely new abilities ship — the clinic visit page,
the cumulative chart and the photo viewer — so **the standing test pointed at
major**. Lutan called it minor, and the reasoning is recorded because it is a
precedent rather than a one-off:

> This was the **third release of one day**, and the headline most people would
> notice is a fix for buttons that broke in the release that morning. A third email
> to every admin in a day, to say "we fixed what we shipped", reads worse than a
> quiet release.

**So no admin mail went out, and that was asserted rather than assumed — in both
directions.** `majorReleasesSince("0.36.0")` must return **empty**, which is the
inverse of the usual assertion and is the whole difference between this release and
an email to every admin. It did. And on both deploys the log was grepped for a
release-mail line with **none expected**:

```
deploy: no major release new to production (was 0.36.0), so no email.
deploy: no major release new to test (was 0.36.0), so no email.
```

**The inverted check is worth keeping as a habit.** On a major release you confirm
the mail arrived; on a minor one you confirm its absence. Both are one grep, and
only one of them is the usual one.

### The migration

One: `0220_doctor_report_purpose.sql`. **Dry-run case: `ok`, the trap did not
apply** — one file, so it could not.

**The claim worth checking was a money claim**: a doctor's written report is "kept
private, never shown on the website, and never counted as a bill". Read in the code
rather than taken from the header:

- **Never counted as a bill.** Bill queries filter `purpose = 'bill'` in both places that read them (`src/lib/bills/photos.ts`, `src/app/bills/page.tsx`); report queries filter `purpose = 'report'` in all four. The column is created `not null default 'bill'` **in the same statement**, so every pre-existing row is a bill and no back-fill can miss one.
- **Never readable by the wrong doctor, and never a bill at all.** All four new policies require `is_clinic_login()`, the visit to be at one of that doctor's **own** clinics, and `purpose = 'report'`. A doctor cannot reach a bill.
- `0220` touches no public view, and reports live in the Medical folder, which the public views already exclude.

**Verified by its effect on production afterwards, read-only:**

```
  attachments total                          243
  purpose = bill                             243
  purpose = report                           0
  purpose null (must be 0)                   0
  clinic_visit attachments                   3
  clinic_visit NOT bill (must be 0 today)    0
  purpose column: nullable / default         NO / 'bill'::text
  doctor report policies on attachments      4
```

Every existing row came out a bill, none is null, nothing is a report yet (correct —
the app could not add one until this release went live), and all four policies
landed. Afterwards: `No drift` on both databases.

### The Pi: the swap fix held, and the peak is now measured

**Both Pi clones built first time.** After `0.36.0`'s four consecutive OOM kills,
that is the swap fix doing its job.

**And the measurement the runbook asked for has been taken.** The first attempt was
useless and is recorded as such: a warm Turbopack cache compiled in 7.5 s and never
reached the heavy stage, giving a meaningless 375 MB. A **cold** build, sampled
every 3 s:

```
peak node RSS   : 3372 MB
peak swap used  :  947 MB
PEAK COMBINED   : 4320 MB
```

The Pi has **4,049 MB** of usable RAM. So the build needs about **270 MB more than
the machine physically has** — which is exactly why it died at "4 GB RAM + 2 GB
swap" and lives at 4 GB + 6 GB. **zram is compressed RAM, not extra capacity**, so
there was never really 6 GB there; the 4 GB *file-backed* swapfile is what gave
those 270 MB somewhere real to go.

**Against the threshold the decision file set** (`2026-10-18-pi-deploy-safety.md`:
a little over 6 GB → swap is defensible; well over → dropping the typecheck is the
only honest answer), **4,320 MB is comfortably under, so the swap is defensible and
`ignoreBuildErrors` can wait.**

**Two caveats, both stated rather than smoothed:**

- **The margin is 270 MB and the app grows every release.** This week alone added a 121-screen sweep, the photo pipeline, the clinic visit page and the dashboard chart. Two or three more features and the build leans much harder on a disk-backed swapfile, which shows up as slow builds before it shows up as failures.
- **Sampling every 3 s can miss a short spike**, so **4,320 MB is a floor, not a ceiling.** `/usr/bin/time -v` is not installed on the Pi, which is why sampling was used; installing it would give an exact figure next time.

### Defect 1 — the new Pi safety code shipped and did NOT run

**`0.36.0`'s two defects were fixed into `deploy-pi.sh` by #708, this release ships
that fix, and none of it executed.**

No `.next.prev` was created, no swap gate reported, and no asset check ran — on
either clone. The new script **is** on disk afterwards (8 matches for its new
markers) and `scripts/pi/check-assets.mjs` exists, and the clone is at the release
SHA. So it was checked out and simply not used.

**The mechanism: `deploy-pi.sh` updates itself.** It runs `git fetch` and checks out
the target ref near the top — which replaces the very file bash is executing. Bash
reads a script incrementally, so it carries on with the copy it already had open.
**A self-updating deploy script always runs the OLD version on the deploy that
introduces the new one.**

**Consequences, none of them harmful this time:**

- The safety features are live from the **next** deploy, not this one.
- So this release had no automatic asset check — **the check was run by hand instead**, against test and then against production, and it passed both: `check-assets: ok /_next/static/chunks/2z0tshjuy6fck.css — 95277 bytes, identical to the build`. The new tool works; it simply was not invoked by the script.
- The swap gate did not fire, but swap was confirmed at 6,143 MB by hand beforehand.

**What to do about it is a judgement for whoever picks it up**, and it is raised on
the backlog: either accept it (any change to `deploy-pi.sh` takes effect one deploy
later, documented), or have the script re-exec itself after checkout (`exec "$0" "$@"`
with a guard against looping). **Accepting it is defensible — but it must be written
down, because "I fixed the deploy script and the next deploy will still be broken"
is exactly the kind of surprise that costs an hour at the wrong moment.**

automating it (a Cloudflare token on the Pi) and that is being raised as its own PR

gives: the check only sees the edge location it reaches, and a phone on mobile data
may reach another — which is precisely how `0.36.0`'s fault hid from the deploy
machine.

### Rollback position

**Easier than the last two releases, and worth saying why.**

- Production is served by the Pi, so the rollback is `./scripts/pi/deploy-pi.sh --ref 1f7eacb5` there, a rebuild to `0.36.0`
- **No mail went out, so the one genuinely irreversible step of a release is absent.** This is the first release in four where that is true
- `0220` is additive and its header states its own undo steps; `0.36.0` code neither reads nor writes `purpose`, and every row is `'bill'`, which is what `0.36.0` assumes — so leaving it is harmless
- **The backup is newer than every applied migration for the first time in three releases**: `lannacare-production-2026-10-17T2000Z.dump.age` (1,279,505 bytes), 20:00Z on 2026-10-17, the eighth consecutive unprompted cron night
- **What a rollback would undo:** the Photos to approve fix, restoring the frozen buttons
