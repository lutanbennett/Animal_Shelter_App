## The release cost three touches, and the third was a tool refusal

Two were his by design: the answer on the email, and the production Worker deploy. **The third was the
production migration apply**, which the auto-mode classifier refused to let Claude run, naming
`[Production Deploy]`. He ran it himself, it applied all four cleanly, and the release carried on.

**Recorded as an avoidable cost, in the terms the runbook asks for.** The target is two touches; this
is three, and the cause is a tool refusal rather than anything about the software. The history matters
because it is not a steady fault: `0.41.1` was refused twice, `0.41.2` ran clean from the same checkout
with the same command, and `0.41.3` was refused again. So **one clean run is not evidence it is fixed,
and one refusal is not evidence it is broken.**

**No allow rule is being asked for.** `0.41.2`'s handover closed that question as *not needed on this
evidence* and said that if it refuses again, say so and hand it over rather than treating it as a new
fault — which is what happened. Raising it again on a second data point would be re-asking him
something already settled. **If a future release is refused a third time, that is the moment to put the
pattern to him, with all four readings.**

## The two answers that were his

1. **Should this release email you?** — *no email.* He asked for "a minor release", which is precisely
   the word `docs/release-procedure.md` says cannot be acted on: in his usage it means the middle-number
   bump, and in `src/lib/releases.ts` `major` means *worth an email*. The question went back with the
   words removed, naming what the seven notes say, that the mail reaches **one** person rather than every
   admin, and that it cannot be unsent once his deploy runs. Hence `0.41.3` and `major: false`. **The
   trap the runbook describes fired exactly as written, and the prescribed question defused it in one
   round.**
2. **10 of 23 plans are signed `pending:` — ship or hold?** — *ship, listed open.* The fourth release
   running with the same answer, and the same clusters.

## What shipped

Seven notes. Adoption updates take videos as well as photos, with a progress bar, a resumable upload and
a listed reason for a file the form cannot take — and shared ones play on the website's success-story and
journey pages behind a still picture. A wrongly typed intake date can be corrected in Settings, moving the
date together across the resident, their first place, their starting diet, their intake weight and the
date their age was estimated, and refusing with the record in the way if it would land after a later
move. The messages shown when an upload is refused now speak Thai. `#` tagging reaches the intake note
and the Edit resident housing-move note, and a tag inside a note visitors can read shows as a plain name
with no link. The Google Drive messages no longer tell anyone to ask an admin. Booking or editing a clinic
visit only offers to type a new doctor's name if your cards let you add doctors. And a clinic visit booked
by asking the assistant now reaches the shelter calendar — with the note saying plainly that visits booked
that way **before** this release may still be missing from it.

### Defect 4 in full, because the cause is NOT established and the next release manager needs the facts

**What is certain.** The damage timestamps on the emptied directories were **13:57–13:58**, inside the
window of the failed test build. The ENOENT copy storm came **before** the esbuild resolve error, so
`node_modules` was already gutted when the copy step ran — meaning something gutted it at the *start* of
that build, not as a consequence of the build failing later.

**The prime suspect, stated as a suspect.** `opennext:build` runs as
`node -r ./scripts/win-junction-symlinks.cjs …`, a Windows-only preload that stands in junctions for real
package directories to get around an `EPERM` in OpenNext's copy step. Empty directories with no reparse
points left behind is the shape that preload failing halfway would leave. **That is a hypothesis fitted to
the evidence, not a diagnosis**, and it is written down as one because the honest state is that nobody has
read that script against this failure yet. **Filed on the `backlog` branch under *Architecture*.**

**A wrong suspect, ruled out, and worth recording so it is not blamed next time.** A
`node scripts/worktree.mjs done control-listing-sweep-6` process from another session was running when the
failure was investigated, and a worktree teardown deleting through a junction into the main checkout is a
plausible-sounding story. **It is wrong: that process started at 14:01:38, three to four minutes after the
damage.** The main checkout's `node_modules` was also stable at 70 entries rather than still shrinking.
**One timestamp settled it**, and the tempting inference would have cost a session an afternoon chasing
another session's clean-up.

**Why nothing else was run in that checkout while the retry built.** The runbook's rule is one command at a
time against shared state. Having just watched `node_modules` fail under a build, the home-icon sync was
held back until the retry reported rather than run alongside it — which is the same rule the `0.40.9`
failure taught, applied to a folder rather than to `.open-next`.
