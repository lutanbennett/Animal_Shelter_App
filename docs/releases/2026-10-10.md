### The silent-failure question answered *yes*, and bigger than last time

`0.21.0` established the question; `0.22.0` answered no; `0.23.0` was the first
yes, a three-minute window on one picker. **This release's window was wider in
scope than that one**, and the reading that found it is the same two commands:
compare the live release's source against this release's, rather than reasoning
about the migration header.

`0172_clinics_and_doctors` renames `vets`, `vet_doctors`, `vet_doctor_clinics`
and `vet_appointments`, the `vet_appointment_id` column on `prescriptions`,
`procedures`, `blood_tests` and `weight`, `site_content.vet_visit_estimate`, the
`vet_id` columns, a view, the `vet` role value, and every function body that
named any of them. It leaves **read-only compatibility views** under the four old
table names, for one release. So between the production apply and the Pi finishing
its build:

- simple **reads** of the four tables survived, through the views;
- every **write** to them failed — booking or editing a visit, adding a clinic or
  a doctor, linking a doctor login;
- every **embed** through those views failed, and the renamed **columns on real
  tables have no shim at all**, so the resident medical sections, the Vets pages,
  prescriptions and weights tied to a visit, and the Management dashboard's
  clinic cards were broken outright.

**Two of those fail quietly rather than with an error**, which is what made this
worth a decision rather than a note:

```
live (0.23.0) src/lib/site/content.ts:173   .select("vet_visit_estimate")   // error ignored, returns null
live (0.23.0) src/app/residents/[id]/[section]/page.tsx:633   .select("id, vet_appointment_id")
```

`loadVetVisitEstimate` destructures only `data`, so a failed query is
indistinguishable from "no estimate set" and the **donate page simply stops
showing the estimated cost of a vet visit**. The one-weight-per-visit guard reads
an empty set, so a visit that already had a reading would have offered to take
another.

**Lutan was given three options before the cut** — go ahead with the window kept
short, wait for a quiet hour, or hold on test — as its own question in the same
round as major/minor, not folded into the count of unsigned plans. He chose to go
ahead. The mitigation was the same as `0.23.0`'s and it is now the pattern: apply
the migrations and start the Pi production build **in the same command**, so no
round trip sits inside the window. It was 06:25 in Thailand, before the shelter
day.

**Measured, not estimated:**

```
apply start: 23:25:37Z
apply exit 0, apply end: 23:25:44Z     (three files, 7 seconds)
Pi production build finished: 23:27:24Z
window: 1 minute 40 seconds
```

The Pi build was faster than the ~3 minutes budgeted, which is where the saving
came from. The Pi is what serves users, so the Pi build is what closes the
window — **not** the Worker deploy, which is the fallback and took twelve times
as long.

### `0172` would not apply at all until a person decided something

This is the part worth carrying forward, because no gate could have found it and
no amount of care in the file would have avoided it.

`0172` folds `vets.name` and `vets.clinic_name` into one clinic name, and
**refuses to choose** where a row has both filled in and they differ. The
production dry-run stopped:

```
dry-run 0172_clinics_and_doctors.sql … FAILED
ERROR:  23514: clinics with two different names, agree which to keep before applying:
  e1c1e016-ba43-446a-85b2-cbabc309bd1d: name 'Dr somchai', clinic_name 'Novel'
HINT:  Set name to the one to keep and clinic_name to null on each, then apply again.
```

**Dev's rows agreed, so the file applied cleanly there and CI was green.** The
disagreement existed only in production data. Put to Lutan with the model's own
reasoning — a clinic is a place, a doctor is a person — and **he decided to keep
`Novel`**. The correction, run from the main checkout before the apply, guarded
so it could only fire on the exact pair the dry-run had reported:

```
before: [{"id":"e1c1e016-…","name":"Dr somchai","clinic_name":"Novel"}]
before: doctors at it: []
updated: [{"id":"e1c1e016-…","name":"Novel","clinic_name":null}]
doctor inserted: [{"id":"b1b949ae-…","name":"Dr somchai"}]
after:  [{"id":"e1c1e016-…","name":"Novel","clinic_name":null}]
after:  doctors at it: [{"id":"b1b949ae-…","name":"Dr somchai"}]
```

**The name was not discarded, it was moved to where the new model puts it.** The
clinic had no doctors recorded at all, so `Dr somchai` was inserted as its
doctor; the insert trigger made the link, confirmed by reading it back.

The lesson for the next release manager: **a guard that says "this is someone's
call" is a question to ask, not a file to fix**, and it can only ever appear at
the production dry-run. Leave room for one.

### The dry-run then went red on a *different* file, and the answer was still to apply

With the fold guard satisfied, the re-run reported:

```
dry-run 0172_clinics_and_doctors.sql … ok
dry-run 0173_retire_staff_role.sql … ok
dry-run 0174_close_the_remaining_over_grants.sql … FAILED
ERROR:  42883: function current_clinic_resident_ids() does not exist
```

That is the per-file `begin … rollback` trap `CLAUDE.md` describes, and this is
the second recorded instance. `0174` calls `current_clinic_resident_ids()`;
`0172` is what creates it (line 273, and the rename at line 232). Each file is
dry-run in its own transaction, so `0172`'s function was gone before `0174` ran.
Both files were read before concluding anything, and **the correct action was to
apply** — which it did, all three `ok`.

Say which it was. "The dry-run failed" and "the file is wrong" are different
statements, and only the second is a reason to stop.

### Migrations

Three, `0172` through `0174`. Production went `171 applied, 3 pending` to
`174 applied, 0 pending` in seven seconds.

The consumer header warned on `0172` and the runner's standard note was, for once,
**exactly the wrong way round** — which `0.23.0`'s record predicted:

> *These tables/columns land before the code that reads them is live. That is the
> safe direction - nothing is blocked - but do not deploy the reader before this
> is applied, and expect nothing to use it yet.*

`0172` is not a file that adds something nothing reads yet. It **renames things
live code was using**, so its apply changes behaviour immediately and "expect
nothing to use it yet" is the opposite of the truth. The runner cannot tell the
difference and prints the same note either way. `0.23.0` wrote that down after
`0170`; it is now confirmed on a second, larger case. **When a consumer warning
names files that already exist, open the migration and ask whether it adds or
restricts or renames.**

`0.20.0`'s correction was followed: **merge, pull, apply, deploy.**
`git status -sb` was read after the pull and again immediately before the
handover, reporting neither ahead nor behind at `d8b19418` both times.

### `main` moved under the handover, and this is what it cost

`0.21.0`'s trap recurred and this time it reached the deploy. Between the
handover (23:27Z) and Lutan running the command (23:55Z), another stream merged
its work and pulled the main checkout, so **the Worker built from `8fcb6835`, not
from the release SHA `d8b19418`**:

```
deploy: production → Supabase project dbkodyyxxhtygxcxmfcu (8fcb6835)
```

Checked rather than assumed, and the answer is that it does not matter here:

```
$ git diff --name-only d8b19418 8fcb6835
docs/backlog.md
$ git cat-file -e 8fcb6835:supabase/migrations/0175_…  -> no
```

**One commit, touching only `docs/backlog.md`.** No `src/`, no `worker/`, no
migration, identical `package.json`. So the Worker's application code is the
release's application code; the two SHAs differ by a documentation edit. PR #506
and its migration `0175` merged *after* the deploy and are not in this release.

Two things follow for next time. **Pinning the Pi builds with `--ref` worked** —
both clones are at `d8b19418` and nothing drifted. **`deploy.mjs` has no `--ref`**,
so the Worker takes whatever `main` is when it runs, and a handover that waits
half an hour is a handover that can ship a different commit. The guard is why it
is safe: it refuses a commit whose database lacks a migration on `main`, so had
`0175` been in the tree the deploy would have been refused rather than shipping
schema-less code. **Read the project-ref line's SHA every time and compare it
with the release SHA**; if they differ, diff them before deciding whether it is
benign.

**Two findings came out of running it, both filed on the `backlog` branch:**

1. **It cannot be run the way the smoke test describes.** `ALL_ROLES` still

   above names the six surviving roles explicitly. It also still lacks
   `second_in_command`, so **2IC was not measured**.
2. **`--clean` is too broad.** It removes every `phonewidth-*` login it finds,
   not just the current run's. Running it here deleted throwaway logins belonging
   to another stream that was evidently mid-run (a role set this version of the
   script cannot even produce), and a stale one from 2026-10-03. Dev data is
   disposable so nothing was lost that matters, but on a shared dev database it
   should be scoped to the run id.

The sweep was also slow enough to need slicing by role: a single run covering
three roles in both languages was killed at 560 s having printed nothing, because
its output is buffered. One role at a time, both languages, each finished well
