### `major: false` — the first time the argument came out this way

Asked before cutting, with the case for each side put, as every cut since
`0.15.0` has been. **Lutan's call was minor**, and it took one round.

The case: both notes are **fixes to things that already exist**. No page appears,
no role gains or loses anything, nobody can do something they could not do
yesterday. That is precisely the ground `0.21.0` through `0.24.0`, `0.26.0` and
`0.27.0` were each called major on — and it is absent here. The case against,
put as well: the second note changes what a person *sees* when they are refused,
which is a visible change to a real screen.

**Six consecutive majors ended here, and that is worth recording as a
calibration rather than a change of policy.** `0.26.0`'s record warned that the
six were not major for the same reason and should not be read as one precedent;
this release is the test of whether the stated ground was really the ground. It
was. `majorReleasesSince("0.27.0")` returned `[]` before the cut was committed,
and **no admin was mailed**.

### The silent-failure question answered *no*, on evidence

Fifth release of eight to answer `no`, and like `0.27.0` the answer took real
work: two migrations, one of them replacing a function the live app calls on
every receipt. `0.26.0`'s lesson — **the header reads identically whether the
migration is harmless or catastrophic** — was applied, so each file was checked
against what the live `0.27.0` app does rather than against its own description.

**`0186_receipt_date_rule.sql`** replaces `issue_donation_receipt` and adds the
rule `received_on <= issued_on <= shelter_today()`. The signature is
**unchanged**, so the live app keeps calling it. The question is whether what the
live app *sends* satisfies the new rule:

```
47760a81:src/app/management/donations/actions.ts:73      p_issued_on: todayIso(),
47760a81:src/lib/format.ts:84   export function todayIso(now = Date.now()) {
                                  const parts = SHELTER_DATE_FORMAT.formatToParts(now);
```

`todayIso()` formats through `SHELTER_DATE_FORMAT`, which is the shelter's own
zone — so what the live app sends **is** `shelter_today()`, the upper bound
exactly. **This is the one that could have gone wrong and did not**: had
`todayIso()` been UTC-based, then between midnight and 07:00 Thai the app would
have sent yesterday's date, and a receipt for a donation received that morning
would have been refused with `22023` on a path that takes a receipt number. The
fact that it is zone-correct is what makes the migration safe, and it is not
something the header says.

**`0187_medical_archive_trigger.sql`** refuses an `archived_at` change without
`medical.archive`. Its header calls itself *"defence in depth, not a live
hole"*, and that was checked rather than believed — the live app asks the same
permission on **both** paths, not just the one that renders the button:

```
47760a81:src/app/residents/[id]/archive-actions.ts:49    if (!can(await loadPermissions(), "medical.archive")) return refuse(...)
47760a81:src/app/residents/[id]/archive-actions.ts:92    if (!can(await loadPermissions(), "medical.archive")) return refuse(...)
47760a81:src/app/residents/[id]/[section]/page.tsx:161   const canArchive = (kind) => !isDeceased && can(perms, "medical.archive");
```

Line 92 is the **restore** path, which is the one worth confirming: restoring
changes the same column, so a guard that covers archive but not restore would
have broken it. Both are covered, the app and the trigger read the same settings
grid, and a caller with no login — the service role, the backup, the migration
runner — is let through by `(select auth.uid()) is not null`.

Contrast `0181` two releases ago, which dropped what the live app called on
every request. Same shape of header, opposite answer.

### Things that look alarming but are not

Everything `0.27.0`'s record lists under this heading still applies. New this
release:

- **`gh pr checks` reporting a job as `pending` after the run has concluded.** All seven jobs read `completed success` from `gh run view 38211194333`, while `gh pr checks 563` still showed `check` pending. The run is the source; the PR-checks view is a cache. Same shape as the `| tail` exit-code trap the runbook already names — **read it from the thing that did the work**.
- **No release mail at all.** Correct by construction on a minor release: `majorReleasesSince("0.27.0")` is `[]`, so nothing is sent and there is no `sent N, skipped M` line to look for. After six majors in a row its absence looks like a failure and is not.
- **Four consumer-header warnings not appearing.** `0186` carries a `-- consumer:` header, and the apply printed no warning for it, because the file is in the release assumed live. Three releases running the *wording* of these warnings has been wrong; this is the first where the useful behaviour is their silence.
