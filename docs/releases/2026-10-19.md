## THE DEFECT THAT MATTERS: a 4.4 GB stale build cache starved the Pi, and it looked exactly like the known OOM fault

**The production Pi build was killed by the kernel four times.** The cause was not
memory pressure, not swap, and not the machine. It was a **4.4 GB stale Turbopack
cache in the production clone**, on a machine with 4 GB of RAM.

| Clone | `.next/cache` before | Built? |
|---|---|---|
| Test | 1.2 GB | **first time, every time** |
| Production | **4.4 GB** | killed 4× |

Clearing it took `.next` from 4.9 GB to 450 MB. **The very next build compiled in
52 s and went all the way through.**

### Why this was so easy to misdiagnose, which is the part worth keeping

Every surface reading pointed at the documented OOM fault from `0.35.0`/`0.36.0`,
and **three separate remedies that address that fault all failed**, because it was
not that fault:

- **`free` showed 3.5–3.6 GB available** after each kill — the same reading `0.36.0` recorded, and the reason that release concluded "contention and leaks are ruled out". True, and irrelevant: a build cache is read as mapped file pages, which never appear as "used".
- **The kernel killed it at *decreasing* RSS**: 2,799 MB → 2,680 MB → 2,254 MB. That looked like the machine degrading, which is what sent me to a reboot. It was not degradation; it was a cache being read further into on each attempt.
- **It died in *compilation*, before the typecheck** — never printing `Compiled successfully`. Previous kills died at or after the typecheck. **This should have been the tell from the first failure**, because it is the stage that reads the cache, and because it means `ignoreBuildErrors` — one of the three candidate fixes on the backlog — would not have saved a single one of these builds.
- **The test clone built fine 30 minutes earlier on the same machine.** That asymmetry was the real evidence, and it was in hand from the start. The two clones differ in exactly one material way, and it was not looked at until the fourth failure.

### The three interventions this cost Lutan, two of them on wrong diagnoses

Recorded as avoidable cost, in his words would be "things I had to do that I
should not have":

1. **A swap-priority change** (`swapoff`/`swapon -p 200` plus an `fstab` line). My hypothesis: zram at priority 100 was being preferred over the real disk swapfile at -2, so the build never reached real swap. **The configuration was genuinely wrong and the change was genuinely correct** — the file swap is now used first and the build was killed anyway. A right answer to the wrong question.
2. **A reboot.** My hypothesis: 16 days of uptime had fragmented memory, since builds were dying at progressively lower RSS. **Wrong** — the next build was killed at 2,212 MB on a machine that had been up for 0 minutes. This also departed from the handover's recorded answer that a restart does not help; that answer was right and I overrode it on reasoning that did not survive contact.
3. **Deleting the cache**, which was the actual fix.

**The lesson, stated so the next session does not repeat it:** when one clone
builds and its twin does not, on the same machine, **diff the clones before
theorising about the machine.** `du -sh .next .next/cache node_modules` on both
costs one command and would have ended this at the first failure instead of the
fourth.

### What went right, and should not be lost in the above

- **`.next.prev` protected production through all four failures.** Every one ended `BUILD FAILED — putting the previous .next back; lanna-care keeps serving the old version`, and `lannacare.org` served `0.36.1` continuously with `x-lanna-served-by: pi`. **This is #708's fallback proven in anger for the first time**, and it is the reason a four-failure evening was an inconvenience rather than an outage.
- **The fstab fix found a latent fault.** `/etc/fstab` had **no swap entry at all**: `/swapfile2` had been created by hand on `0.36.0` and **would have vanished on the next reboot**, taking the `0.36.1` swap fix with it. `setup.sh` does add a line, but this Pi had never been re-run through it — and even that line sets no priority, so it would have come back below zram. Both are now fixed on the live machine, and the reboot in step 2 above accidentally **proved the persistence works**: `/swapfile2` came back at priority 200.
- **The self-updating deploy script fix ran, a release earlier than predicted.** `deploy-pi: restarting under the script from 2b1dc2e5` is in the successful log. The handover expected it absent on the release that ships it, and it would have been — but the four failed attempts had already checked the new script out, so by the successful build it was in place. **The prediction was right about the mechanism and wrong about this release**, and it was corrected to Lutan out loud rather than left standing.

## The migration

Three files, not one: `0221`, `0222`, `0223`. The handover's warning that "one
migration" can be several, met for real.

- **The dry-run was the clean case** — all three `ok`, nothing `FAILED`. Of the three possible outcomes this is the plain one; the per-file rollback trap that fired on `0.36.0` and `0.32.1` did not fire here. Worth saying explicitly, because a clean dry-run is now the minority outcome.
- **The first production apply was refused by the classifier with no explanation**, and per the runbook it was not retried blind — it was handed to Lutan with the dry-run result. **It then succeeded on a single considered retry after he said to proceed**, before he had run it. So `0.28.0`'s Defect 3 remains unpredictable rather than fixed, now for a ninth release, and the "retry once after he asks in chat" pattern held again.
- **Two of the three recreate the same function**, which is exactly the shape the handover's item 11b asks about. **Both were read in full and compared**: `0222` is `0221` plus a join to `roles` requiring `archived_at is null`, with both refusal messages, the permissiveness rule, the body and the grants identical. Nothing from `0221` was lost. This is the half `create or replace` would *not* have failed loudly on — a dropped `where` clause goes quiet — which is why it was read rather than assumed.
- **Ordering mattered this release.** `0223`'s own header says "NOTHING IN src/ READS THESE TABLES YET". That was true when it merged in #725 and was **no longer true** by release time, because #728 and #729 had since landed the code that reads all three tables. Applied before every deploy, and the runner's thirteen `-- consumer:` warnings were it saying exactly that.
- Production went `221 applied, 3 pending` → **`224 applied, 0 pending`, `No drift`**. Dev `No drift`, 224 of 224. Both read, not trusted.

### Rollback position

Production is served by the Pi, so the rollback is
`./scripts/pi/deploy-pi.sh --ref e581c631` there, a rebuild to `0.36.1`.
`npx wrangler rollback --env production` reverts only the Worker fallback. **Neither
reverts the three migrations**, and all three are additive and re-runnable, so
leaving them is harmless — `0.36.1` reads none of the new tables and no cell is
written by either function.

**What a rollback does not undo: the mail.** `major: true` means every admin was
mailed at the Worker deploy, and that is the one genuinely irreversible step.

Backup: **`lannacare-production-2026-10-17T2000Z.dump.age`, 1,279,505 bytes**, read
from Drive rather than recalled. It is the most recent *expected* one — the cron
runs 03:00 Thai — and it **predates all three migrations**, so a restore would
unwind them and they would need re-applying. The README restore recipe has still
never been exercised.
