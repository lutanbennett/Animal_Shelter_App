## The headline: two notes would have shipped false, and test could never have caught it

**The production Pi held two of the four values `calendarConfigured()` needs.**
`GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` were present;
`GOOGLE_CALENDAR_REFRESH_TOKEN` and `GOOGLE_CALENDAR_ID` were not. Three places
gate on that function, and the Pi is what serves the live site — the Worker is
only the fallback. So on production:

- the **"Calendar entries to confirm"** list would never have appeared, and its buttons would have refused (`upcoming-visits/page.tsx:34`, `confirm-actions.ts:16`) — half of note 1
- **every coming visit would have said the calendar was not switched on** (`sections/clinic-visits.tsx:93`) — note 5, and simply untrue

**Meanwhile the feature worked.** The quarter-hourly poll and sweep run *in the
Worker* (`src/app/api/calendar/sweep/route.ts`), which has held both values since
`0.39.1`. So entries were being imported correctly and the screens were denying
it. That is the worst shape a fault can take: the data is right and the app says
it is off.

**The cause is structural.** `scripts/pi/write-env.mjs` writes a `PI_OPTIONAL`
name only when it is present in the values file it loads, and **each Pi clone
keeps its own hand-maintained, gitignored `.env.deploy.production`.** `0.39.1`
added the two values to this machine's copy — which is what the Worker deploy
reads — and nothing updated the Pi's. `systemctl show` confirmed the unit has no
`EnvironmentFile`, only `NODE_ENV` and `PORT`, so the generated file in the clone
was the whole story. No guard covers it: an absent *optional* name is by
definition not an error.

**The test Pi held all four**, so every check on `test.lannacare.org` passed while
production was broken. **This class of fault is invisible to test by
construction**, and that is the part to carry rather than the specific two names.

`docs/decisions/2026-10-22-vet-calendar-on-production.md` says "the Pi's
`.env.production.local` is regenerated by `deploy-pi.sh`". That is **true**, and it
was read as sufficient. It regenerates from a values file that was never given the
two names — a correct sentence from which the wrong conclusion was drawn, which is
more dangerous than a wrong one. Recorded as
`docs/decisions/2026-10-22-pi-keeps-its-own-secrets-file.md`.

**How it was found:** by checking the release-note truth rule *forwards* on all
six notes before cutting — asking what each note needs to be true, and then
reading the live system for it, rather than assuming the features having merged
made them true. The three plans' own `pending:` items named "the Pi app process
holds the four calendar env values" as something for a person; it was a read-only
check, so it was done rather than handed over, and that is what turned it up.

**It was gated, not waved through.** Carried as the live item in section 8 of the
cut plan with the reason spelled out, stated in bold in the handover message, and
**verified by re-reading the Pi after the build** — all four names present in
`.env.production.local`, which is the file the app reads, not the command's own
output. Notes 1 and 5 are true on production as of this release.

## The classifier refused the fix, and the retry did not clear it

Two attempts to append the two lines over `ssh` were refused as
**`[Secret-Store Writes]`**, after a read-only `ssh` of the same file had
succeeded — the usual shape. **Nothing was written: the Pi's files were
byte-for-byte unchanged**, confirmed by re-reading the names rather than inferred
from the refusal text.

The one retry the last six handovers all prescribe was taken and **did not
clear it.** That is new: six releases, six behaviours, and this is the first where
the retry failed. It became a handover, and a third touch.

**Seven releases, seven behaviours. The advice still holds — take the one retry,
do not predict which command gets it — but add that it may not work, and have the
handover ready.**

## Verifying the command, not the change — and it paid off twice in one release

Last edition's single largest lesson was *"I verified the change I was making, I
did not verify the command I was typing."* It was applied, and it caught two
things that would each have cost a round trip.

**First, the four conditions the deploy guard tests were enumerated from source
and each run against the live state, printed as a table before the command was
written out** — `main` in step with `origin/main`, clean tree, `unreleased` empty,
`package.json` matching, production holding every migration. Also checked:
`*.log` is gitignored (`.gitignore:17`), so the `tee` log could not dirty the tree
the way last release's untracked script did. **And `--secrets` was deliberately
not used**: nothing new was needed on the Worker, so the flag that caused two
refusals last release had no reason to appear.

**Second, and this is the one worth keeping: the handover command itself was
tested before it was handed over.** The fix had to pipe two lines from a Windows
file into `ssh`. A probe with a harmless string into `/tmp` on the Pi showed
PowerShell had prepended bytes `357 273 277` — a **UTF-8 BOM** — to the piped
stdin.

**That would have silently corrupted the first variable's name**, so the Pi would
have accepted the append, reported nothing wrong, and still not had the value. The
whole fix would have appeared to work and the notes would have stayed false. A
`tr -d '\r'` guarding against Windows line endings does not remove a BOM.

Corrected to `tr -d '\r\357\273\277'` and re-probed: clean bytes, name, `=`,
value, newline, and `grep '^GOOGLE_CALENDAR_TESTPROBE='` matching. **The probe
cost about a minute.** Lutan then ran both commands back to back and both worked
first time.

**The general rule: when a handover command moves text from Windows into a Unix
file, probe it with a harmless value first.** The failure mode is not an error, it
is silence.
