**The per-file dry-run trap did not fire, and this release was exactly its
shape.** Three pending files where `0197` names a function `0196` creates is the
textbook case for `--dry-run` reporting FAILED on a file that is perfectly
correct. It came back `ok` on all three, because `0197` is a bare
`create or replace function` — replacing a function does not require the earlier
file's objects to exist. Worth recording precisely because the expectation was
the opposite: the trap is about a file *using* something a pending file provides,
not about a file *redefining* it.

**The silent-failure question has one real candidate here, and it is covered.**

`0195` narrows read on `site_content`, `site_pages` and `site_content_photos`
from `using (true)` — readable by every login since `0018` — to holders of
`website.content` Read or `reports.cashflow` Read. The quiet failure that shape
invites is a page going blank rather than erroring, and the code invites it:
`loadClinicVisitEstimate` in `src/lib/site/content.ts` destructures `{ data }`
and discards the error, so a refused read returns `null` and the cashflow
forecast would simply use no estimate and say nothing.

It holds, for reasons that were checked rather than read off the header:

- `site_content` has exactly **one** direct reader in `src/` —
  `src/lib/site/content.ts` — and that function has exactly **two** callers:
  `src/app/admin/website/page.tsx` and `src/app/management/cashflow/page.tsx`.
  Those are precisely the two permissions the new policy allows. The match is
  deliberate: `0195`'s own header names the cashflow forecast as the reason
  `reports.cashflow` is in the policy at all.
- Visitors are untouched for a structural reason rather than a hopeful one: the
  public pages read through the `public_site_*` views, which run as their owner
  (`0122`, `0059`) and never consult the caller.
- `0195` ships its own evidence. `scripts/check-security-schema-fold.mjs` is a
  one-transaction harness, always rolled back, that walks **every live role** and
  measures who can read each of the three tables after the change. That is a
  measurement of the policy, not a reading of it.

**`0196` is the better worked example, and it is worth reading as one.** It
restructures `user_roles` and rewrites every permission helper, which sounds like
the most dangerous thing in the release. It is not, because of its shape: the
restriction helpers (`is_clinic_login`, `photos_medical_only`,
`on_volunteer_floor`) now return true only when *every* live role is restricted,
so the rewrite can **widen** access and never narrow it, and only for a login
that has two rows. Until Admin uses the Add-a-role panel every login still has
exactly one row, so the union of one role is that role.

**And `0197` is the counter-example that shows the loud direction working.**
`0196` pinned `role_row_live()`'s `search_path` to the empty string, so it could
not call `shelter_date()`, so every permission helper that asked it failed
outright on dev. That is as loud as a fault gets, it was found immediately, and
the fix shipped in this release with its parent. A quieter version of the same
mistake is what the silent-failure question exists to catch.

The consumer warnings are the safe direction, as the handover says: two of
`0196`'s declared consumers differ from live `0.30.0`, so the tables landed
before the code reading them was live.

**No production-only guard appeared** — the seventh release running. It can only
show up at the production dry-run, and it did not.

### Defect 1, and what the next release manager should take from it

The handover already says `main` moves under a release and prescribes the two
remedies that worked: **pin both Pi builds with `--ref <release sha>`** and
**re-run `release-prs.mjs` against the release SHA rather than `HEAD`**. Both
earned their place here — the `--ref` pins meant the Pi builds were never
ambiguous, and the re-run is the only reason `#625` is in this record at all.

What it does not yet say, and should:

- **The Worker deploy cannot be pinned.** `deploy.mjs` takes no `--ref` and
  refuses a `main` that differs from `origin/main`, so the Worker is always built
  from whatever `main` is at that moment. The Pi and the Worker therefore have
  *different* exposure to a moving `main`, and the asymmetry only shows up when
  it bites.
- **So the window to protect is from the cut's merge to the production Worker
  handover.** Everything built before a late merge has to be rebuilt afterwards
  if "all four from the release SHA" is to stay true.
- **The cheap mitigation is ordering, not vigilance.** Hand over the production
  Worker deploy *first*, then build the two Pis pinned to whatever SHA that
  deploy reports. That costs nothing and makes a late merge harmless. This
  release did the opposite — Pis first, to parallelise — which is what the
  handover currently recommends for speed, and the two goals genuinely conflict.
  Worth a decision rather than a habit.

Nothing about this was user-visible: production served `0.31.0` throughout, first
at `30d21293` and then at `c1026407`, and the two differ by no application code.
