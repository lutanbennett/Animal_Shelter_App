`0195` narrows read on `site_content`, `site_pages` and `site_content_photos`

### Defect 1, and what the next release manager should take from it

The handover already says `main` moves under a release and prescribes the two
remedies that worked: **pin both Pi builds with `--ref <release sha>`** and
**re-run `release-prs.mjs` against the release SHA rather than `HEAD`**. Both
earned their place here — the `--ref` pins meant the Pi builds were never
ambiguous, and the re-run is the only reason `#625` is in this record at all.

What it does not yet say, and should:

- **The Worker deploy cannot be pinned.** `deploy.mjs` takes no `--ref` and
  refuses a `main` that differs from `origin/main`, so the Worker is always built
  from whatever `main` is at that moment. The Pi and the Worker therefore have
  *different* exposure to a moving `main`, and the asymmetry only shows up when
  it bites.
- **So the window to protect is from the cut's merge to the production Worker
  handover.** Everything built before a late merge has to be rebuilt afterwards
  if "all four from the release SHA" is to stay true.
- **The cheap mitigation is ordering, not vigilance.** Hand over the production
  Worker deploy *first*, then build the two Pis pinned to whatever SHA that
  deploy reports. That costs nothing and makes a late merge harmless. This
  release did the opposite — Pis first, to parallelise — which is what the
  handover currently recommends for speed, and the two goals genuinely conflict.
  Worth a decision rather than a habit.

Nothing about this was user-visible: production served `0.31.0` throughout, first
at `30d21293` and then at `c1026407`, and the two differ by no application code.

### The silent-failure question, and why the dangerous-looking file is the safe one

**One real candidate, and it closes.** `0198` creates `map_room_placements`, and
the Enclosures page reads it through an embedded select —
`src/app/enclosures/page.tsx:238` — whose error is discarded: `const { data:
roomRows }` with no `error`, then `roomRows ?? []`. PostgREST answers an embedded
resource the caller may not read with an **empty array rather than an error**, so
a policy mismatch here would take every room off the facility map with nothing
said, on a page that would otherwise look perfectly healthy. That is the exact
shape the question exists to catch.

It closes because the two policies are the same policy, and that was established
by **diffing them, not by reading `0198`'s header claim that they match**:

- `0198`: `map_room_placements_read on map_room_placements for select to authenticated using ((select private.has_app_access()))`
- `map_rooms`, as narrowed by `0170` after the 2026-10-09 finding: `map_rooms_read on map_rooms for select to authenticated using ((select private.has_app_access()))`

Character-for-character identical, and `map_rooms` is read in the **same query**
as the embedded placements. So no login can be allowed the rooms and refused their
placements: either both answer or neither does, and "neither" is the pre-existing
behaviour of a login with no app access rather than anything this release
introduces.

**`0199` is the one that sounds far worse and is safer, and it is the better
worked example.** It drops the two unique indexes on `is_purchase_unit`, removing
the database's guarantee that an item has exactly one purchase unit — precisely
the change that normally lets old code quietly pick an arbitrary row. It does not
here, for two reasons that were checked rather than assumed:

- **Nothing in the app ever picked "the" row by that column.** The only resolver
  in the tree is `src/lib/units.ts:160`, and it reads
  `conversions.find((c) => c.isDefaultPurchase) ?? conversions.find((c) => c.isPurchase) ?? null`
  — the new column first, with the old one as a fallback. Every other hit on
  `is_purchase_unit` in `src/` is the Units panel listing rows or writing one.
- **The migration keeps the old invariant true anyway**, with a trigger: the first
  bought-in size of an item becomes its default, and unticking the default
  promotes another bought-in size, so `is_purchase_unit and is_default_purchase`
  names exactly the one row the dropped index used to name.
  `scripts/check-unit-conversions.mjs` asserts both halves in a rolled-back
  transaction — `FAIL C second purchase unit refused` and
  `FAIL C default not handed on`.

`0199`'s price decision is deliberately inert in this release: the view
`item_latest_delivery_cost` is created, but the forecasts and Cashflow still read
`cost_per_unit`, so nothing is re-valued by applying it.

**One finding, recorded rather than fixed: `0199`'s `-- consumer:` header is
wrong.** It declares `-- consumer: none`, but `src/lib/units.ts` selects
`is_default_purchase` in its column list and resolves through it, and that code
merged in `0199`'s own PR (#635). An applied migration is never edited, and the
header's only mechanical effect is the advisory release warning, so this is
recorded as a defect rather than corrected. It is also the benign direction: the
consequence of applying late would be a **loud** `42703` from PostgREST, not a
quiet empty result. **This is the handover's "a header is a statement of intent,
not evidence — diff it" earning its keep for the second release running**, and
this time the diff found the header actually wrong rather than merely unproven.

### What the next release manager should take from this one

**The build-order question is settled — do not re-derive it.**
`docs/decisions/2026-10-15-worker-first-then-pin-the-pis.md` is the answer:
production Worker first, then both Pis pinned with `--ref` to the SHA it reports.
`0.31.0`'s record and the handover both left this open and asked for a decision
rather than another silent choice, and this is it. The one thing to know is that
**this release did not test it** — `main` held still — so a later release that
sees `main` move under it is the first real exercise. Do not read a quiet release
as the decision being unnecessary.

**Two first-run-clean `release-prs.mjs` runs in a row still do not mean it is
fixed.** Nothing in the script changed. This range, like `0.31.0`'s, happened to
contain no squash-merged PR.

**A gap in the PR numbers has a cheap, definitive check.** `#638` was missing from
this range and the answer took one `gh pr view 638 --json state`: still open,
another session's work. Do that rather than reasoning from the numbering, in
either direction.

**The cut plan can be written before the PR is opened, and it changes the CI
shape.** Committing the plan alongside the cut made the **first** CI run green,
where the template expects it to fail on `test-plan` by construction. The cost is
that the plan's header has to guess the PR number — it guessed #638 and the PR
came out #639 — which the CI-green commit then corrects. Worth doing: it trades a
guessed number for a run that is green from the start, and the second run still
happens because ticking the CI line is itself a commit.
