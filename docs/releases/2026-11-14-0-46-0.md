### A COUNT THAT MOVED WITH NOTHING UNDERNEATH IT — RECORDED AS UNRESOLVED

`0.45.0`'s record says `table-policy-commands` finished that release at **78 output lines / 75
`no policy`**. Measured today, before any apply: **74 lines, all 74 `no policy`**. Between the two
readings **production had no migration applied** (367 both times) and **the check's own code did not
change** (`scripts/lib/readonly-checks.mjs` has no commit in `15854dd4..HEAD`), and the check reads
only `pg_class` and `pg_policies` on the live database. It reproduced at 74 on a second run.

**So one of the two figures is wrong, and it is probably the older one** — that release's record
documents this very count being mis-counted by hand once already, and today's has its saved output
file beside it. It is recorded rather than resolved: it gates nothing, and chasing it would be the
scope-creep the runbook forbids. **For the planner, not for a release.** The lesson is the one
`0.44.3` and `0.45.0` both wrote down from the other direction — *count it, do not read it over* —
with one addition: **say which run the figure came from, so the next reading can be compared rather
than guessed at.**

### TWO OF THE SIX BUILDS ARE THE CUT COMMIT AND FOUR ARE NOT — AND I NEARLY PUBLISHED THE WRONG COUNT

An earlier draft of this record said *"five of the six builds came from the cut, and the sixth is
code-identical"*, copied in shape from `0.45.0` where that happened to be true. **It was wrong here.**
`main` moved early — PR #1577, a planner handover — so everything after the first two builds picked up
`4644759ef`, including **Lutan's production Worker**, which the draft had down as the cut.

What caught it was reading `/api/version` on all three hosts and seeing **two different SHAs**, then
going back to each of the six build logs for the `built from` line rather than reasoning about the
order things happened in. Two of those reads came back blank for mechanical reasons and both were
nearly taken as absence of evidence:

- **Lutan's own log is UTF-16**, because PowerShell's `tee` writes it that way, so `grep` matched
  nothing at all on a 26,430-byte file. `tr -d '\000'` reads it.
- **The UAT Pi's log needed `grep -a`**, for the same class of reason.

**The durable claim is code identity, and it holds for all six.** The diff between `afc48e409` and
`4644759ef` is exactly:

```
docs/planner-handover.md
docs/test-plans/handover-746.md
```

and filtered to everything outside `docs/` it is **empty**. So every build carries identical code, and
the SHA spread is two documents. `0.45.0` recorded the same shape from `docs/backlog.md`. **A claim
about SHAs decays; a claim about code identity does not** — and this release is the one that shows why
a SHA claim must be *measured per build* rather than inferred from when the release started.

**Both Worker deploys were confirmed from `wrangler deployments list`, not from "it finished"** — the

### TWO OF THIS RELEASE'S HEADLINE FEATURES CANNOT BE REACHED BY THE PUBLIC YET, AND THAT IS BY DESIGN

Signed out, on production **and** UAT:

```
/shop/merch               307 → /login?next=%2Fshop%2Fmerch
/services/report-animal   307 → /login?next=%2Fservices%2Freport-animal
```

**This is not a fault.** `PUBLIC_SITE` is `"locked"` on both Workers — read from the UAT deploy's own
binding list, `env.PUBLIC_SITE ("locked")`, not from a document — and `src/lib/public-site.ts` defines
`locked` as exactly this: *"strangers out, staff may preview. A signed-out visitor gets the sign-in
landing page and every other website address redirects to /login; a signed-in login still sees the
website, so staff can check it before go-live."* The whole public website is pre-launch.

**But it is worth saying plainly, because two release notes read as present tense.** The merchandise
note is careful — supporters *"will be able to buy"* — while the report-an-animal note opens *"The
website has a new Report an animal page (under Services) where anyone can tell the shelter about a
stray"*. Nobody outside the shelter can, today, because the site is locked. The note is not false to
its readers (release notes are read by signed-in staff, who **can** see the website), and it is not
this release's outstanding step — the lock is a standing pre-launch state, not something `0.46.0`
left undone. **Recorded, not fixed:** editing a note that has already mailed would be worse than
noting it, and the release-note truth rule governs a PR's own outstanding steps.

**What this record cannot say:** that a signed-in person has loaded either page on production. Claude
has no account there, and while the site is locked a signed-out check can only ever see the redirect.
The mechanism was read in code and the lock state read from the live binding; the page itself has not
been seen working on production by anyone. It is on the manual list.
