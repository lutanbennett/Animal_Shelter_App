and is reconstructed here, five hours and one release later; `0.18.0`'s was

thing worth recording, because it is the failure mode this whole file exists
against: a release record has no automated trigger, so it only exists if someone

### `0133`'s own note was stale, and the consumer header is what caught it

The migration says **"ADDITIVE AND READ BY NOTHING YET"**, and
`apply-migrations.mjs` repeated it. That was true when #333 wrote it as a
schema-first PR. It was false by the time #335 and #342 landed the reader in the
same batch: `src/lib/recurring-jobs/eligibility-load.ts:28` calls
`supabase.rpc("role_can", …)` at runtime.

So `0133` had to be applied **before** the deploy, not merely before the next
one. It was. What made the claim checkable was the `-- consumer:` header naming
a file: grep the area, find a real `rpc(` call rather than a comment, conclude
the note is stale. Three of the four `role_can` references in `src/` are
comments; the fourth is the call.

Two things left open by it: the note is misleading to anyone reading `0133`
cold, and its header names `src/lib/recurring-jobs/eligibility.ts` while the
caller is `eligibility-load.ts` beside it. Applied files are never edited, so
both are recorded rather than fixed.

### The red dry-run meant "apply", and that was checked rather than recognised

```
dry-run 0134_volunteer_narrowing.sql … ok
dry-run 0135_perm_convert_medical.sql … ok
dry-run 0136_medical_role.sql … FAILED
Failed to run sql query: ERROR:  42883: function sees_all_clinical() does not exist
```

`CLAUDE.md` documents this: each file is dry-run in its own `begin … rollback`,
so a file depending on an earlier **pending** file fails, and "the trap is that
a red dry-run normally means *do not apply*, and here the correct action was to
apply".

The temptation is to recognise the shape and move on. Instead:
`sees_all_clinical()` is created by `0135_perm_convert_medical.sql` **at line
56** — an earlier pending file, rolled back before `0136` ran. All six then
applied `… ok`, which is the confirmation rather than the assumption.

The distinction `CLAUDE.md` asks for, stated plainly: **the dry-run failed
because of how the runner works, not because the file is wrong.**

The consumer-header warnings fired as designed, naming files that did not exist
in `0.17.0` — correct, since they ship here:

```
WARNING 0134_volunteer_narrowing.sql: declared consumer src/lib/residents/who-and-where.ts does not exist in release 0.17.0.
WARNING 0136_medical_role.sql: declared consumer src/lib/home/tiles.ts does not exist in release 0.17.0.
```

### The cut script met a third note shape and refused

`unreleased` has held two shapes: a multi-line object with roles, and a bare
string. This release introduced a third — a whole object on one line — and the
parser threw:

```
Error: unrecognised line in unreleased: "  { text: \"Search on the Residents list now finds a resident by their ID…
```

That is the behaviour `0.16.0` bought, where a comparison keyed on one shape
would have checked two of seven notes while printing success. Here the parser
hit something it did not recognise and **stopped**. It was taught the shape and
re-run, and the cut verified through the parsed module: `7 of 7` carried across,
`text lost: 0`, `role tags changed: 0`,
`majorReleasesSince("0.17.0") → ["0.18.0"]`.

Its closing tally still counts a single-line object as "string form", so the
printed summary is wrong. That is why the verification is a separate pass, and
it is on the cut plan as a defect rather than tidied away.

### `gh pr checks` reported a check as pending after it had passed

`script-integrity` showed `pending 9s` long after the run finished. The run's

honest-looking move — waiting for a check that will never turn green — looks

### A validator was run and its answer thrown away

Recorded because it is the same shape as the faults this file keeps describing,
and because it was mine. The cut's test plan was committed **failing**:
`check-test-plan.mjs` was run through `| head -3`, which swallowed its output
and its exit code, and the commit was chained after it with `&&`. The checker
had correctly rejected an `n/a *for this PR*:` — the reason must follow the
colon immediately, which is what keeps every reason greppable.

It was caught a minute later by re-running the checker on its own, and fixed in
`751fc5f5`. CI would have caught it regardless. The lesson is not about the
typo, which is trivial and was made once before: **a validator whose result is
discarded is worse than one that was never run, because the transcript shows it
running.**

### The cut script's tally was wrong again, for the second release

It printed `object form: 0, string form: 8` for a register holding four
single-line objects. This is `0.18.0`'s defect 1, unfixed, and it now disagrees
with the verification pass in the same output. The verification is authoritative
— it reads the parsed register through `noteText` and `noteRoles` rather than
counting lines, and reported `8 of 8` carried across with `role tags changed: 0`.

Two disagreeing numbers in one output is worth fixing rather than explaining a
third time. It was not fixed inside a release cut deliberately.
