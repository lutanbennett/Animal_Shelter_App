A major release: the first since `0.32.0`, and the first in four where the mail
actually goes out. Three genuinely new abilities ship — Record Weight's "Weigh
these first" list, the "Counting since (year)" box on impact figures, and Thai

### What shipped

Five notes, all untagged, so every signed-in role sees all five:

- Impact figures get an optional "Counting since (year)" box, so the home page can read "Animals rehomed since 2019" in English and Thai
- Residents get optional Thai breed and colour, shown to Thai readers of the website with the English kept where no Thai is typed
- Record Weight opens on "Weigh these first" — every animal the vet saw yesterday or today with no weight recorded since, each leaving the list as its weight is saved
- The "All zones" button shows as chosen in plain white or black, so it no longer reads as the Orange zone being picked
- Registering a resident shows the intake date again instead of "NaN undefined NaN"

**One feature shipped with no note, on purpose.** The vet calendar (#656) is in
this release as code. Under the release-note truth rule a note would have
promised every admin a feature that may do nothing yet, so there is none, and
the cut asserted its absence mechanically rather than trusting that nobody had
written one. See *What this record cannot say* for the part that is genuinely
unresolved.

### A correction to this release's own cut test plan

**`docs/test-plans/cut-release-0-33-0.md` says #662 was "open on purpose" and
"the only gap". That is wrong, and this record supersedes it.** #662 merged at
`08:15:42Z`, roughly twenty minutes *before* the plan asserting it was still open
was written, and about half an hour before the cut PR merged. It is in the
release: `83ff5a86`'s first parent is `3db9bdd9`, #662's merge commit.

What actually happened is the benign version of this: the intention was to leave
#662 alone so `main` could not move after the cut, and the *outcome that mattered*
still held — #662 landed **below** the cut, `main` did not move after `83ff5a86`,
and all four builds came from one SHA. Nothing shipped that should not have, and
#662 is a docs-only change with its own completed plan.

**The fault is one of method, not of consequence.** The plan asserted the state
of a PR from an intention formed earlier in the session instead of re-reading it,
and a test plan is exactly the wrong document in which to state something
unchecked. The same habit applied to a migration or a deploy target would not
have been harmless. Logged as Defect 3.

### The silent-failure answer

The public-view rule — *a column is public only when the public view names it*,
and an omission is silent rather than an error — **closes clean**, for the first
time in three releases. Each of the three columns this release's public-facing
code reads was checked by reading the view, not the `-- consumer:` header:

- `since_year` — `0204` rebuilds `public_impact_figures` and names `b.since_year`
- `breed_th`, `colour_th` — `0205` rebuilds both `public_resident_cards` and `public_resident_profiles` and names `r.breed_th, r.colour_th` in each
- `0209` claims in its header that it needs no view change, and that claim is **true** — it registers the two columns for the signed-in Translations page, and the public views already carried them from `0205`

**One shape worth knowing rather than discovering.** `weigh_first_visits()` gates
on `has_permission('medical.weight', 'edit')` and returns an **empty set** rather
than an error when it is not held — so a permission problem would look exactly
like "there is nobody waiting to be weighed". It was traced rather than assumed:
`0194_role_cards.sql` gives `head_of_medical` the `record_weight` card, which maps
to `medical.weight` at level 2. An empty list is still not by itself proof the
read works.

### What this record cannot say

- **Nothing on the public site was smoke-tested, and this release put real work there.** `PUBLIC_SITE` is `locked`, so an anonymous request to `lannacare.org` gets the staff gate — confirmed this release, served `Cache-Control: private, no-cache, no-store` with `x-lanna-cache: MISS`. The "since &lt;year&gt;" label on the home page and the Thai breed and colour on `/adopt` are both public surfaces, and the deploy proves only that the code and schema shipped. **The edge-cache check is vacuous, not merely hard**: there is no cacheable public page to get a `HIT` on.
- **No signed-in smoke test was run.** This session has no account, so `/residents`, a resident hub, `/management/dashboard`, `/admin` and the Drive-connected line were not loaded. They are deferred to a person, as in every release since the site was locked.
- **Whether the vet calendar is actually live on production is unresolved.** `strip-baked-env` lists `GOOGLE_CALENDAR_REFRESH_TOKEN` and `GOOGLE_CALENDAR_ID` among the 13 it removed from the Worker bundle, which means they exist in the build environment — so the feature may be configured rather than dormant. Whether the production **Pi** carries them could not be checked: the read was refused as a production read, and that refusal was not worked around. The Worker's own quarter-hourly sweep needs `GOOGLE_CALENDAR_REFRESH_TOKEN` as a Worker binding and it is not in the bindings list, so **the sweep will no-op regardless**; the direct sync on save is the Pi's. Either way the release is safe — no note promises the calendar — but "dormant" is an assumption this record is not entitled to make, and the next release should settle it rather than repeat it.
- **The restore test into a real Supabase project has still not been done** — eight releases now, and still the cheapest item on the outstanding list.
