## Findings for next time

- **The record convention collides.** `docs/releases/<date>.md` assumes one release
  a day and three landed today. Either the filename needs the version
  (`2026-09-24-v0.2.1.md`) or the file needs to be a day's log, as this one is.
- **A release record written by a script is not a smoke test.** Everything a
  `curl` can reach is ticked above and everything it cannot is outstanding. If the
  browser items matter — and the cache one does, since the edge cache is what keeps
  public pages off the CPU-limited render path — they need a person, and the record
  should stay honest about that rather than quietly ticking what was inferred.

## 0.2.2 — appended 2026-09-24

The fourth release of the day, cut after `0.2.1` shipped. One customer-facing
change, and unlike every release before it **that change was verified by a
person before it shipped**.

### What is in it

Six PRs merged since `0.2.1` (#94–#99). Exactly one carried a release note: the
user manual's Contents list now stays in place on a computer with its own scroll
bar, and opening a link to a topic highlights it and scrolls the list to show it.
The other five are internal — the `test-plan` CI change, the Data API grants
migration, and documentation.

`major: false`, so no admin email. `majorReleasesSince("0.2.1")` was checked to

### Schema

Two migrations were applied to production ahead of this release, both after a
clean dry-run:

- `0077_data_api_grants.sql` — writes down the grants Supabase's
  `alter default privileges` currently adds for itself. **A no-op on the existing
  databases today**; it matters from 2026-10-30, after which a from-scratch
  project built without it comes up with every table unreachable through
  `supabase-js` whatever RLS says. That is exactly what the domain cutover
  plans to do, so having it in the history is the point. Applied with no app
  code change and **no deploy**, because nothing that runs had changed —
  `git diff` over `src/`, `worker/` and `public/` was empty.
- `0078_prescriptions_diets_updated_at.sql` — `updated_at` on `prescriptions`
  and `resident_diets` plus a trigger to maintain them. Schema ahead of code:
  nothing merged reads either column yet. **The trigger is now live and fires on
  every write to those two tables**, which makes it the newest moving part near
  prescriptions and diets.

## 0.3.0 — appended 2026-09-24

The fifth and largest release of the day: eight PRs (#101–#108), four notes, and
the first `major: true` since `0.2.0`, so **admins were emailed**.

### What is in it

Two new public-facing capabilities, which is why it is major:

- **Shelter Friends** — local businesses that help the shelter get a published
  card on the public site, with a thank-you strip on the home page and a mention
  on Donate. Nothing appears until it is published, and archiving the contact
  takes the card down.
- **Public kennel QR codes** — scanning a kennel now shows the enclosure's name,
  its zone and a card per resident, instead of a sign-in page. The note is
  explicit about the boundary: nothing about capacity, notes or repairs is shown,
  and Hospital, Fostered and the other status buckets have no public page at all.
  Signed in, the code still opens the enclosure page as before.

Plus phone handling for the desktop-shaped setup pages ("Best on a larger
screen", with **Show anyway**), and frequency options moving from
Management → Medications to Settings → Frequencies.

### Schema

- `0079_public_enclosures.sql` — the view behind the public QR page. Applied
  before this release.
- `0080_social_urls.sql` — `facebook_url` and `instagram_url` on
  `site_content`. Applied after a clean dry-run. **Schema ahead of code**: the
  four merged files that mention `facebook_url` all read it from
  `shelter_friends` (added by `0076`), not from `site_content`, and
  `SITE_CONTENT_COLUMNS` does not list the new columns. The consumer — social
  icons in the public footer — is not built yet.

Production ended at **80 applied, 0 pending**. **28** public-view checks pass,
including the new `public_enclosures`: `anon` can SELECT it and is refused
PATCH and DELETE, so the new public surface is read-only as intended.

### The cache question, answered

Lutan tested the edge cache in a browser on 2026-09-24 and it is working — the
item that had been outstanding across four releases. He also reported that
`1102 Worker exceeded resource limits` still appears occasionally, and both
facts are true at once rather than in tension:

`worker/index.mjs` only serves from cache when a request is a GET, for a public
page, **with no Supabase auth cookie**. So every signed-in staff page bypasses the
cache and renders in the Worker at 30–40 ms against a 10 ms budget, which is
where the `1102` comes from. A smaller case: the first anonymous hit per data
centre per 10 minutes is a MISS and renders in the Worker too.

The cache was never going to fix that, and is not failing. The fix is the
Raspberry Pi origin (`docs/pi-hosting.md`), due the week of 2026-09-28. Two of
its steps — the `ORIGIN_KEY` secret and the WAF rule on `pi.lannacare.org` —
are Cloudflare-side and can be done before the Pi is physically up.
