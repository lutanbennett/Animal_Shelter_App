### What is in it

Eleven notes — the longest entry the register has held; the previous high was
eight, yesterday. The order was changed at the cut, as `0.22.0`'s was: they left
`unreleased` in the order their PRs happened to add them, which put a **privacy
narrowing** and a **Thai PDF fix** above three brand-new sections. A major
release is mailed, so the entry is also what every admin reads first.

1. **Management → Donations** — record a gift and the app issues its numbered receipt, saved to Drive (Admin and Management)
2. **Management → Translations** — one place to translate everything a Thai reader sees, not just the long text (Management)
3. **Operations → Outreach visits** — temple and village dogs recorded on a phone, feeding the home page's impact figure (Management)
4. **Shelter Operations is now Operations**, with Unallocated, Fostered and Hospitalised chips on Residents (everyone)
5. **One row of zone chips** on Enclosures and Residents, with every off-site zone under one Off-site chip (everyone)
6. **A vet's cards now open what they count** — overdue visits in red, oldest first (vets)
7. **Contacts have Address and Map link** as two boxes, the address printed as words (everyone)
8. **The carer list shows names without phone numbers** when fostering or rehoming (everyone)
9. **Settings → Recent changes names every kind of change it lists** (everyone)
10. **Recurring job titles wait on Translations** with the rest of the text (Management)
11. **Thai PDFs no longer drop the last letter** of a line containing ำ (everyone)

All eleven are untagged, so every signed-in role sees every one of them.

`major: true` on Lutan's call, asked before cutting with the argument for each
side put to him. The case he took: **three roles gain whole sections they never
had — Donations, Translations and Outreach — and a menu entry is renamed**, so
someone who knows where the daily work lives will go looking under the old name.
The case against, which he heard: nothing is removed and every old link still
opens. Same shape as `0.21.0` and `0.22.0`, three releases running.

`majorReleasesSince("0.22.0")` returned `["0.23.0"]` before the cut was
committed, and the production deploy mailed accordingly.

Lines were moved, never retyped — the cut script lifts each note's own source
line and re-indents it — and the result was compared as a **set** and as a
**permutation**: `got [3,4,0,7,6,8,9,1,10,5,2], intended [3,4,0,7,6,8,9,1,10,5,2]`,
every source note used exactly once, `role tags changed: 0`,
`carried across unchanged: 11 of 11`, text lost 0, invented 0, all 35 previous
entries byte-identical. Sixteen assertions from one script that exits non-zero on
any failure.

**Three notes were candidates for a role tag and all three were left untagged** —
the donation receipts, the carer phone-number change and the recurring-job
titles. An untagged line is never filtered out, a wrong tag hides a line from the
people it is for, and a tag invented at the cut is a change to a note its own PR
did not write.

The order was then confirmed **in the delivered mail**, not just in the register:
the message's preview text opens *"New: Management → Donations. Record a gift
(who gave, when, how, what it is for, and"*.

### The silent-failure question answered *yes* this time

`0.21.0` established the question and held the release on test; `0.22.0` asked it,
read the candidates in code, and answered no. **This release is the first where
the answer was yes**, and the shape of what followed is the point: it was named
on its own, before the cut, in the same round as the major/minor call — not
folded into a count of unsigned plans.

**`0170_close_the_over_grants` narrows the `contacts` read policy to
`contacts.browse`, which staff do not hold.** The new code reads a cut-down
`picker_contacts` view instead — but the *live* `0.22.0` code read the table
directly, confirmed rather than assumed:

```
live (0.22.0) src/lib/contacts/carers.ts:27   .from("contacts")
this release   src/lib/contacts/carers.ts:29   .from("picker_contacts")
```

So between the production apply and the Pi finishing its build, **a staff login's
carer picker returns no rows** — and an empty picker reads as "no carers", not as
an error. Management and Admin hold `contacts.browse` and were unaffected.

Lutan was given three options: go ahead with the window kept short, wait for a
quiet hour, or hold the release on test. **He chose to go ahead**, and the
mitigation was to apply the migrations and start the Pi production build in the
same breath. The Pi build finished in **about three minutes**, so the window was
roughly that, against a budget of five.

What the migration actually closed is worth recording, because the window was the
price of it: **any staff login could read every contact's phone, email, address
and notes straight off the table** by sending a request by hand with its own
token — a right no screen ever showed. Two more went with it: any signed-in
login with no role could reset a prescription, diet or frequency to its default
rounds, and `facility_maps` and `map_rooms` were readable by every signed-in
login including `public_viewer`.

### Migrations

Seven, `0165` through `0171`. Production went `164 applied, 7 pending` to
`171 applied, 0 pending`. All seven **dry-ran `ok`** twice — once early and once
immediately before the apply — and the per-file `begin … rollback` trap did not
bite, although `0171` was the file to watch: it is a correction to `0170` on the
same branch, and a dependency between two pending files is exactly what produces
a red dry-run that should still be applied. It did not arise.

The consumer headers warned loudly and correctly, and the runner's own framing
is the one to keep:

> *These tables/columns land before the code that reads them is live. That is the
> safe direction - nothing is blocked - but do not deploy the reader before this
> is applied, and expect nothing to use it yet.*

**That framing fits six of the seven and not `0170`.** The others add tables and
columns nothing yet reads; `0170` *narrows a policy that live code was using*, so
its direction is not merely "safe but early" — it is the one file whose apply
changes behaviour before the deploy catches up. A reader who takes the runner's
note as covering all seven misses the only one that needed a decision.

`0.20.0`'s correction was followed: **merge, pull, apply, deploy.**
`git status -sb` was read after the pull and again immediately before the
handover, reporting neither ahead nor behind at `7928bd7a` both times.
