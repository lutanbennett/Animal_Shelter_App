**Written after the fact, from `deploy.log`.** Lutan ran the deploy himself — the

**Fourth release running whose record lagged its deploy** (`0.6.0`, `0.8.0`,

at all, and again everything below is quoted rather than remembered. This is no
longer an occasional slip — it is the normal outcome, and the cause is structural:
the record has no trigger of its own, because it is written *after* the deploy
*from* its output, and whoever deploys is not always whoever writes records. The
two fixes proposed in `0.8.0`'s record — a nudge at the end of `deploy.mjs`, or a
script comparing `latestRelease.version` against `docs/releases/` — are both still
unbuilt. Lutan's call, but the evidence for the first one is now four releases deep.

### What is in it

A vet sees only the residents their own clinic treats, with each one's whole
history; an Access requests card on Settings → System status and a Review access
requests task for admins; prescriptions and diets that ended yesterday no longer
showing as current before 7am, and three placement forms no longer offering the
day before; admin pages showing the real reason an action was refused; the puppy
loader on the way to `/adopt`; and refiling a resident photo into another folder
from the photo viewer.

`major: true`, so admins were emailed. The reason it was major was the lead note:
a vet account with no clinic set sees no residents until an admin sets one.

deploy looks like in the log, and the next person reading this file should not have
to work out which it was.
