### What shipped

Five notes. One is untagged, so everyone sees it; the other four carry the role
tags their feature PRs wrote.

- **The app now reads properly on a phone held upright, in English and Thai.** Every one of the 121 screens was checked at phone width and nothing scrolls sideways any more. The screens that changed most are the resident actions — Send to hospital, Move, Rehome, Record death — where a long name no longer wraps one word per line; the maintenance edit page, whose due date and Clear button pushed the page wide; the donation appeal pages; and the outreach forms. The animal then shows a Read their news link under its picture in Happy endings on the public adoption page. The staff note is never shown, and nothing is published unless someone ticks it *(`admin`, `management`)*
- **Add Medical Photos and Record Weight can pick the resident from their name card.** Type the printed code, paste the card's link, or tap Scan card and hold the phone to it *(`admin`, `management`, `head_of_medical`)*
- **The Status alert mail tile now says what to do** when it is red, instead of only reporting that the last alert mail reached nobody *(`admin`)*
- **The assistant can record a death and place a resident with a foster carer or an adopter.** Nothing is recorded until Confirm, the date is left blank unless it was typed, and a death asks once more in the same words as the Record death page *(`admin`, `management`)*

Three `-- consumer:` warnings printed, all naming the live release `0.34.0` as
differing from the declared consumer — `check-public-views.mjs` and
`src/lib/assistant/audit.ts` for `0214`, `src/app/adopt/HappyEndings.tsx` for
`0215`. That is the safe direction: the columns and views land before the code
that reads them.

Afterwards: **`216 applied, 0 pending`** and
**`No drift: production matches origin/main`**, 216 of 216 in both directions.

**`0213` is the file worth knowing about, and it was not taken on trust.** It is
the one non-additive migration in the release: it rewrites two live column types
to match the shape dev has always had, after the database review of 2026-10-13
found they had been hand-edited on dev and never written down as files.

```
immunization_types.interval_months  integer (0007)  ->  numeric not null
zones.internal  boolean not null default true (0004)  ->  nullable, default true
```

Two things about it that no gate would have told us:

- **Its view-rebuilding block had never executed anywhere.** The block is guarded by `if v_type = 'integer'`, and dev is already `numeric` — so the guard is **false on dev**, the block is dead code there, and **production was the first place it would ever run.** It drops and recreates `immunization_next_due` and `picker_immunization_types`, because Postgres refuses to retype a column a view reads. A wrong grant or a lost `security_invoker` there would have been **silent**: immunization due dates would simply stop appearing for some role, with nothing showing an error.
- **It refuses loudly rather than guessing.** `0007` documented a null `interval_months` as "one-off, no recurring due date", and the file raises an exception rather than inventing an interval if production holds such a row. The clean dry-run is the evidence that it holds none — and this is the case where a clean dry-run is a *finding*, not a formality.

**So it was verified by its effect, before and after, not by its exit code.**
Before the apply, the two views' shape was read off **dev** as the reference.
After the apply, the same facts were read off **production**:

```
  column    internal                                       boolean nullable
  column    interval_months                                numeric not null
  grant     immunization_next_due                          authenticated SELECT
  grant     picker_immunization_types                      authenticated SELECT
  nullrows  immunization_types.interval_months null count  0
  viewopt   immunization_next_due                          {security_invoker=on}
  viewopt   picker_immunization_types                      (none)
```

That is dev's shape exactly: `authenticated` keeps `SELECT` on both views,
`security_invoker` is `on` for `immunization_next_due` and unset for
`picker_immunization_types`, `anon` holds no grant on either, and there were no
null-interval rows for the guard to refuse. The only divergence from dev is
`service_role` losing write privileges on a view, which nothing can use. **The
"after" read is what makes this evidence rather than assertion.**

### The silent-failure answer

Three candidates, each read in the code rather than taken from its header.

- **Adoption success stories on the public site — the real one.** A surname, an email, a phone number or the note an adopter wrote to staff reaching a public page would be silent, and `0214` creates a view that strangers on the internet read. The header's claim was diffed rather than repeated: `public_adoption_updates` selects **five columns only** — `id`, `resident_id`, `drive_file_id`, `public_story`, `public_first_name`. `received_on`, `sender_contact_id`, `channel`, `note`, `created_at` and `created_by` are all absent, and `public_first_name` is typed by hand rather than read from `contacts`, so a surname cannot arrive through a join. The opt-in is `not null default false` and **never backfilled**, so every update that already existed comes out of the file unpublishable. The view also requires `r.is_public_visible`, excludes Deceased animals, excludes the Medical sub-folder exactly as `public_appeal_photos` does, and restricts to image extensions.
- **And the consumer was checked, not only the view** — the lesson `0.34.0` recorded. Every public reader goes through the view: `src/lib/adoption-updates/public.ts` selects exactly those five columns, and `/adopt/stories/[id]` reads nothing else. The direct `adoption_updates` reads are all under `src/app/residents/`, behind sign-in. The photo proxy is the subtle one and it is right: `src/app/api/photos/[fileId]/route.ts` asks `public_adoption_updates` **as the caller**, so unticking the box, hiding the animal or recording a death stops the photo being served the moment the database says so — and the on-disk cache is only consulted **after** that check, so a photo that has stopped being public is not served from disk.
- **`0213`'s retyping** — covered above. Loud by construction, and verified by its effect on production both before and after.
- **`0215`'s view replacement.** It appends `resident_id` to `public_recent_adoptions`, restating every existing column. A dropped or reordered column would break `/adopt` quietly — except that `create or replace view` **cannot** drop, rename or reorder columns; Postgres refuses. So the failure mode is a loud error, not a quiet one, and the clean dry-run covers it.

**One change that could break quietly, named separately from the count and
accepted by Lutan.** The phone-width sweep changed layout on all 121 screens, and
**four were never seen by a person.** If a form came out unusable at phone width,
nothing would error — it would simply not work, and Management on a phone is the
Director's main surface during the day. It was put to him in the opening round as
its own question, separately from the eight pending items, with the offer to put
the four screens on test and tell him where to tap before shipping. **He chose to
ship and accept the risk**, and it is recorded here as an accepted risk rather
than a defect. **It is the first thing to look at if anyone reports a screen that
will not work on a phone.**

### Rollback position

**Code is reversible; schema and the mail are not.**

- Production is served by the Pi, so the code rollback is `./scripts/pi/deploy-pi.sh --ref 598c2e56` there, a rebuild to `0.34.0`. `npx wrangler rollback --env production` reverts only the Worker fallback
- `0214` and `0215` are additive or `create or replace` and safe to leave in place
- **`0213` is the gap, and it has no down-migration.** It rewrites two column types, so a rollback to `0.34.0` code would meet a database where `immunization_types.interval_months` is `numeric not null` and `zones.internal` is nullable. The argument that this is harmless is a real one — both are the shape dev has always had, and dev is the only shape the app has ever been tested against — but it is an argument, not a reversal, and it is a one-way step
- **The mail is the real point of no return.** This is a major release, so the production Worker deploy mails every admin, and that cannot be recalled

The destructive-migration gate therefore **applied** this release, and was not a
formality: `0213` rewrites live columns. The newest production backup is
`lannacare-production-2026-10-16T2000Z.dump.age` (1,215,818 bytes), written at
20:00Z on 2026-10-16 — the **seventh consecutive unprompted cron night** — and it
predates this release's migrations, which is the right direction for a rollback.
The README restore recipe has still never been exercised.
