# Release record — `0.37.1`, 2026-10-19

The **second release of one day**, and a **minor** one for exactly that reason.
Its story is not what shipped — the five notes are four fix bundles and one new
ability, and all of it went live cleanly. Its story is that **two of the three
interventions it cost Lutan were caused by me**: one by starting a Worker build
in the same folder as his, and one by a release-SHA change forced by a PR that
merged mid-release. Both were avoidable and neither was a fault in the software.

### What shipped

Five notes. **Four are tagged and one is untagged**, so unlike `0.37.0` — where
every note was tagged and three roles saw an empty section — every role sees
something on `/releases` this time.

- **Make a meme in the app** — the meme library gains a maker: English or Thai words that wrap to fit, three styles, two crops, the resident tagged and the logo in the corner. Medical photos are excluded. Tagged `admin` only
- **Diets and clinic visits** — a diet that looks like a typo (22 meals a day) is held with a message rather than quietly inflating the food forecast; a past clinic visit is no longer switched to Completed for you. Untagged, so everyone sees it
- **Forms on a phone** — tapping Save before the page has finished loading now waits and saves, instead of saving nothing. Plus a date box that says when a day does not exist
- **Bills** — the cost typed into "Record a new delivery from this bill" is carried through instead of dropped, and appeals no longer list animals who have died, been adopted or are on outreach
- **Photo approval is its own card** — Residents no longer carries the power to approve other people's photos

### Why minor, when `0.37.0` that morning was major

`0.37.0` mailed every admin a few hours earlier. Four of these five notes are
fix bundles, and the one genuinely new ability is tagged `admin` only — so a
major release would have mailed the same people a second time in one day to
announce one new feature.

That is the same reasoning `0.36.1` used, and the standing test and the audience
argument **agreed** again, in the opposite direction from `0.37.0`. Lutan's call,
put to him with the counter-argument stated: the meme maker is a real new ability
and a case could be made for major.

**The check that proves it:** `majorReleasesSince("0.37.0")` returns **nothing**,
asserted mechanically rather than by reading the `major:` flag, and both deploy
logs then printed `no major release new to <env>, so no email`. **On a minor
release the absence of the mail line is the check**, and it is the reverse of
last release, where its presence was.

## THE DEFECT THAT MATTERS: the production Pi reported a failed deploy that had succeeded

`deploy-pi.sh` ended the production build with:

```
# deploy-pi: DEPLOY FAILED — NOTHING NEW IS BEING SERVED
# exit code 1: the build exited with an error (read the output above)
# The Pi is still on the OLD version. Do not announce this release.
deploy-pi: http://localhost:3000/api/version serves 'nothing', expected '0.37.1'.
```

**Every word of that was wrong.** The build had compiled, the Server Actions key
matched (`cbd55beae8d8`, with the second line `the build in .next carries that
key`), systemd had started `0.37.1` at 16:46:19, and `lannacare.org/api/version`
was already answering `0.37.1` @ `9804e211` with `x-lanna-served-by: pi`.

### The cause, and why it is worse than a one-off

The script verifies itself by asking `http://localhost:3000/api/version`.
**Production refuses direct origin requests**, returning `Forbidden` — and it
does so **even with `Host: lannacare.org` set**. The test clone on port 3001
answers normally, which is why the test build passed the same check minutes
earlier.

**It is not new, and that is the part to internalise.** The same `Forbidden` was
recorded at 15:03 that afternoon, from a plain curiosity check run **before any
deploy, while `0.37.0` was still live**. So this self-check has been failing for
some time and nobody noticed, because `0.37.0`'s four Pi failures were **genuine**
— the script was right four times in a row for the wrong reason to trust it.

Two consequences, and the second is the dangerous one:

1. **It cries wolf.** A correct deploy now ends in a red banner telling the
   release manager not to announce the release. The temptation is to roll back
   something that is working.
2. **It exits before the asset check.** `check-assets.mjs` is the last step and
   never ran on production. It had to be run by hand
   (`node scripts/pi/check-assets.mjs --url https://lannacare.org`), and it came
   back `ok … identical to the build`. **A session that trusted the banner and
   rolled back would have skipped the one check that catches a poisoned edge
   cache**, which is the failure that stays broken for a year and is invisible
   from the machine you deployed from.

**The diagnosis took one command, because the handover's lesson from `0.37.0`
was applied**: when one clone behaves differently from its twin on the same
machine, diff the clones before theorising. Production `Forbidden`, test
`{"version":"0.37.1"}`, same moment, same machine. That is also why this cost
Lutan nothing.

**Raised on the backlog.** The fix is for the self-check to ask through the
public hostname, or for the gate to allow a loopback health probe. Until then,
**a red banner from the production Pi deploy is not evidence of anything** —
read `/api/version` on `lannacare.org` and run the asset check by hand.

## The second thing: a PR merged mid-release and the deploy guard forced it in

PR #744 (schema-only, migration `0226`) merged while the release was in flight.
I decided deliberately to **leave it out**: the cut was at `2b8fbb04`, test was
already built and verified there, and folding it in meant re-doing work.

**That decision did not survive contact with the deploy guard**, which refused:

```
deploy: production deploys only from a clean, pushed main:
  - main and origin/main differ (2 behind / 0 ahead)
```

This is the `0.20.0` trap in the runbook, and the guard was right. There is no
way to satisfy it except to pull, which means taking #744. So the release SHA
moved from `2b8fbb04` to **`9804e211`**, `0226` was dry-run and applied to
production, and the **test Worker and test Pi were both rebuilt** so all four
builds still came from one commit.

**Three things worth keeping from this:**

- **"Leave it out" is not a decision the release manager can actually make** once the cut has merged and `main` has moved, unless they are willing to not deploy. Say "I am folding it in because the guard requires it", not "I am excluding it".
- **Folding in a schema-only PR is cheap and folding in an app PR would not have been.** `0226` is `-- consumer: none` with nothing reading it, so the app bundle is behaviourally identical and no release note was owed. An app PR would have meant re-cutting.
- **All four builds came from the release SHA for the sixteenth release running** — but only because the test pair was rebuilt. The streak was nearly broken by bookkeeping, not by anything going wrong.

## Things that look alarming but are not

Everything the previous editions hold still applies, in particular: a red `audit`
never blocks; `| tee` writes UTF-16 so strip the nulls before grepping, and the
arrow does not survive, so grep for the project ref; the `ERROR Failed to copy …`
lines are noise; a backgrounded `deploy.mjs` writing nothing for minutes is
buffering; `-- consumer:` warnings naming files that differ from the live release
are the safe direction. Also:

- **`DEPLOY FAILED — NOTHING NEW IS BEING SERVED` on the PRODUCTION Pi is, as of this release, not evidence of anything.** See *THE DEFECT THAT MATTERS*. On the **test** Pi the same check works and a failure there is real.
- **`Forbidden` from `localhost:3000` on the production Pi is normal** — production refuses direct origin requests, with or without the right `Host`. The test clone on 3001 answers.
- **`strip-baked-env` removing a different count on test and production is expected** — 14 and 13, the extra being `SCRATCH_RESTORE_DB_URL`.
- **`/api/version` and `/api/releases/current` disagreeing mid-release is not a fault** — the first comes from the origin Pi, the second from the Worker. This release had that window twice, once deliberately.
- **A foreground deploy past the ten-minute tool cap is moved to the background, not killed.** Read its log file.
- **A second CI run on the cut PR is correct and expected.**
- **`release-prs.mjs` exiting 0 while printing a DISAGREEMENT is a real third case.** Trace the files to their squash merges and add the PRs by hand; do not treat the exit code as the whole answer.
