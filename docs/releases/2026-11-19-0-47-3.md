## The production Worker is deferred, and why that is safe rather than merely tolerable

**What happened, in order.** Lutan ran his one command three times. The first two died in the build
with `Module not found: Can't resolve '@vercel/turbopack-next/internal/font/google/font'`, preceded by
`There was an issue requesting https://fonts.gstatic.com/...`. Between the second and third the root
cause was found and fixed (below). The third was refused before it built:

```
deploy: production deploys only from a clean, pushed main:
  - main and origin/main differ (1 behind / 0 ahead)
```

**A feature stream (#1716, `#shadm`) had merged while the network was being fought**, and two more were
on the way. That refusal is correct and there is no way round it:

- `releaseProblems()` (`scripts/lib/release-guards.mjs:24`) refuses a guarded deploy while `unreleased`
  has notes, and #1716 added one.
- The clean-pushed-main guard (`scripts/deploy.mjs:304–316`) is `exit 2` with **no override flag** —
  read in the source rather than assumed, because a flag a refusal offers is not advice.

So the tree stopped being a written-down release, and it will not be one again until the next cut.
**There was nothing left to retry, and no attempt was made to reach production by another path.**

**Why a lagging fallback Worker is safe here specifically.** It runs `0.47.2`'s code against a
`0.47.3` database, and this release's eight migrations are **purely additive** — three brand-new
tables, new functions, new policies, nothing rewritten, tightened or dropped (established before the
apply, above). Older code against this newer schema is exactly the direction that is safe. If the Pi
went down, the fallback would serve correctly. **That is a property of this release and must not be
copied forward**: `0.47.2`'s own record says the opposite about its eighteen.

**What it costs until it is closed.** The Worker serves only when the Pi is unavailable, and it sets
the response headers (`worker/security-headers.mjs`), so any header change in this release is not live
— there was none. **What closes it is the next release's production Worker deploy**, which will carry
`c473c1f35` and everything merged since in one commit, in the ordinary way.

### The process fault this exposed, which is worth more than the incident

**Lutan's command is last and it is his, which makes it the step most exposed to `main` moving
underneath it.** The procedure already reversed UAT to sit *ahead* of his command for exactly this
reason — on `0.47.0`, feature PRs merged during the production build and UAT's Worker was shut out for
a whole release (`#uatwk`). **Today the same thing happened to production's Worker, which appears to
be a first.** The ingredient that was new is elapsed time: three network failures stretched a
five-minute step across the better part of an hour, and a stream merged into the gap.

Two things follow, offered as findings rather than changes made inside a release:

- **The release manager should say out loud when the window is closing.** The first failed build was
  the moment to warn that streams merging would end the release, and it was not said.
- **A `--ref` that could deploy the released commit from a moved `main` would close this properly**, and
  `deploy.mjs` already accepts `--ref` as an *assertion*. Making it able to build a named, already-cut,
  already-pushed commit is a small change with a real guard behind it, and it is the difference between
  "retry" and "cut a whole release again". Worth a backlog item.

### The root cause: IPv6 preferred, IPv6 absent — and the two tools that hid it

The deploy machine's address-selection table had the Windows default, **IPv6 above IPv4**:

```
Precedence  Label  Prefix
        40      1  ::/0              <- all IPv6
        35      4  ::ffff:0:0/96     <- IPv4
```

and the machine **had no usable IPv6 address at all** (`Get-NetIPAddress -AddressFamily IPv6`,
excluding well-known, returned nothing). DNS still answered with an IPv6 address for
`fonts.gstatic.com`, so a client that takes the first address and does not fall back stalls until its
own timeout. Measured directly:

```
=== IPv4 only ===            === IPv6 only ===
  try 1: 200 0.213703s         try 1: FAILED (exit 6)
  try 2: 200 0.155932s         try 2: FAILED (exit 6)
  try 3: 200 0.134431s         try 3: FAILED (exit 6)
```

**Why four separate steps failed and every diagnosis came back clean.** `curl` and Node both do Happy
Eyeballs — they race both families and quietly fall back to IPv4. Ten Node fetches and seven curl
fetches of the exact failing font URL all returned `200`, which "proved" the network was fine twice
over. **Turbopack fetches Google Fonts in its own Rust client, which does not fall back**, so it was
the one thing on the machine that met the fault. Cloudflare's API and `lanna-pi.local` are the same
story from different clients.

**The lesson, which is the general one and not about fonts:** *a reachability test run with a
forgiving client is not a reachability test.* The decisive measurement — `curl -4` against `curl -6` —
takes ten seconds and was not run until the fourth failure. Until it was, "transient, retry" was
recorded twice as a finding when it was a guess.

**The fix**, applied by Lutan in an elevated shell and **reverted by him afterwards**, raised IPv4
above IPv6 in the selection table. It was verified at the layer that was failing, by asking the OS
resolver rather than a forgiving client: `fonts.gstatic.com` then returned an `InterNetwork` address
only, and `api.cloudflare.com` and `fonts.googleapis.com` both returned IPv4 first.

### What did NOT recur, which is as worth recording

**The Next.js `SecurityFatalError` advisory halt did not happen once.** It stopped a *completed* build
twice during `0.47.2` — including Lutan's own deploy, where it looked exactly like a stall — and cost
that release a re-run of the gates. This release ships on `16.4.6` (PR #1699) and the gates' build
`exited 0 after 126s` on the **first** attempt, with no re-run line in the log; the dev server came up
first time too. Added to the seven clean stream builds the planner handover records, **this is the
eighth**, and `brief-blocks.md` still describing the halt as live is now safe to rewrite.

### Mistakes of the release manager's own, recorded because none is visible afterwards

1. **"Transient" was recorded as a finding twice before it was measured.** The font failure and the
   Cloudflare DNS failure were each written up as network blips on the strength of a `curl` that
   passed. They had one root cause, it was findable in ten seconds, and not finding it cost Lutan two
   six-minute builds and ultimately the production Worker. *Naming something transient is a claim about
   a cause, and it needs the same evidence as any other.*
2. **The wrong host was named in the warning given to Lutan.** He was told the font fetch could fail
   and to watch for `fonts.googleapis.com`; the host that actually fails is `fonts.gstatic.com`, which
   serves the font file rather than the CSS. He was given a symptom to watch for that would not appear.
3. **The harness reported `exit code 0` for both failed Worker deploys.** Both ran as
   `node scripts/deploy.mjs … > log 2>&1; echo "EXIT=$?"`, and the *shell line* succeeds even when the
   deploy inside it fails — so the completion notification said `completed (exit code 0)` while
   `TEST_WORKER_EXIT=1` and `UAT_WORKER_EXIT=1` sat in the output. **Both were caught by reading the
   captured exit line rather than the notification**, which is the only reason neither was written up as
   a success. Same shape as `0.47.2`'s *"the process table is the instrument; the panel is a view that
   can be stale"*: **the notification's exit code describes the wrapper, not the work.**
4. **The closing window was never named.** From the first failed production build it was foreseeable
   that a merging stream would end the release, and saying so would have cost one sentence.
