### The silent-failure answer

This release's risk is public photo exposure, and it was read in the SQL rather than
taken from the headers.

- **The approval gate is real and complete.** `0217` adds `approved_at` / `approved_by` to `attachments`, NULL meaning waiting, and **six** public views filter on it: `public_resident_photos`, `public_resident_cards`, `public_resident_profiles`, `public_recent_adoptions`, `public_adoption_updates` and `public_appeals`. `appeal_photos_guard()` refuses an unapproved photo onto an appeal. Approval is stamped by a trigger and **never taken from the caller**, and the trigger raises if a login without publish permission tries to change it.
- **The backfill is what stops the gate breaking the existing site.** `0217` sets `approved_at` on every pre-existing row, so nothing already public disappeared when the filter went live. **Verified on production after the apply, read-only**: 121 resident attachments, **0 waiting**, 0 waiting-and-not-medical.
- **`0216` loosens the absolute "never a Medical photo" rule, for appeals only, and does it the safe way round.** The rule is positive and structural: a Medical-folder file **cannot be attached to an appeal at all** without `medical_ok`, which is `not null default false`; `medical_ok_by` / `medical_ok_at` are stamped by the database and the caller's values ignored; the public views are live joins so unpublishing, unticking, hiding the resident or refiling withdraws it on the next read; the photo proxy asks the same view so the direct file URL closes at the same instant; and `is_known_drive_file` is deliberately **not** widened, which would have made every Medical file public. A new narrower activity, `appeal.medical_photo`, decides who may tick it. **On production: `medical_ok` is `not null` defaulting false, with 0 rows ticked.**
- **The interaction neither feature's own plan could catch.** `0217` recreates `public_appeals` **after** `0216` relaxed it. If `0217` had been written against the pre-`0216` definition it would have silently reverted the medical rule — or, because `create or replace view` cannot drop columns, failed loudly. Checked directly: `0217`'s definition carries **both** `att.approved_at is not null` and `sub_folder <> 'medical' or p.medical_ok`, plus the appended `cover_is_medical`. Neither reverted the other.
- **`0219` narrows privilege rather than widening it.** It replaces the service-role client in the Add Shelter Photos route with two functions that check `photos.shelter_add` **inside** themselves, so being reachable is not being allowed, and `set_shelter_photo_folder` writes **only where `drive_folder_id` is null**, so it can never repoint a resident and orphan every photo already filed under the old folder. This also closes the Low defect #699 had accepted.
- **One finding worth knowing, by design rather than by accident:** the approval trigger auto-approves on insert when `auth.uid()` is null — service-role and script writes are treated as a publisher. So a bulk import publishes immediately. It is documented in `0217`'s header as intended, and it is the reason the first version of the test harness below reported a false failure.

#### Defect 1 — the Pi memory fault got worse, and the handover's remedy was wrong

**`0.35.0` found this fault hours earlier and this release proves its prescription
insufficient.** That handover said: expect the first Pi build of each clone to be
killed, budget one retry each, and escalate only if a retry also fails. On
`0.35.0` one retry per clone was enough.

**On `0.36.0` the test clone was killed four times running.** Attempts 2, 3 and 4
were identical re-runs; two of them died even earlier than the first, during
`Creating an optimized production build` rather than the typecheck. Between
attempts the Pi showed **3.5–3.6 GB of its 4 GB available** with nothing
competing — the largest processes on the box were the Next server at 74 MB and
`cloudflared` at 30 MB — so this was never contention or a leak. The build's own
appetite simply exceeds the machine, and it grew again with this release.

**A restart was considered and correctly rejected.** Lutan asked whether to restart
the Pi. The answer was no, with numbers: a restart reclaims memory that is already
free, the box had been up 15 days without leaking, and restarting briefly drops the
Pi as the production origin for no gain.

**What fixed it was Lutan adding swap**, from 2 GB to 6 GB — a 4 GB disk swapfile
alongside the existing 2 GB of zram (`/swapfile2`, visible in `swapon --show`). The
very next test build completed, and the production build then succeeded on its
first attempt. **zram is compressed RAM and adds little real headroom; the
file-backed swap is what did it.**

**Three things to carry forward:**

1. **"Budget one retry" is withdrawn as insufficient.** Retrying is not a remedy; it was luck on `0.35.0`. The escalation rule — stop and tell Lutan rather than improvise on the machine that serves users — is the part that held, and it is what produced the fix.
2. **The swap increase is now load-bearing and undocumented.** `/swapfile2` was created by hand on a live machine. It is **not** in `scripts/pi/setup.sh` or `docs/pi-hosting.md`, so **a rebuilt Pi would go straight back to failing**, and nothing in the repo explains why the swap is that size. The backlog item is updated accordingly: the fix is no longer hypothetical, it is deployed and needs writing down.
3. **The escalation cost a third touch and could not have been avoided.** Enlarging swap needs a `sudo` outside the four commands the Pi grants Claude, so this was always going to be his. The lesson is not "ask less" but "when the blocker is on his machine, bring the diagnosis, not the question" — which is what the numbers above were for.

**It also nearly repeated `0.35.0`'s quiet-failure trap and did not, because the
warning existed.** A killed Pi build leaves the service `active` and the clone
already fetched to the release SHA; only `/api/version` reveals it. Every Pi build
in this release was followed by reading `/api/version` on both hosts rather than
trusting the service state, which is exactly what the previous record asked for.

#### Defect 2 — the deploy poisoned the edge cache, and a user found it, not us

**This is the most important thing in this record, because every check in the
release passed and the app was still broken for a real person on a real phone.**

**What Lutan saw:** the app on his iPhone rendering with **no styling at all** —
white background, default serif text, no orange — while the page *content* was
current and correct. Everything looked perfect from the laptop throughout.

**What made it a real finding rather than a stale browser cache:** he cleared
Safari's data, it came back correct, and **it then broke again minutes later.** A
one-off stale cache does not do that.

**The mechanism.** `/_next/static/**` is served
`Cache-Control: public, max-age=31536000, immutable`, so Cloudflare caches it for a
year and never revalidates. `deploy-pi.sh` builds into a fresh `.next` and then
**swaps it**, so there is a window in which a request for an asset can be answered
with a 404 or a half-written file — and **whichever Cloudflare location serves that
request keeps the failure for a year.** A phone on mobile data and a laptop on wifi
can reach different Cloudflare locations, so it presents as "only broken on mobile"
and is **invisible to whoever is doing the checking.**

**What was ruled out, with evidence, before concluding it was the edge:**

| Checked | Result |
|---|---|
| The stylesheet at origin | Complete, **92,570 bytes, byte-identical to test**, on 20 consecutive fetches |
| Which origin served it | `x-lanna-served-by: pi`, `HTTP 200`, 12 times out of 12 |
| What the page asks for | Exactly that file, and it answers `200` |
| A fresh browser, desktop | Renders correctly, full styling and brand colour |
| A fresh browser at 375 px with a phone user agent | Renders correctly — **so it was never "mobile" as such** |
| The CSP | `style-src 'self' 'unsafe-inline'`; the stylesheet is same-origin |
| The HTML being stale | Served `private, no-cache, no-store` — it is not cached |
| A service worker pinning an old page | None in the repo, none served |
| The edge copy | `CF-Cache-Status: HIT`, `Age: 26158` — cached, and *this* node's copy was good |

**Resolved** by Lutan purging the Cloudflare cache (Caching → Configuration → Purge
Everything), which is the only lever available today: there is **no purge script in
the repo and no dashboard access from a session.**

**Three things to carry forward:**

1. **It will recur on every Pi deploy.** The window is small, invisible, and the consequence lasts a year. Four candidate fixes are on the backlog (`ff55fd1a`): purge automatically at the end of `deploy-pi.sh`; make the `.next` swap atomic; serve assets from the Worker only; or at minimum a post-deploy check that fetches the referenced stylesheet and asserts its length.
2. **Every release check passed while this was live.** All four surfaces agreed on version and SHA, both databases were clean, the keys matched, the mail arrived. **None of that touches whether the CSS a browser fetches is intact**, which is why option (d) — assert the stylesheet's length after deploying — is worth doing even if a better fix lands later.
3. **The release manager cannot see this from the deploy machine.** It was found because the person who owns the shelter opened the app on his phone. That is not a reproducible process. Until the fix lands, **check the site from a phone on mobile data after a Pi deploy**, or accept that this class of fault is invisible.

**Not recorded as a third touch**, though it cost Lutan real time: it was found and
reported by him rather than requested of him, and the purge was the only action
available to anyone. It belongs here as a defect, not as a budget overrun.
