## What shipped, in a sentence

A person reporting a stray can now attach a photo, and that photo is deleted 90 days after the
report is closed; the merchandise shop takes new currencies and previews a product's photo before
the product is public; Management lists nine pages that until now could only be reached from
someone's home screen; and every API-reachable view and function in the database now obeys
row-level security instead of bypassing it.

## THE PI COULD NOT BE REACHED, AND THE MESH IS WHY THE RELEASE RAN ANYWAY

**This is the release's one real finding, and it cost Lutan the third touch.**

The runbook's Pi commands are `ssh lutan@lanna-pi.local …`, and the SSH config resolves that name to
the Pi's address behind the FR205 on the **home** network. This machine was on a **different**
network: its only default route was through a gateway on another subnet, `ping` to the Pi got
nothing, SSH timed out, and NordVPN itself was disconnected. **The Pi was perfectly healthy
throughout** — all three sites answered `x-lanna-served-by: pi` the whole time — so this was never a
Pi fault. It was the path from this laptop to it.

**The three Pi builds are what actually change what users see**, so that is half a release, and it
was put to him rather than worked around. **His answer was the fix: *"Can we deploy over mesh
net?"*** — and it was already recorded in the repo that we can.
`docs/decisions/2026-11-07-network-review-closed.md` says Meshnet has been installed and signed in on
the Pi since 2026-11-06, and `docs/as-built-2026-11-13.md` lists *Management SSH, anywhere* over the
mesh as **IN PLACE**. The mesh host name is in the private network notes on his Desktop, where
`CLAUDE.md`'s writing rule puts values of this kind, and **all three Pi builds ran over it without a
single further problem.**

**Three things to promote out of this, which is why it is written at length:**

1. **The runbook's Pi step assumes the home network and does not say so.** A line naming the mesh as
   the alternative route is added to `docs/release-procedure.md` in this record's PR. Without it the
   next release manager re-derives this from scratch, and the first thing they will conclude from a
   timed-out SSH is that the Pi is down — which it was not.
2. **Read the served headers before believing the Pi is down.** `x-lanna-served-by: pi` on all three
   hosts settled it in one command, and it settled it the *right* way round: the box was fine.
3. **One attempt by the bare mesh number was refused once before** (recorded 2026-11-07), so use the
   mesh **host name**, not its address.

**`0375` IS THE WHOLE STORY OF THIS RELEASE'S SCHEMA HALF, AND IT DID EXACTLY WHAT IT PROMISED.**
225 flagged objects to **zero**, on production, UAT **and** test. On Supabase the `postgres` role has
`BYPASSRLS`, so a view that is not `security_invoker` and a security definer function both skip every
row-level policy; multi-tenancy needs them to obey the tenant policy. `0375` creates a Postgres role
that does not bypass RLS, gives each RLS table a permissive `definer_all` policy, and moves ownership
onto it. Two objects stay owned by `postgres` **by name, with a reason** — `login_display_name` and
`label_translations`, both of which read `auth.users`, which has RLS on and no policy and which
`postgres` cannot add one to. Those are the `2 allowed by name`.

**And it incidentally retired a number three release records could not agree on.**
`table-policy-commands` has been the subject of an unresolved discrepancy since `0.45.0` — 78 lines
there, 74 then 76 on `0.46.0`, and **80 lines / 77 `no policy`** when read today with no migration
applied between and the check's own code unchanged in `4644759ef..HEAD`. It is almost certainly three
people counting different things (total output lines vs `no policy` lines), which is why both numbers
are given here. **After `0375` the question is moot: the answer is now zero on every table**, and the
check prints one sentence instead of a list. **For the planner: the item can be closed as overtaken,
not solved.** The lesson stands and gains a clause — *count it, do not read it over*, **and say which
run and which number the figure is.**

**`role-cells` did not move, and that was the prediction.** None of the five migrations touches a
stored permission cell; `0379` and `0380` resolve through `has_permission('merch.manage')`, an
activity that already existed, so no card and no cell changed. Both card invariants stayed clean
across the applies.

**The five dry-runs were all `ok` — no repeat of the per-file-transaction trap.** `0.46.0` had `0373`
fail its dry-run for a documented reason; nothing here depends on an earlier pending file.

**Five `-- consumer:` warnings, all the safe direction** — schema landing before its readers are
live. One (`photo-store.ts`) *"does not exist in release 0.46.0"*, which is exactly right for the
retention job. `0380`'s three declared consumers produced **no** warning, which per the runbook means
those files are unchanged since the live release — the safest order of all, and a predicted warning
that does not appear is fine.

**Nothing in the five rewrites existing rows at apply time**, and that was read rather than assumed:
`0375` adds policies and changes ownership, `0377` creates a private bucket and a column, `0378` sets
two defaults to NULL (existing rows keep their value), `0379` grants and adds two policies on a table

*snapshot the table the migration writes* — was applied by reading what the files actually do, and
the table `0375` writes to is `pg_policies`/`pg_class`, which is what the tenancy lint and
`table-policy-commands` read on both sides.
