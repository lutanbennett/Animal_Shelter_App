**The public-views move is exactly one line, and it is a refusal:**

```
> ok    foundation_documents: anon SELECT is refused — HTTP 401
```

`0362`'s new table, closed to anonymous visitors. Nothing else moved.

**`table-policy-commands` moved by one line too, and it is the same table.** The added line is:

```
   foundation_documents: nobody can update (no policy)
```

**That is the design, stated in the migration's own words** (`0362`, line 80): *"No update policy and
no update grant: a wrong entry is removed and filed again, so a row never changes under the file it
names."* So `0362` creates select, insert and delete policies and deliberately no update. **It is a
reading, not a regression, and not a fault to file** — and it was checked against the migration rather
than guessed at, because "nobody can update" on a brand-new table is exactly what a real mistake would
also look like. Every other line is identical to `0.44.3`'s.

**Counting it by hand was wrong, and the script was right.** A hand count of the `no policy` lines gave
73 before the applies and read as a one-line *improvement*; counted properly it was 77/74, identical
to `0.44.3`. `0.44.3` recorded the same trap from the other direction. **Count it, do not read it
over** — and note that the before figure was taken **before** the applies, which is why the real move
is the one new table and not six migrations' worth of churn.

**`role-cells` did not move at the migration, and that was the prediction this time.** `0.44.3` got
this wrong in the other direction and recorded why: `0361`'s grant change lives in
`src/lib/permissions/catalogue.ts` and `cards.ts`, so it takes effect at the **deploy**, and stored
cells change only when a role's cards are next saved. The four edit settings it removes were held by
nobody, so no cell was stripped. The card checks are therefore re-run **after** the production deploy,
which is their proper place.

## Backups: a wrong turn worth recording, because the obvious reading was wrong

`0361` rewrites rows, so the pre-production gate asks for a fresh backup. Taking one by hand
**refused**: `BACKUP_GOOGLE_OAUTH_CLIENT_ID/SECRET/REFRESH_TOKEN` are not in
`.env.deploy.production`, and the script offered `--shared-drive-token` to borrow the app's token
instead. **That flag was not taken** — the app's token is *deliberately* not used for backups, and a
refusal's suggested remedy is not advice.

Then the evidence looked alarming and was misleading: `backup.log` in the main checkout is **0 bytes,
dated 4 October**, and no Windows scheduled task runs `backup.mjs`. Read alone, that says production
has never been backed up. **It is not true.** The Drive folder holds nightly encrypted dumps at
20:00Z — newest `lannacare-production-2026-11-11T2000Z.dump.age`, with the older ones pruned on
schedule — so backups run, from something other than this machine's task. **The gate is satisfied by
a backup about twenty hours old.**

**Worth someone's time later, not this release:** where the nightly run actually lives, and whether
the hand path on this machine should get its own token so the gate can be met on demand.

**`0361` is the one that rewrites rather than adds** — it takes four unused edit settings off the
activity list, which recomputes stored rows — so the before-pictures are of `role-cells` and
`role-cards`, the tables it actually writes. That is the `0.40.2` lesson applied rather than
re-learned.

**Counting `table-policy-commands` by hand was wrong and the script was right.** A hand count of the
`no policy` lines gave 73 and looked like a one-line improvement since `0.44.3`. Counted properly it
is **77 total / 74 `no policy`, identical to `0.44.3`**. The records count total output lines; this is
the same trap `0.44.3` recorded from the other direction, and the remedy is the same — count it, do
not read it over.

**Audit: clean by the register.** `npm run audit:prod` exits 1 with 5 vulnerabilities (1 moderate,
4 high); `npm run audit:register`, which is what CI runs and what this step is for, exits **0** —
one high advisory, `GHSA-5j98-mcp5-4vw2` (`glob`), dated in `docs/advisory-register.json` and still
unreachable here. The cut bumps `package.json`, so CI's `audit` ran for real rather than `skipped`.

**Production dry-run: all seven `ok`.** The eighteen `-- consumer:` warnings are the safe direction
— schema landing before its readers are live. `0364`'s consumer produced no warning, which means
`src/app/management/translations/page.tsx` is unchanged since `0.44.3` and its reader was already

## The DNS fault that cost two presses last release is gone — measured, not assumed

`0.44.3`'s headline was a 12.1 s cold lookup of `api.cloudflare.com` against a 10 s deadline, caused
by a NordLynx adapter advertising Nord's resolvers with NordVPN not running. **Before the command was
handed over the lookup was measured again: 0.1 s**, and `Get-DnsClientServerAddress` lists only the
router (`192.168.1.1`, `192.168.68.1`) — no NordLynx, no `103.86.96.100`.

**So the `Resolve-DnsName` prefix was deliberately NOT handed over**, and both Worker deploys ran
first time. Handing over a workaround for a fault you have not measured is cargo cult: the diagnosis
is worth keeping, the habit is not.
