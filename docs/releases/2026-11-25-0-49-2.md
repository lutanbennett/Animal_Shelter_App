## The headline of this release is not what shipped. It is what happened during the deploy.

**`lannacareforanimals.org` was publicly reachable for roughly the length of the remaining release
steps, and the release manager caused it while following the recorded order exactly.** Everything
else below is ordinary, and that is the point: the fault was in the order, not in the work.

### What the recorded order said, and why it was wrong

`#1879` changed production's `PUBLIC_SITE` in `wrangler.jsonc` from `"locked"` to `"open"`, lifting
the deployment-wide floor so that each shelter's own `public_site` decides what a signed-out visitor
sees (`publicSiteStateFor` serves the **more closed** of the two).

`docs/decisions/2026-11-25-website-lock-truth.md` set out four steps: Lutan sets Lanna's website to
`locked` on the console, the deployer reads it back, **then** the production Worker deploys, then it
is checked from outside. The cut plan, the cut commit message and PR #1890's body all repeated that
order, and all three said the floor lifts "from the moment the production Worker deploys".

**It does not.** `scripts/lib/runtime-config.mjs` declares `PUBLIC_SITE` as `where: "pi"`,
`source: "wrangler"`, and `scripts/pi/write-env.mjs` copies it out of `wrangler.jsonc` into the Pi's
own `.env.production.local` at **build** time — in its own words, "so the Pi renders what the Worker
would". Every public page is served by the Pi (`x-lanna-served-by: pi` on every response). So the
floor lifted at **the production Pi build**, which is the deployer's step and comes *before* Lutan's
deploy, not after it.

### What was measured

Before the production Pi build, `lannacareforanimals.org/` was the construction page: **200,
24,462 bytes**, construction wording present. After it:

| URL | Status | Bytes |
| --- | --- | --- |
| `/` | 200 | 78,877 |
| `/adopt` | 200 | 86,198 |
| `/our-work` | 200 | 68,069 |
| `/donate` | 200 | 69,570 |

`CF-Cache-Status: DYNAMIC` on every one, so this was live from the Pi and not a stale edge copy.
Real content throughout — "Every street dog and cat deserves a second chance", "Our impact", "Thank
you to our Shelter Friends", and resident pages including Wua. **`robots.txt` served `Allow: /`
with a sitemap**, so crawlers were being invited in. `cooperjaidee.org/` was unaffected and kept
307ing, because the product site has its own switch (`PLATFORM_SEARCH`).

### The second finding, which the first one uncovered

The site could only be public if **Lanna's own `public_site` was still `open`**, because the served
state is the more closed of the two values. `0426` had set it to `open`; the console change Lutan
made on 2026-11-25 had not taken effect. Nobody would have discovered that until go-live if the
floor had lifted at the step everyone believed.

### How it was closed

Lutan set Lanna's website to `locked` on the Platform console → Shelters → Lanna → Website tab on
2026-11-26, and the site closed within a minute:

| URL | Status | Bytes |
| --- | --- | --- |
| `/` | 200 | 24,468 — construction wording present |
| `/adopt` | 307 → `/login?next=%2Fadopt` | 20 |
| `/our-work` | 307 → `/login?next=%2Four-work` | 23 |
| `/donate` | 307 → `/login?next=%2Fdonate` | 21 |

`robots.txt` back to `Disallow: /`, `x-robots-tag: noindex, nofollow`, `x-lanna-cache: BYPASS`,
`x-lanna-served-by: pi`. **`0.49.2` stayed deployed throughout** — `/api/version` still reads
`0.49.2 @ 5344c037a`. No rollback was needed and none was performed.

**One honest limit on that confirmation.** `isPublicSiteLocked` treats `locked` and `off`
identically for a signed-out visitor, so **from outside the two cannot be distinguished**. What is
proved is that Lanna's own value is now one of them, and Lutan pressed Locked. No script in the repo
reads `shelters.public_site` on production; the only read-back available is the console itself.

### What must change, and it is not this release's files

**`docs/decisions/2026-11-25-website-lock-truth.md`'s step 3 names the wrong step.** The read-back
has to be in front of **the production Pi build**, not the production Worker deploy. Filed on the
backlog rather than patched here, because the order in that decision file is the thing to correct and
a release record is not the place to do it. PR #1890 carries a correction comment stating the same.

**A second lesson, cheaper and more general:** a configuration change was reviewed for *what* it did
and not for *which step applies it*. `runtime-config.mjs` already answers that question for every
variable in one word — `where` — and nobody read it. A `wrangler.jsonc` change with `where: "pi"`
takes effect at a Pi build; one with `where: "worker"` takes effect at a Worker deploy. That one
word should be read on any release that changes that file.

## No email, proved three ways

A minor release's silence is only proved by both halves of the cut's own check, and then
independently by the deploys:

```
ok   mail ABSENCE: majorReleasesSince(previous) is empty  [[]]
ok   control: from further back, an older major release is still found
```

Without the control, an empty answer and a broken query look the same. Then:

- test: `no major release new to test (was 0.49.1), so no email`
- UAT: `no major release new to uat (was 0.49.1), so no email`

**UAT's is the one that counts.** It has a live `RELEASE_MAIL` binding
(`RELEASE_MAIL_ENV: "UAT"`, `releases@lannacare.org`) and its database holds production's real
people, so its silence is the strongest of the three. `--no-mail` was passed anyway.

character-identical.

**2. `| tail -4` again.** `node scripts/guarded-install.mjs 2>&1 | tail -4` showed npm warnings and
was read as success. The install had not finished; `wrangler` was missing and `deploy.mjs` died with

Redirect to a file and read the file.

## GitHub was partly down during this release

`gh pr create` failed once with a GraphQL error; `gh pr merge` failed twice through GraphQL and once
through REST (`unexpected end of JSON input`). `githubstatus.com` confirmed a **Partial System
Outage with Pull Requests in major outage**. The third merge attempt succeeded
(`mergedAt 2026-11-25T16:20:31Z`). **Nothing was lost and none of it was a refusal** — worth
recording because a `gh` failure that is not a refusal looks exactly like one, and `CLAUDE.md`'s rule
is to stop and hand a *refusal* to Lutan.

Mesh SSH to the Pi also flapped, with about ten timeouts after the first success. The `setsid nohup`
pattern meant every build survived the dropped session, and `deploy-pi.sh`'s machine-wide
`flock -n` **refuses rather than waits**, so stacked concurrent builds were impossible by
construction — worth knowing before fearing them, as this release did.

production Pi rebuild**, which is the same lesson as above read backwards.
