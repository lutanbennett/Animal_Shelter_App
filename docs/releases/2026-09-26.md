## The migration count was wrong, and the plan is what caught it

The cut PR's apply plan stated that **five** migrations (`0087`–`0091`) were
pending on production, reasoning from production having been at `0086` after
`0.5.0`. That reasoning was wrong: the schema streams had applied their own
migrations to production as they merged during the day.

`--drift production`, run by Lutan against `origin/main 8cc4880`, answered:

```
91 file(s), 90 applied row(s).
  On origin/main, not applied here: 1
    0091_record_stocktake_staff.sql
  Applied here, no file on origin/main: 0
Drift: production and origin/main disagree.
```

**One file, not five.** The plan said "confirm production is at `0086` before
assuming five are pending", and that instruction is the only reason the wrong
number did no harm. Worth keeping as the pattern: a release manager reasoning
about production's schema from the last release's record is reasoning from a
snapshot that other streams have been writing to all day. The measurement is
cheap; the assumption is what costs.

`0091` is a single `create or replace function`, re-runnable, with nothing else
pending for it to depend on — so the two-file dry-run artefact could not apply,
and a clean dry-run was the expectation.

### What `0091` changes, since it is a privilege change

It widens `record_stocktake` from admin and management to also admit staff and
volunteers, which is what note 10 promises. To do that it becomes
`security definer`, so RLS no longer filters it. Read rather than waved through:
the body writes only `stock_on_hand`, the role check at the top is now the whole
access rule and explicitly refuses vets, `public_viewer`, anon and archived or
role-less logins, and `set search_path = public` is pinned — that pin is what
keeps a definer function safe from a caller's search path. Grants unchanged, anon
and public revoked.

**Deploying without it would not have broken anything**, which is worth recording
because the cut PR braced for worse: Stocktake would have worked for admin and
management and refused staff and volunteers. A degradation against the release
note, not a broken page.

## Findings for next time

- **A release is not finished when it deploys.** `0.6.0` was live and verified
  within minutes, and still had no record a day later. The deploy is the
  reversible part; the record is the part that cannot be reconstructed after the
  terminal scrolls. Write it before moving on, even if it has to say "not
  captured" three times.
- **Do not reason about production's schema from the last release's record.**
  The cut PR said five migrations were pending and one was. Other streams apply
  their own migrations as they merge, so the last record is a snapshot with a
  day of writes on top of it. `--drift production` is cheap and it is the only
  answer.
- **The sign-in lock hides the thing most worth checking.** Every public page was
  redesigned in this release and none of them can be seen signed out, by design.
  Until go-live, verifying public-facing work on production requires a signed-in
  session or the `public_viewer` account added in `0.5.0` — which is exactly what
  that account was built for, and it has not yet been used for it.

`SITE_CONTENT_COLUMNS` (`src/lib/site/content.ts:40`) gained `messenger_url`,
`whatsapp_number` and `x_url` in this release. That is the loader every public

the site down. Same mechanism as `0080` in `0.4.0`.

The apply plan named it as the one ordering mistake that breaks the site, and it
went on first. **The plan also deliberately refused to say how many migrations
were pending**, because the `0.6.0` cut asserted five and the answer was one. This

### A logging artefact that looked like a failed deploy, and was not

Worth recording in full, because the wrong conclusion was reached first and acted
on.

`deploy.log` ends at `Total Upload: …` on **every** run: no
`Uploaded lanna-animal-care`, no `Current Version ID`, no custom-domain lines.
On the 19:16 attempt this was read as the deploy having "died between uploading
the assets and publishing the Worker", and a re-run was advised.

That diagnosis was wrong. The same truncation appears on runs that demonstrably
succeeded — `0.6.1` is live — so the missing tail is **not** a missing deploy.
The cause is almost certainly the Windows PowerShell 5.1 `2>&1` artefact: wrangler
writes its closing lines to stderr, and redirecting a native command's stderr in
5.1 wraps each line in an ErrorRecord. That is also where the
`FullyQualifiedErrorId : NativeCommandError` near the top of the log came from,
which had reinforced the false reading.

Two consequences:

- **`> deploy.log` truncates on every run**, so a second deploy destroys the
  first one's evidence. That is why `strip-baked-env` appeared to be missing
  again: the successful run's output had been overwritten by a redundant re-run
  started a minute later. `>>` would append.
- **The live version endpoint is the authority on whether a deploy landed**, not
  the log tail. It is `no-store`, so it cannot answer stale.
