`0.43.3` was cut this morning: two notes, no migration, one touch. **This one is eight notes and eight
migrations** — the whole of batch 7 plus the reels library, the three-state photo approval, the
deceased-record widening, vet costs in the Expenses report, a new project-folders card and a health endpoint
for Home Assistant.

**`0.43.2` taught that a request worded as a small release can be anything.** Here the same command came

### The deferred-note review, which was the work of this cut

`check-deferred-notes.mjs` listed **nine** plans whose release-notes line was answered `n/a`. On four the
reason was *"needs `03xx` applied to production"* — and this release applies them, so those steps close
here. `docs/decisions/2026-10-11-release-note-truth-rule.md` puts the note in the PR that closes the step,
and `docs/release-procedure.md` says so in terms: *"For each one decide whether this release closes its
step; if so add the note to `unreleased` first."*

**The five that owed nothing, said plainly rather than skimmed:** a `next dev`-only switch, two planning
handovers, the last release's own record, and `resident-record-guards-schema` — the same `0320` step,
already covered by the deceased-record note.

**Two departures from the drafted wording, both deliberate, and both the same principle:**

- **The *Private only* note was corrected, not carried.** It said *"(This shows once the shelter has the
  Private only answer, which is not live yet.)"* — true when written, and **false the moment this release
  publishes it**, because `0318` is the migration that makes the answer live. That is `#518`'s fault
  pointing the other way: a note telling users a feature is *not* live on the day it goes live. The
  parenthetical was deleted and the rest is character-identical.
- **The reels note does not promise the `#` picker.** The draft said *"type # and an animal's name to tag
  them"*. `docs/decisions/2026-11-06-reels-follow-ups.md` §4 establishes the picker asks `resident.record`
  at Read, which `meme_library` does not carry — so a holder of the reels card alone gets a plain
  description box. The note says that, and adds that a resident's page now lists their reels.

**`--base` was needed, and this is the case it exists for.** Because the cut wrote notes, `origin/main` no
longer held what the new entry should be compared against; run without it, **exactly** the two note
assertions fail, which is the script working rather than a problem. The base was `origin/main`'s file with
the cut's two edits replayed by a script, so the comparison was against the pre-cut tree and not against
the cut itself.

### The UAT refusal is a stream landing underneath a release, not a fault

`node scripts/deploy.mjs --env uat` refused, and **the refusal was right**. `.env.deploy.uat` held
`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY=` with an **empty value**, which is layered *over* `.env.local` and so
shadowed the working key rather than falling through to it.

**The cause was established rather than guessed, and it is worth the paragraph.** The file no longer points
at the dev project: it points at `fsjagxmxjosauwmxwype`, a **third Supabase project in a second Supabase
account**, created by Lutan for `claude/uat-own-database`. `--status --env uat` then failed with *"Missing
required permission(s): database_read"*, which is that stream's own outstanding token step. **#1338 merged
to `main` while this release was deploying** — so the release ran its UAT deploy in the window between the
stream's half-filled config being written to the machine and its code reaching `main`.

`docs/decisions/2026-11-06-uat-own-database.md` settles what should happen, and it is exactly what was
done: *"`.env.deploy.uat` (gitignored, **Lutan fills it in**)"*, and *"Until UAT is redeployed with its own
values, `lannacare.org` still runs the previous build against dev."* **So nothing in `.env.deploy.uat` was
touched by this release.**

**The tool's suggested remedy was read and not taken,** per `CLAUDE.md`: the error says to make a new key
with `actions-key.mjs --generate`. Generating one would have given UAT a key differing from the one it ran
on yesterday and written a secret into a file whose owner is Lutan, to fix a symptom of somebody else's
half-finished migration. **The refusal knew less about the situation than one `grep` could establish.**

## The touches this release cost

**The target is two. This one cost three, and the third was avoidable.**

1. **The email answer** — given unprompted in the request itself, so it cost nothing.
2. **The production migration apply** — *should not have been his*, and is Defect 1.
3. **The production Worker deploy** — his one standing job.

**A fourth was avoided by checking rather than assuming.** He said *"Running my deploy now"* while this
session's test Worker build was still bundling in the same checkout; two builds in one worktree destroy
each other, which is the `0.40.3` failure. His terminal was read, the build was seen to be mid-flight, and
he was asked to hold for a few minutes. **That is the third release running in which reading the live state
instead of accepting "it's done" has prevented something.** The reverse case also appeared: he answered
*"Yes, carry on"* to a question about merging the PR, and a session that read it as *"the migrations are
in"* would have deployed code against a database eight migrations behind. `--status` said `8 pending`, so
it did not.
