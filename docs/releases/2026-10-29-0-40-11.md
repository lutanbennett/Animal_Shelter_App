checkable terms and a decision file, and **fails on anything else**. `audit` was **green** on this

still exits 1, which is correct: the release step and the daily `advisories.yml` read the raw
advisory, and that is the check a person acts on. The backlog item is ticked.

## The narrowing this release carried, and how it was settled

`0280` takes `reports.cashflow` **off** the `dashboard` card. The `0257` triggers recompute every
role's `role_permissions` whenever `card_grants` changes, so a narrowing there can quietly remove a
cell from a live role — exactly the case the runbook says to photograph first.

**It was settled by reading production rather than by trusting the migration's own header:**
`check-production.mjs role-cards` before the apply showed **no role holds the `dashboard` card**. So
the narrowing removed a grant nobody had, and the predicted after-picture was "all six roles
unchanged". That is what happened.

## The rule that had cost two releases, and what following it looked like

`0.40.9` and `0.40.10` each cost Lutan an avoidable round-trip, and he named the pattern. The rule
written into the runbook afterwards: **one command at a time; nothing of mine running against shared
state while a command of his is in flight; the next command only after the previous one reports.**

**It held, and it cost nothing.** The migration command was handed over alone, with the deploy
described in words only. The deploy command was handed over alone, after the apply had been
**verified** rather than taken on trust. **No test Worker deploy was started while his production
deploy was outstanding** — the exact collision that wasted ten minutes on `0.40.9`.

**What genuinely parallelises was used fully**, so the sequencing cost nothing: both Pi builds ran on
the Pi while his command was outstanding, and the cache purge and the icon sync — neither of which
builds anything in this checkout — ran in the same window. By the time his deploy reported, the only
work left was the test Worker deploy and the paperwork.
