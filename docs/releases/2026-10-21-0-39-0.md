### What shipped

**Nine notes, and every live role sees at least seven** — admin 9, every other role
7. Measured from the tags rather than assumed.

- **Diets are now recipes** — ingredients with per-size amounts, a portion multiplier on a resident's diet form in place of a daily amount, and Purchasing, the forecast, Cashflow and stock usage all reading ingredients
- **A Donors list** under Management → Donations → Donors, kept apart from Contacts, with every gift and the total per donor
- **Role home screens are set by cards alone**, and an Admin can put a role's cards into **groups** — one tile that opens a page of cards, so a crowded phone home becomes a few doorways. Both of these notes are tagged `admin`
- **Home screen tiles** for My tasks, Operations and Management
- **Two new assistant sentences** — record a vaccination by typing it, and bring a resident back from foster or adoption
- **Cancelled clinic visits** no longer counted in a resident's total, in their own folded section, and in the archive PDF

### Why major

Put to Lutan with two other questions in one opening round. The case: this release
**changes things people already use** rather than adding to them — a resident's diet
form loses its daily amount for a portion multiplier, food ordering now works from
ingredients, and the Home screen panel in Settings is gone. The minor case was that
`0.38.0` had mailed admins two days before. **He chose major**, with the
recommendation.

**The check, the right way up for a major:** `majorReleasesSince("0.38.2")` returns
`["0.39.0"]` — the mail asserted to be *going out*, by importing the module rather
than reading the `major:` flag — and asked from `0.38.1` as well, so a function
that always returned `[]` could not have passed either way.

## The rollback is not clean this release, and it was written out rather than ticked

Six of the seven migrations are additive. **`0243_dead_schema_drop.sql` is not**: it
drops `diet_types.daily_qty_small/_medium/_large`, `diet_types.is_standard`,
`resident_diets.diet_type_id` and `resident_diets.daily_quantity`, plus
`role_home_tiles` and five functions and triggers.

So the usual rollback sentence — a Pi rebuild of the previous release — **is false
here.** It would restore a `0.38.2` build whose diet-ingredient path writes to
columns that no longer exist. The honest position: **the build rolls back, the
schema does not.** The way out is a restore, which needs the administrator's private
key and is not a step any session can take.

**So a fresh production backup was taken rather than relying on the 03:00 nightly
one** — `lannacare-production-2026-10-21T1406Z.dump.age`, 1.32 MB, encrypted for one
recipient, in Drive and kept at `~/backups/lannacare` (16 kept). Taken **on the Pi
with the cron job's own command**, because `backup.mjs --env production` refuses on
the deploy machine: `BACKUP_GOOGLE_OAUTH_*` is deliberately absent from
`.env.deploy.production` and the script says exactly that. **That refusal is the
design working, not a fault** — worth recording, because at first glance it reads
like a broken backup, and the next release manager meeting a destructive migration
will go looking for this.

**One consequence nobody can design away, and it is stated rather than hidden:**
both deploy guards refuse a build whose database lacks a migration that is on
`main`, so the apply must precede the deploy. For the roughly ten minutes between
the apply and the production Worker finishing, **`0.38.2` was live against a schema
that no longer had those columns.** The only path that would have failed is an admin
adding a diet ingredient in that window. Nobody did, and the Pi — which is what
actually serves production — was on `0.39.0` well before the Worker. But it is a
real window, it recurs on any drop, and it is the price of the guard rather than a
mistake.

## The icon sync is a diff now, and Lutan's question is what caused that

`0.38.2` lost its icon sync to a Drive 403 `userRateLimitExceeded` after uploading
40 of 344 files. I filed that as a missing-backoff bug. **Lutan asked whether the
next release would upload only the new cards**, and reading the loop to answer him
established that it would not — it re-uploaded all 344 unconditionally, with no
comparison against what was already in Drive. The item was rewritten to lead with
*upload only what changed*.

**That shipped in this release as #810, and this release's run proves it:**

```
43 cards, 344 images drawn.
Done: 344 images checked against Drive → Home screen icons: 344 unchanged, 0 updated, 0 created.
```

**Zero Drive writes where there were 344**, exit 0, no 403, no retry needed. So the
403 is not merely survivable now — its cause is gone, and the ~688 requests a
release are gone with it. Trimming the eight variants per card is the remaining
half and is still his call.

The reason this earns space in a record rather than a changelog line: **the
diagnosis came from his question, not from my investigation.** I had the failure in
front of me, retried it successfully, and filed an item aimed at the wrong cause. A
green retry is a weak reason to stop looking, and that is the second release running
where that sentence would have saved something.

## The per-file dry-run trap fired twice, and the script explained itself

`--dry-run` against production exited **0** overall and reported **two files
FAILED**: `0242` on `relation "diets" does not exist` and `0243` on `cannot drop
column daily_qty_small … view special_diet_list depends on it`. Both are the runner's
per-file `begin … rollback` hiding what the previous file adds — `0239` creates
`diets`, and `0242` restates `special_diet_list` without the legacy columns, which is
what lets `0243` drop them.

**The correct action on a red dry-run here is to apply, and the script now says so
itself** rather than leaving the reader to recognise the trap:
`NOT a fault in … A real apply commits each file first, so this one is expected to
apply.` Both applied cleanly, `ok` each. **Running tally: three times fired, ten
not.**
