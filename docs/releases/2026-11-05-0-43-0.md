## THE FINDING: `main` moved under the deploy, and doing nothing was correct

**The Worker built from `fda3c508`; both Pi clones are pinned at the release commit `3227a19e`.** #1286 (the planner preflight) merged itself on green between the cut's merge and the deploy — which is exactly what *every PR merges on green* makes normal, and is not a fault of anyone's.

**The code-identity check, in its authoritative allow-list form, is EMPTY:**

```
git diff --name-only 3227a19e..fda3c508 | grep -E '^(src/|worker/|public/|next\.config\.|open-next\.config\.|wrangler\.jsonc$|package(-lock)?\.json$|postcss\.config\.|tsconfig[^/]*\.json$|scripts/pi/|scripts/lib/[^/]+$|scripts/(deploy|apply-migrations|actions-key)\.mjs$)'
```

Nothing. **So the served application code is identical and the release is sound however many SHAs appear.** The allow-list's own failure mode was closed by reading the other side, as `docs/decisions/2026-11-04-release-check-false-positives.md` requires: the three files that differ are `.claude/skills/plan-day/SKILL.md`, `docs/test-plans/planner-preflight.md` and `scripts/check-planner-preflight.mjs`. **None is imported by the build or run during a deploy** — the new script is a planner check, not in `scripts/pi/`, not in `scripts/lib/`, and not one of the three deploy scripts — so nothing needs adding to the list.

**Nothing was rebuilt, and that is the whole point.** The trap is explicit that `main` moving does not license chasing a SHA: a past release moved the Pis to match, and left Cloudflare holding the intermediate build's HTML. **`0.42.0`'s allow-list fix earned its keep on the very next release:** under the old `grep -vE '^(docs/|\.claude/)'` form, `scripts/check-planner-preflight.mjs` and the test plan would both have printed, and the instruction *any line means stop* would have halted a sound release for the second release running.
