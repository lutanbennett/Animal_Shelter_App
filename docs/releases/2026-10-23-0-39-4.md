### What shipped

**Three notes.** Notes 1 and 3 are role-tagged by their own feature PRs; note 2 is a
plain string, so every live signed-in role sees it.

- **Operations → Feeding list**, a new page adding up each zone's ingredients per meal
- **Diets written as one serving**, with an editable *Servings by size* row per diet
- **A Medical-records-card login can open a resident's whole page**

### Why minor — and the recommendation was major

**The advice was major and Lutan chose minor**, breaking two releases of advice and
answer agreeing. The case for major: the diets change rewrites how every diet is
written in Settings → Diets, which is more than cosmetic.

**What changed his answer was a correction, and that is the point worth keeping.**
The first question put to him said major would "mail the admins". That overstates the
lever — `release-procedure.md` records that a major release today mails **one
person**, the shelter's own address not being on the production admin list — and the
runbook says to state it plainly whenever the call comes up. Told, he moved from
major to minor.

**So the standing instruction is not a courtesy sentence; it demonstrably changes the
outcome.** A session that skips it is not saving a line, it is getting a different
answer to a question that cannot be taken back.

**The check, both ways**: `majorReleasesSince("0.39.3")` is `[]`, so no mail; and
`majorReleasesSince("0.38.2")` still returns `0.39.0`, so a function that always
returned `[]` could not have passed both.

## The headline: this release can quietly feed the dogs less

**This is the finding. Everything else in this record is smaller.**

`0250` (diets, one amount per serving) is **additive in the database**: it adds
columns, fills the new `qty_per_serving` only `where qty_per_serving is null`, and
explicitly keeps `qty_small/medium/large` — the column comment says *"Replaces
qty_small/medium/large, which stay until the app stops reading them"*. Nothing is
dropped, rewritten or back-filled over, so the pre-drop backup gate does not engage.

**And none of that makes it safe.** `0.39.4`'s app computes a dog's food as
`qty_per_serving × servings(size)`, and the back-fill takes the **Small** amount as
one serving. A diet entered as **1 : 2 : 3** therefore feeds less:

| Diet / ingredient | small | medium was | medium now | large was | large now |
|---|---|---|---|---|---|
| Diabetic / Green beans | 30 | 60 | **45** | 90 | **60** |
| Diabetic / Oats | 20 | 40 | **30** | 60 | **40** |
| Standard Kibble + Chicken / Turkey mince | 50 | 100 | **75** | 150 | **100** |

**On dev, 8 of 10 ingredient lines are out of proportion**, so this is the normal
shape of the data, not one odd row. Nothing on screen announces it; the kitchen's
feeding list simply shows smaller numbers.

**`0250`'s author anticipated exactly this.** The file ends with a `do $report$`
block raising one NOTICE per out-of-proportion line, a count, and the sentence
*"Each is Lutan's call."*

**That report reaches nobody.** `apply-migrations.mjs` talks to the Supabase
Management API, which does not return `raise notice` output, so the production apply
printed `applying 0250 … ok` and **not one of its findings**. The one safeguard built
for this risk was mute at the exact moment it mattered. Filed on the `backlog` branch
with the general form: **any migration relying on a NOTICE to tell a person something
is invisible through this path.** If you need to tell someone, write a check.

**What was NOT established, and is recorded as not established:** which *production*
diets are affected. All five diets check scripts are hard-locked to the dev project
(`refusing: <ref> is not the dev project`); that guard was left alone rather than
worked around, so production's own diet rows were never read. **Do not assume dev's
8-of-10 shape is production's.**

**Lutan's decision, taken before any deploy**: given the dev figures and the per-diet
remedy — Settings → Diets → *Servings by size* → **1 / 2 / 3** restores the old
amounts exactly — he answered *"deploy now, I will fix diets after"*. Accepted, filed
as a FOR LUTAN backlog item, and the cut plan's `Result` is **pass with accepted
defects** rather than `pass`.

**Why this was worth stopping for rather than absorbing:** his standing rule is that
unsigned test plans ship as recorded gaps, but a change that **breaks quietly** holds
the release. This is the second kind. It was found by reading a migration that every
gate had already passed — `typecheck`, `lint`, `test`, `build`, ten CI checks and a
clean dry-run all said yes.

## The handover's first instruction could not be carried out

`0.39.3`'s handover opened with START HERE: deploy the production Worker at
`0.39.3`, then run the calendar back-fill, **before** cutting anything. **Following
it literally was impossible, and following it loosely would have shipped a round of
unreleased feature work to production.**

Three reasons, each fatal alone:

1. **`main` had moved far past the three doc commits the handover describes** — 11 PRs of work, 29 files under `src/`, two migrations
2. **`deploy.mjs` refuses while `unreleased` has lines in it**, and it had three. The handed-over command would have stopped before building
3. **Both migrations were pending on production**, so a Worker built from `main` would have read schema the database lacked

`deploy.mjs` takes **no `--ref`**, so there was no supported way to build the Worker
at `c0bdf272` at all. **The catch-up was folded into this release**, which is the
better outcome: one SHA, all builds in step, the Worker finally current.

**The lesson is the handover's own, turned on itself.** It says *"check the diff
rather than assuming cosmetic"* about `main` moving mid-release. The same applies to
a handover read the next morning: **its facts have a shelf life of hours, and the
first thing to do with START HERE is re-measure it.** Both the record and the
handover called the Worker gap "one command"; by morning it was no command at all.

## `npm ci` was needed TWICE, and paperwork rule 2 needs a caveat

Rule 2 reuses a free leftover worktree to avoid a four-minute `npm ci`. **It saved
nothing.** The leftover (`Animal_Shelter_vet-visit-booking-polish`, 71 commits
behind) had `next` **16.3.8** installed against a `package.json` saying **16.4.2**,
because the range contains the Next bump (#869) — the `0.28.0` asymmetry exactly, in
the worktree instead of the main checkout.

**Caught by the `0.28.0` tell**, `require('next/package.json').version` against
`package.json`, before any gate ran. Both checkouts then read 16.4.2, and the first
Worker build printed `Next.js version : 16.4.2`.

**The caveat:** reuse saves the install only when **no dependency changed inside the
release range**. When one did, reuse costs the same `npm ci` *plus* the chance of
building against the wrong framework — and here **no guard would have caught it**:
the gates do not read `node_modules`, and unlike `0.28.0` no deploy guard inspects a
worktree.

## A new way to lose the production deploy log: PowerShell's `tee` writes UTF-16

**The runbook tells us to hand over the deploy with `| tee`, and that is still
right** — the lines worth reading print before a long build and otherwise scroll out
of the buffer. But `tee` in PowerShell 5.1 writes **UTF-16LE**, so every plain
`grep` of the resulting log returns nothing:

```
grep -aE "Supabase project|strip-baked-env|Server Actions key" .local/deploy-0.39.4.log
   → no output, on a 30 KB log that plainly contains all three
```

**That is a silent zero, which is the dangerous kind** — indistinguishable from "the
deploy did not print those lines", and this record's own ancestor nearly concluded
something similar from an empty `git show`. Read it with `Get-Content … |
Select-String` in PowerShell instead, or decode it first.

**Related and already known:** the `→` in `deploy: production → Supabase project`
does not survive the encoding either (it renders `ΓåÆ`), which is why the runbook
says to grep the **project ref** rather than the arrow. **Now it is clear that is not
a cosmetic quirk but a consequence of the same encoding.** The test deploy, which
Claude ran with a plain `>` redirect rather than `tee`, greps fine in Bash — so the
two logs of one release need two different tools to read.
