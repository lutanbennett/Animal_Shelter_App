### The release had a prerequisite, not just a checklist

#312 makes **both** deploy paths refuse to build until
`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` is set, and at cut time it was in none of the
four values files it needs (two environments × two machines). Next otherwise
generates a random key per build and uses it as the salt for every Server Action
id, so a form rendered by the Pi and submitted to the Worker answers
`500 Failed to find Server Action` — which, since `0.15.0` made the Worker serve
writes on a 530, is an ordinary event rather than a curiosity.

Claude attempted to generate and install the keys and was **refused by the
auto-mode classifier as a secret-store write**. That is the correct outcome and
was not worked around; Lutan installed both keys, and the verification was done

### How the procedure held up, first time out

Written yesterday, used today. What it changed, concretely:

- **Major-versus-minor was asked before the cut** — the question `0.15.0` skipped.
- **Both Pi builds were Claude's and ran without a handover**, the production one
  in parallel with the test Worker deploy rather than after a wait.
- **Step 0 caught a prerequisite** rather than a surprise: reading the PRs' plans
  before cutting is what surfaced #312's missing key while there was still time
  to ask for it.
- **The commands handed to Lutan were given in forms that work** — absolute paths
  after one failed from `C:\WINDOWS\system32`, which was corrected in the same
  exchange rather than costing a round trip each time.

What it did not prevent: a gates run killed with the session and quoted from a
partial log would have been easy to accept; it was re-run instead. Worth adding
to the traps if it happens twice.

### What is in it

Seven notes, mailed in a chosen order rather than merge order, leading with the
security fix exactly as `0.14.0` led with the forced sign-out:

1. **Changing your password now asks for your current password first**, and signs
   you out everywhere else. Before, anyone holding your unlocked phone could set
   a new password without knowing the old one and take over the account (#322).
2. New **Medication list** under Management: who needs medicine today, enclosure
   by enclosure in walking order, with photos of the animal and of each box
   (#325) — `admin, management`.
3. **Staff and managers can record a blood test.** The form was offered and then
   refused on save; it now saves (#319) — `admin, management, staff`.
4. **Maintenance jobs moved on by tap** on a phone, and logging a job as short
   steps (#324).
5. **Pages fit a phone screen** instead of sliding sideways, across resident,
   enclosure, vet, contact, delivery and booking pages (#320).
6. **Scan a chip finds the animal** — it previously answered "0 residents" for a
   chip just recorded (#318).
7. **Midnight–7am date refusals fixed**: logging an immunization, blood test or
   procedure dated today, and moving a resident on the day they arrived (#318).

`major: true`, so every admin was mailed.

### Major, asked before the cut

Lutan's call in chat, with the security fix named as the reason to mail. That it
behaved as a major was checked at each stage rather than assumed:
`majorReleasesSince("0.15.1")` returned `["0.16.0"]` at cut time; the test deploy

### The cut needed a different check than the last two

Five of the seven notes are **bare strings** and two are the object form with
roles. The comparison used for `0.15.0` and `0.15.1` keyed on `text:` lines —
correct then, because every note had the object form — and here it would have
compared two of seven and reported success.

Both registers were imported as modules instead (the pre-cut one straight from
`origin/main`) and compared through `noteText`, with role tags matched **by text
rather than position**, since the order deliberately changed:

```
pre-cut notes on origin/main: 7 - forms: object,string,string,string,object,string,string
in 0.16.0: 7 - forms: string,object,object,string,string,string,string
carried across unchanged: 7 of 7
text lost: 0 text invented: 0
role tags changed: 0
notes rendering badly: 0
```

Worth keeping as a lesson about check design: a verification keyed on one shape
of the data silently passes when the data takes another shape, and prints the
same reassuring number either way.

### The verification trap closed itself, and had been closed for two releases

`0.15.0` and `0.15.1` were both verified with `/api/releases/current`, which the
Worker answers from its own bundle and which therefore reports the Worker's
version whatever the Pi is serving. On `0.15.0` that produced forty minutes of
test being wrong while two signals said otherwise.

**`/api/version` answers from the app itself and has done since `0.14.0`** — PR
#290, `claude/version-endpoint-from-origin`, built for exactly this. It existed
through both releases that were checked the wrong way, and through the writing of
the procedure that named the trap without naming the remedy. The difference, on
the same host, moments apart:

```
/api/version            x-lanna-served-by: pi       {"version":"0.16.0","sha":"4a626930869db06d482c747a29fa257f4a823d63"}
/api/releases/current   x-lanna-served-by: worker   {"version":"0.16.0"}
```

The sha matches `main`'s HEAD exactly, and test returns the identical object —
which is what "production and test shipped the same commit" now means here,
rather than two version strings agreeing. `docs/release-procedure.md` is updated
in the same PR as this record.

### Three `Failed to copy` errors in the OpenNext bundle, and why they are not a defect

The production build printed:

```
ERROR Failed to copy C:\Development\Animal_Shelter_App\node_modules\age-encryption
ERROR Failed to copy C:\Development\Animal_Shelter_App\node_modules\color-string
ERROR Failed to copy C:\Development\Animal_Shelter_App\node_modules\data-uri-to-buffer
```

They are logged as `ERROR` and the build then completed and deployed, which is
exactly the shape of thing that gets ignored. Checked rather than assumed:
`age-encryption` is imported only by `scripts/lib/backup-crypto.mjs` and
`scripts/check-backup-encryption.mjs` — **nothing under `worker/` or `src/`** —
so it is not needed in the Worker bundle, and backups run from `scripts/`, not
from the Worker. The other two are transitive. Consistent with the known Windows
junction/symlink behaviour that `scripts/win-junction-symlinks.cjs` exists for.

Not established: whether these errors are new in this release. Nobody captured
the equivalent lines for `0.15.x`, so "they have always been there" would be a
guess.
