first time this sequence has exercised it.

### The release had a prerequisite, not just a checklist

#312 makes **both** deploy paths refuse to build until
`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` is set, and at cut time it was in none of the
four values files it needs (two environments × two machines). Next otherwise
generates a random key per build and uses it as the salt for every Server Action
id, so a form rendered by the Pi and submitted to the Worker answers
`500 Failed to find Server Action` — which, since `0.15.0` made the Worker serve
writes on a 530, is an ordinary event rather than a curiosity.

Claude attempted to generate and install the keys and was **refused by the
auto-mode classifier as a secret-store write**. That is the correct outcome and
was not worked around; Lutan installed both keys, and the verification was done
by comparing fingerprints, never values:

| | dev machine | Pi |
|---|---|---|
| production | `cbd55beae8d8` | `cbd55beae8d8` |
| test | `ecc41837fc0b` | `ecc41837fc0b` |

Then end to end, which is the part that matters: each deploy printed the key it
built with, and each Pi build confirmed the key was **in the build**, not merely
configured:

```
deploy: Server Actions key ecc41837fc0b (the Pi's build must print the same)      [test Worker]
actions-key (test): the build in .next carries that key                          [Pi test]

deploy: Server Actions key cbd55beae8d8 (the Pi's build must print the same)      [production Worker]
actions-key (production): configured key fingerprint cbd55beae8d8                 [Pi production]
actions-key (production): the build in .next carries that key
```

`strip-baked-env` removed `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` along with ten
other variables from the test Worker bundle, confirming it is a **build-time**
value and not shipped in the bundle:

### How the procedure held up, first time out

Written yesterday, used today. What it changed, concretely:

- **Major-versus-minor was asked before the cut** — the question `0.15.0` skipped.
- **Both Pi builds were Claude's and ran without a handover**, the production one
  in parallel with the test Worker deploy rather than after a wait.
- **Step 0 caught a prerequisite** rather than a surprise: reading the PRs' plans
  before cutting is what surfaced #312's missing key while there was still time
  to ask for it.
- **The commands handed to Lutan were given in forms that work** — absolute paths
  after one failed from `C:\WINDOWS\system32`, which was corrected in the same
  exchange rather than costing a round trip each time.

What it did not prevent: a gates run killed with the session and quoted from a
partial log would have been easy to accept; it was re-run instead. Worth adding
to the traps if it happens twice.
