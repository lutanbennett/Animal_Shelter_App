### The silent-failure question answered *yes*, and the danger was in the order, not the feature

`0.21.0` established the question. `0.22.0` and `0.25.0` answered no; `0.23.0` and
`0.24.0` answered yes, both times because a migration changed behaviour under a
live app. **This release is the first where the answer came from the migration's
own header telling us so**, and where the standard release order was itself the
hazard.

`0181_perm_drop_enum_drop.sql` says, in its header:

> *Apply only once the new app is live: the previous release still selects
> `app_users.role`, calls `current_user_role()` and writes `user_roles.role`, and
> fails the moment this lands.*

**Believed, then checked**, which is `0.25.0`'s lesson 2 applied. Read against
the live release's source rather than reasoned about:

```
590a9d35:src/lib/auth/app-access.ts:27      const { data } = await supabase.rpc("current_user_role");
590a9d35:src/lib/supabase/proxy.ts:114      // The app itself is for staff roles only (src/lib/auth/app-access.ts).
                                            // One role lookup per app request
590a9d35:src/lib/status/alerts.ts:135       .from("user_roles").select("user_id").eq("role", "admin")
590a9d35:src/app/admin/security/page.tsx:25 admin.from("user_roles").select("user_id, role, archived_at")
```

So the live `0.25.0` app called `current_user_role()` **on every non-public app
request**, through the proxy. And `loadCurrentRole` destructures only `data`:

```ts
const { data } = await supabase.rpc("current_user_role");
return (data as string | null) ?? null;
```

A dropped function therefore does not raise — it reads as **`null`**, which
`hasAppAccess(null)` answers `false`, which the proxy treats as *this person has
no role*. **Every signed-in person bounced out of the entire app, with no error
shown anywhere.** That is the worst shape a failure can take: closed, silent and
total.

The six consumer warnings fired exactly as loudly as they did for `0172` and for
`0175`–`0177`, and said the opposite of the truth:

```
note: These tables/columns land before the code that reads them is live. That is the safe direction -
      nothing is blocked - but do not deploy the reader before this is applied, and expect nothing to use it yet.
```

`0181` removes things the *current* reader uses. `0.25.0`'s lesson 1 holds for a
second release running: **the header warning is not the finding, and it looks
identical either way.**

### The order Lutan chose, the order that turned out to be impossible, and what actually ran

This is the part worth carrying forward, and it is a process failure, not a
software one.

**Three options were put to him before anything was applied**, with the cost of
each:

1. the standard order now — a certain ~2 minute total lockout, on a Sunday afternoon in Thailand;
2. **apply the three safe files, put the new app on the Pi first with `--force`, then apply `0181`, then the Worker** — no user-facing window at all, at the cost of the Worker fallback being a release behind for ~13 minutes;
3. wait until ~06:00 Thai, as `0.24.0` did, and run the standard order then.

He chose (2), and **(2) cannot be executed with the tooling that exists.**
`apply-migrations.mjs` applies every pending file or none — it has `--status`,
`--dry-run`, `--drift`, `--baseline`, `--env`, `--quiet`, `--short`, and nothing
that stops at a chosen file. And it deliberately refuses to run when a file on
`origin/main` is absent from the checkout:

```
for (const name of mainFiles) {
  if (!files.includes(name)) problems.push(`${name} is on origin/main but not in this checkout — sync first`);
}
```

So moving `0181` aside is not a workaround, it is defeating the guard that stops
us applying a different set of migrations than `main` holds. **The option was
offered without checking it could be run.** That cost a round trip at the worst
possible moment — after the cut PR had merged, with `main` already carrying the
release.

Put back to him as three honest options (wait for 06:00 Thai; teach the runner a
`--upto` flag as its own PR and ship today with no window; or accept the two
minutes now), **he chose to accept the window.**

**The lesson, and it generalises past this release: an option put to Lutan is a
commitment that it can be carried out. Verify the mechanism before offering the
choice, not after he has taken it.** The cost here was a round trip and some
trust; the next version of this mistake could be a plan abandoned half-applied.

Shorter than the ~2 minutes Lutan accepted, because the Next build compiled in

closes the window — not the Worker deploy, which ran afterwards and took far
longer.

### Migrations

Four, `0178` through `0181`. Production went `177 applied, 4 pending` to
`181 applied, 0 pending` in 17 seconds, all four `ok`.

**The production dry-run was red, and the correct action was to apply.** Third
recorded instance of the per-file `begin … rollback` trap:

```
dry-run 0178_perm_functions.sql … ok
dry-run 0179_role_floor_schema.sql … ok
dry-run 0180_perm_drop_enum_readers.sql … FAILED
Failed to run sql query: ERROR:  2BP01: cannot drop function has_shelter_floor() because other objects depend on it
DETAIL:  policy maintenance_delete_perm on table maintenance depends on function has_shelter_floor()
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

`0179` line 99 drops and recreates `maintenance_delete_perm` without
`has_shelter_floor()`; `0180` line 193 then drops the function. Each file is
dry-run in its own transaction, so `0179`'s new policy was rolled back before
`0180` ran. Both files were read before concluding anything, and dev already held
all four applied in order with `No drift`.

**Say which it was.** "The dry-run failed" and "the file is wrong" are different
statements, and only the second is a reason to stop. `CLAUDE.md` has carried this
since `0076`; it has now fired three times, and `--dry-run` has been misleading on
a release-blocking file twice in three releases. That is frequent enough to be
worth a tool change rather than a warning — see the backlog.

`0.20.0`'s correction was followed: **merge, pull, apply, deploy.**
`git status -sb` was read immediately before the apply and reported neither ahead
nor behind at `c3862e52`.
