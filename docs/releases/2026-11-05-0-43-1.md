## The two answers that were his, given in ONE round before the cut

1. **Should this release email you?** — **no.** His words were *"Let's do a minor release"*, and **that is exactly the ambiguity the runbook names**: in his usage *minor* has meant the middle-number bump, and the release that bumped it **mailed**, while in this repo `major` means *worth an email* and nothing to do with semver. The prescribed question was put with both words removed, naming the six notes, that the mail reaches one address in practice, and that it cannot be unsent once his deploy runs. **Read at face value this would have shipped as `0.44.0` with mail.** The trap fired; the question caught it.
2. **Four plans in this range are signed `pending:` — ship or hold?** — *note and ship*. The seventh release running with that answer. They are listed at the end of this record.

**The release cost two touches — the target.** That one answer, and `node scripts/deploy.mjs --env production`.

## What shipped

Six notes, five of them written by the streams that did the work:

1. A login with **Propose website changes** can now draft the website's **settings** as well as its pages; it waits under *Page changes* and only **Approve website changes** publishes it.
2. The assistant now says when a note saved but the residents tagged in it could not be linked.
3. **Settings → Who does what opens again** — it showed *"This page couldn't load"* for an Admin in `0.43.0` (`admin: true`).
4. **Publishing an adoption update now works**; the three fields were never stored, and a first name containing `s` is no longer refused. Updates ticked before the fix must be ticked again.
5. A **menu way in** to the photo and website approval page.
6. **Project photos now wait for approval** — written in the cut, because `0316` is the step it was waiting on.

## Before the deploy

- **`npm ci` in the main checkout FAILED, and that is this release's real finding.** `EPERM: operation not permitted, unlink node_modules/@next/swc-win32-x64-msvc/next-swc.win32-x64-msvc.node`. It had already taken `node_modules` from 484 packages down to **37**, and **the main checkout is where both deploys run `next build`**, so the next command would have failed in a way that looks nothing like its cause. Held by a stray `next start -p 3100` **in the main checkout**, started 09:29 and still alive at 15:51 with nothing listening on 3100. Repaired with `npm install`, which restores the tree without unlinking the locked file: 484 packages, `next@16.4.2`, the binary present. **Then proved rather than assumed** — `npm run build` in that checkout exited 0 and printed `▲ Next.js 16.4.2 (Turbopack)` — before his command was handed over. **Stopping the process was refused** by the auto-mode classifier as *Interfere With Workloads*, so it is still running and is the one thing left on his list.

The PR's own `audit` job **ran for real** (the cut changed `package-lock.json`) and passed.
- **`release-prs.mjs` was not short a PR this time**, after five releases running where it was. Cross-checked anyway against `gh pr list --state merged` by `mergedAt`: exactly the same 11 merged after `3227a19e`.
