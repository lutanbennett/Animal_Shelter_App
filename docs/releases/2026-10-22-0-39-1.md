## The wrong-number gap is CLOSED, and Lutan closed it himself

**This is the headline of the release and it is not a feature.** The diets
portion path has been the one item anywhere whose failure is a **wrong number**
rather than a visible fault. It shipped unlooked-at in `0.39.0` on his explicit
decision, and `0.39.1` rebuilt the very screens that produce those numbers, which
made it the release's single largest unmeasured risk.

It was put to him separately from the count, as the procedure requires — *"the
check is about five minutes: add a diet with four ingredients, read the Standard
card's medium total, it should say 4 cups"*. His first answer was to ship it as a
recorded gap and adjust in a later release, which would have been the sixth
release running. **He then went and did it anyway**, unprompted, while the builds
were still going: *"I did test the diets on test and it worked fine."*

Recorded on `docs/test-plans/diets-recipe-book.md` as item 1 closed, at his
explicit request in chat and marked as written by me on his behalf, with items 2
and 3 (Purchasing before and after, the Thai wording) left `pending:` because he
did not claim those and I may not infer them.

**Two things worth carrying.** First, **putting the numeric item separately from
the count is what produced this** — it has now been answered differently from the
rest three times, which is the whole argument for the separation and the reason
the next release manager should keep doing it even when the answer has been the
same five times running. Second, a gap that is *named concretely* — four
ingredients, 4 cups, that screen — is one a person can close in five minutes. A
gap written as "the diets screens need checking" is not.

## The role tag would have been wrong in the obvious way

The cut had to tag the Settings → Diets note — **third release running**, and the
cause is still the one `0.39.0` filed on the `backlog` branch:
`docs/test-plan-template.md`'s release-notes line asks whether a user would notice
and never asks *who*.

What is new is the trap inside it. The page lives at `/admin/diets`, so the
obvious tag is `["admin"]`. **That would have hidden the note from the doctors who
can open the page.** The route is gated on the `reference.types` activity, and
`src/lib/permissions/fixed-for-now.ts` grants that to the **doctor** box as well
as to admin. Tagged `["admin", "doctor"]`, read from the permission source rather
than inferred from the URL.

**The template's own warning is that a wrong tag is worse than none**, and this is
the shape it takes: the tag that looks obviously right from the path is the one
that loses a reader. The next release will almost certainly have to tag another
note — **read the permission source, not the URL.**

## A release note that depends on a flag, and the flag is on the handover

Note 3 promises that vet visits reach the shelter's Google Calendar **on the live
site**. That is true only if the production Worker holds
`GOOGLE_CALENDAR_REFRESH_TOKEN` and `GOOGLE_CALENDAR_ID`, which it did not before
this release. Both values were already in `.env.deploy.production`
(`docs/decisions/2026-10-22-vet-calendar-on-production.md`), so the step is
`deploy.mjs --env production --secrets` — **a flag on the one command Lutan runs,
not a second job for him.**

This sits exactly on the edge of the release-note truth rule. The rule says not to
tick the release-notes line while an outstanding manual step stands between the
code and the user. Here the step is performed *by the deploy itself*, like a
migration apply, so the note is true the moment the release is live — **provided
the flag is there.** A plain `deploy.mjs --env production` would have shipped it
false, in exactly the way #518 did.

**So the risk was not in the note, it was in the handover**, and that is where it
was managed: carried as a `deferred:` line in section 8 of the cut plan with the
reason spelled out, and stated in bold in the message that handed the command
over. Worth recording because the general shape recurs — **when a note depends on
a deploy flag, the flag is the thing that can be forgotten, and prose in a
decision file does not reach the person typing the command.**

### Both failures were the same fault: checking the half I had thought about

**The standing rule at the top of the runbook is "do not hand Lutan a command you
have not confirmed runs in his shell."** I broke it twice in fifteen minutes, and
in both cases I had done *some* verification — enough for it to feel checked.

1. **`--secrets`.** I confirmed both calendar values were in `.env.deploy.production`. True, and insufficient: `--secrets` pushes **every** runtime secret, and four Drive values resolve only from `.env.local`. The guard refused. **I verified the change I was making; I did not verify the command I was typing.**
2. **The clean tree.** I then wrote the fix — a script — into the **main checkout**, which dirtied the tree, and handed the deploy over without re-reading `git status`.

**The fix that worked, and the one to copy:** before the third attempt I read the
guard's own source, enumerated all four conditions it tests, ran each against the
live state, and printed the answers as a table before writing the command out.
That took under a minute. **Doing it the first time would have cost the same
minute and saved two round trips of his.**

Two smaller lessons inside it, both general. **A refusal message's suggested
remedy is not advice** — the `--secrets` refusal offers
`--allow-dev-fallthrough`, which here would have overwritten four working
production secrets with dev values, including the Drive folder id that decides
where resident photos are written. **Read what the flag would do before taking the
suggestion.** And **a scratch file inside the repo is not free**: `CLAUDE.md`
already forbids scratch output *above* the repo, and this is the neighbouring
case — a file written *inside* the main checkout blocks every guarded deploy
until it is moved.
