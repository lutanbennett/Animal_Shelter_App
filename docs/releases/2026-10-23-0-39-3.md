## The headline: I broke his deploy, and it cost the release's shape

**I started the test Worker deploy in the main checkout and then handed him the
production command before it had finished.** Next refuses a second build in one
checkout, so his died about a minute in:

```
⨯ Another next build process is already running.
deploy: `npm run opennext:build` exited with 1
```

**The collision is already written down** in `release-procedure.md` — *"two builds
in one worktree collide"*. Knowing the trap did not help, because **I never checked
the precondition before handing the command over.** That is the same fault this
release found twice in the runbook's own text, committed by the person who found
them.

**It cost two things, not one.** The obvious one is a wasted ten minutes of his
time. The second is the release's shape: by the time a second attempt was possible,
`main` had moved, and `deploy.mjs` requires `HEAD == origin/main` with **no
`--ref`**, so the Worker could then only be built from the moved tip. The
"all four builds from one SHA" property was lost to a mistake rather than to
anything about the software.

**What to do differently, concretely:** before handing over the production deploy,
confirm `Get-Process node` returns nothing **and** that your own test deploy has
*exited* — not merely printed its last interesting line. A backgrounded deploy that
has reached the upload stage is still holding the lock.

## Note 2 is half-true on production, and that is this release's one open inaccuracy

Worth stating plainly, because it is the `#518` shape found before anyone
complained rather than after.

Note 2 promises two things. **The first is true**: booking or editing a visit
writes the calendar entry — including `Reason: …` — from
`src/app/clinic-visits/new/actions.ts` and `[id]/edit/actions.ts`, which are server
actions, so on production they run **in the app on the Pi**, which has `0.39.3`.

**The second is not true yet**: *"entries already in the calendar gain it within 15
minutes after the update"*. That depends on the quarter-hourly sweep, and the sweep
runs **inside the Worker's own bundled app** —
`worker/index.mjs:197`, `await openNext.fetch(request, env, ctx)`, where
`STATUS_ALERT_SITE` only builds the `Request` and is never fetched over the
network. So the sweep is `0.39.2` code and adds no Reason line.

**Two steps make it true, in this order:**

1. the production Worker deploy above;
2. then `node scripts/resend-calendar-reasons.mjs --env production --apply`, which
   marks existing upcoming visits out of date so the next sweep rewrites them.

**Step 2 was deliberately NOT run.** With a `0.39.2` sweep behind it, it would have
marked the visits, let the old sweep rewrite them without the Reason line, and
cleared the out-of-date flag — leaving the entries wrong and the evidence gone.
**Ordering matters here and the obvious order is the harmful one.**

**No mail went out**, this being minor, so the note is only visible to someone
reading `/releases`. **The note was not edited**: amending a published entry means
re-running the gates and the note-by-note comparison on a register meant to stay
stable, for a sentence that becomes true with one command.

## Two faults found in the runbook itself, both fixed in it

- **The handover command could not have run in his shell.** It read `mkdir -p .local && node scripts/deploy.mjs …`: `&&` is not a statement separator in PowerShell 5.1 and `mkdir -p` is not a PowerShell flag, so it would have parse-errored and run **neither** half. It sat a few paragraphs below where the same document names the `&&` trap, under its own rule about not handing over an unverified command, and survived because release managers fixed it silently on the way past.
- **There are four gates, not three.** `gates.mjs` ends `typecheck=0 lint=0 test=0 build=0`; a `test` gate runs between lint and build. `release-procedure.md` and `CLAUDE.md` both said "typecheck, lint, build".

**When a document's instruction is wrong, fix the document.** Both are corrected in
this PR.

## `check-test-plan.mjs --base origin/main` earned its place again

Two faults caught before CI saw them, which keeps the "first CI run green by
construction" counter at **3**:

- **a cut PR cannot tick the release-notes line.** The checker holds it to the diff and a tick needs `unreleased` to have *gained* a line; a cut's purpose is to *empty* it, so the honest state is `n/a:`
- **a reason must follow `n/a:` immediately** — `n/a as a banding change` fails where `n/a: there is no band …` passes
