## The migration

`0194_role_cards.sql` → `dbkodyyxxhtygxcxmfcu`, applied before either deploy.
`applying 0194_role_cards.sql … ok`. Afterwards: `195 applied, 0 pending`.

**This is where the silent-failure question was asked, and it answers no.** The
release note promises "Nobody's access changes on the day this arrives", which is
precisely the kind of claim the handover says to diff rather than believe.

It holds, for a better reason than a careful author:

- The migration carries **no seed taken from dev**. Its seed block derives each
  non-fixed role's cards from **that database's own `role_permissions`** — the
  cards whose bundles the role's existing cells already fully give — records every
  remaining cell as a `role_extras` row with a stated reason, and then asserts
  that cards-plus-extras reproduces `role_permissions` **cell for cell**, with
  `raise exception` if it does not. It also refuses a named card the role's cells
  would not already give, calling it "a finding, not something to adjust".
- So it **cannot** quietly shrink anyone's access. If it could not reproduce
  production's permissions exactly, it aborts and rolls back. The failure mode is
  loud by construction.
- And it was exercised against production's real rows **before** the apply:
  `--dry-run` runs the real DDL inside `begin … rollback` against production's
  actual schema, so that seed block ran against production's own
  `role_permissions` and raised nothing. That is the evidence for the apply, not
  the header's description of itself.
- Forward of that, `set_role_cards()` keeps extras across every recompute, and
  `scripts/check-cards-schema.mjs` is the standing assertion that the live rows
  and the code still agree. The two readers that come live in this release fail
  loudly rather than quietly: `src/lib/home/roles.ts` throws on a failed
  `role_cards` read, and the Who does what actions return a visible
  `databaseFailure` rather than a partial write.

**Two of the release's other changes remove silent failures rather than adding
any.** Bill photos were being saved and never shown — the bill just kept asking
for a photo — and the page now says so when one cannot be loaded. And the backup
tile now reads an unconfigured folder as a stated settings fault instead of
looking like a missing backup.

The consumer warnings are the safe direction, as the handover says:
`src/lib/permissions/cards.ts` and `scripts/check-cards-schema.mjs` do not exist
in `0.29.0` at all, and two more differ from it. The tables landed before the code
reading them was live.

**No production-only guard appeared** — the sixth release running. It can only
show up at the production dry-run, and it did not.
