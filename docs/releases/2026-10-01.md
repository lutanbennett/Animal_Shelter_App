### What is in it

Sign-in and every form on the site working again; units of measure, so food and
medicine can be bought and counted in one unit and fed or dosed in another; the
website and app now prepared by a Raspberry Pi at the shelter, with the weekly
backup moved there; a deceased resident's Drive archive reporting a failed
refresh instead of going stale silently; and real messages with a reference on
the Projects pages.

`major: true` on Lutan's call. The deciding note was the first: **sign-in and
every save failed from the evening of 30 September until the morning of 1
October.** Admins fielded that, and the mail is how they learn what it affected
and that it is over.

### Two copies of the app, and only one of them was ever guarded

**This is the finding of the release, and it was turned up by a drift check Lutan
asked for** on the suspicion that an urgent fix for the sign-in outage had been
applied to the database by hand. It had not — but the reason the fix was already
live turned out to matter more.

Production serves from the Pi (`ORIGIN_HOST: pi.lannacare.org`;
`lannacare.org` answers `x-lanna-served-by: pi`), with the Worker as fallback.
`scripts/pi/deploy-pi.sh` is 51 lines: `git fetch` → `git reset --hard
origin/main` → `npm ci` → `npm run build` → `systemctl restart`. **It has no
release guard of any kind** — nothing checks `unreleased`, `latestRelease` or
`package.json`, where `deploy.mjs` refuses to ship anything that is not a
written-down release.

So the Pi serves whatever is on `main`, and **every note in this release was
already live before it was cut.** Three consequences, none fixed here:

- Code reaches users without a release cut, so release notes describe what people
  already have rather than what a deploy will give them.
- The release-time check that every PR in a release has a completed test plan
  never runs for anything arriving that way.
- **`npx wrangler rollback --env production` no longer rolls production back.** It
  reverts the Worker, which is not serving. Rolling the Pi back means `git reset
  --hard <sha>` and a rebuild, which is written down nowhere as a rollback path.
  Every earlier record in `docs/releases/` states the `wrangler rollback` position
  as if it were the whole answer; from 2026-09-30 onward it is not.

**A correction that applies backwards.** `/api/releases/current` is answered by the
Worker (`worker/index.mjs:158`, handled locally with `BYPASS` before the origin is
consulted). So every "the version endpoint reports X" line in this session and in
`2026-09-29.md` and `2026-09-30.md` is evidence about the **fallback**, not about
the app anyone uses. It was demonstrated live during this release: between the test
deploy and the production deploy, `lannacare.org/api/releases/current` reported
`0.10.1` while the Pi was serving `main`. Neither figure was wrong; they described
different copies.

**The Pi's own version cannot be read from outside, which is a real gap — but it was
answered for this release.** `/releases` is app-rendered and therefore Pi-served,
but it redirects to `/login` while the public site is locked, and signing in from
this session is out of scope; nothing exposes the Pi's commit or register version
unauthenticated. So the evidence came from the Pi itself. Lutan ran
`./scripts/pi/deploy-pi.sh` after the production deploy, and its output reads
`> lanna-animal-care@0.11.0 build`, then `Compiled successfully in 4.3s`,
`Finished TypeScript in 6.7s`, `Generating static pages (66/66)`, and finally
`deploy-pi: lanna-care running` with the script's own closing check,
`deploy-pi: https://lannacare.org/ served by: x-lanna-served-by: pi`.
**So both copies are on `0.11.0`**, the service restarted cleanly, and the Pi is
confirmed still serving — `/releases` now shows users the release the mail
announced.

The build reported one warning, pre-existing and unrelated to this release:
`[turbopack-wasm] /node/loadWasm.ts:25:10 — The file pattern … matches 55196
files in [project]/`. A Turbopack glob warning on a dynamic `node` require, not an
error; the build succeeded.

**The gap itself stands even though this instance closed.** It was closed by
someone pasting a terminal into chat — the same mechanism that loses a release
record when nobody does. A version endpoint served by the app rather than the
Worker would make it answerable from anywhere.

### Why this deploy was worth doing promptly even though the Pi was current

The sign-in fix (#247: `40559a2` at 08:21 and `d063fee` at 08:33 on 2026-10-01)
changes `next.config.ts`, so it only takes effect in a build. The last production
**Worker** deploy before today was `0.10.0` at `d26103b`; `0.10.1`'s was never
logged. Both predate 08:21. So until this deploy, **a Pi timeout would have fallen
through to a Worker that still refused Server Actions** and reinstated the outage
for its duration. Refreshing the fallback was the urgent half of this release.

### Worth doing next

1. **A release guard on `deploy-pi.sh`** — the same shape as the `deploy.mjs --drift`
   item already on the backlog: a check that exists on one path and not on the one
   that matters. Without it, "what is live" and "what has been released" drift apart
   by design.
2. **A version endpoint served by the app, not the Worker.** One line of the gap
   table above exists purely because `/api/releases/current` is intercepted upstream
   of the origin.
3. **Rewrite the rollback position** wherever it is documented. `wrangler rollback`
   has not been the production rollback since 2026-09-30, and four release records
   state it as though it were.
