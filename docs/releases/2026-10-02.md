Two things in this release have no release note, and that was the right call
rather than an oversight:

### SSH to the Pi, set up during this release

Until today the Pi half of every release was a hand-off: Lutan ran
`deploy-pi.sh` on the box and pasted the output back. That is now partly closed.

- A keypair was generated on the laptop (`ed25519`, no passphrase) and Lutan
  installed the public half on the Pi. `~/.ssh` had held **no key at all**, which
  is why an earlier attempt at the same thing had silently done nothing.
- `pi.lannacare.org` is **not** reachable by SSH — it is the cloudflared ingress
  and forwards HTTP only. `lanna-pi.local` is the address that works.
- Three commands failed on the way, all for shell reasons rather than anything
  being wrong: `&&` is not a statement separator in Windows PowerShell 5.1;
  `ssh-copy-id` does not exist in PowerShell (only in Git Bash); and
  `./scripts/pi/deploy-pi.sh` was pasted into PowerShell on the laptop, where it
  is a bash script on the wrong machine. The fix that stuck was a one-token
  `.cmd` file, because `.ps1` is blocked by this laptop's execution policy — the
  same policy that has required `npm.cmd` all week.

**What it does and does not buy.** Claude can now run `deploy-pi.sh` over SSH
unattended — the `git reset`, `npm ci` and `npm run build` all completed that
way. It cannot finish the job: the script ends in
`sudo systemctl restart lanna-care`, and sudo over a non-interactive SSH session
fails with `sudo: a terminal is required to read the password`. So the Pi deploy
currently stops one step short and a person restarts the service. A sudoers rule
scoped to that single command would close it; it is a privilege change on the
Pi and was deliberately left to Lutan rather than made by the session.

### Proving the Pi took it — new in this release

Every record since 2026-09-30 has had to say the Pi's version was unverifiable
from outside, because `/api/releases/current` is answered by the **Worker**
(`worker/index.mjs:158`) before the origin is consulted, and `/releases` redirects
to `/login` while the site is locked. So a Worker reporting `0.13.0` says nothing
about what the Pi is serving — which is exactly how a stale Pi could hide.

Two checks close it, and both were run:

1. **The service really restarted.** Before: `MainPID 8760`, started
   `02:06:41` — about ten hours old. After: `MainPID 10533`, started
   `12:02:38`, uptime 17 seconds. A first restart attempt had *not* taken, and the
   PID timestamp is what caught it; the version endpoint would have read `0.13.0`
   throughout.
2. **The served page carries the build that was just made.** `.next/BUILD_ID` on
   the Pi is `X-FfsFYHo531vJjYDSvP_`, and the markup returned by `lannacare.org`
   (answered `x-lanna-served-by: pi`) contains that exact string.

A correction worth keeping with it: an earlier attempt at check 2 reported "still
serving the OLD build" when its extraction had simply found no build id — the
script fell through to the wrong branch on an empty value. The conclusion was
withdrawn. A comparison that cannot find one side of itself must say so rather
than report a mismatch.
