## The three migrations, and the two that needed reading

### `0437` rewrites rows, so it got a before-picture

The runbook requires a kept before-picture for anything that rewrites rather than adds. The backfill
is two statements and both are blanks-only:

```sql
update public.shelters set display_name = name           where display_name is null or btrim(display_name) = '';
update public.shelters set short_name = left(name, 60)   where short_name   is null or btrim(short_name)   = '';
```

Read with `check-shelter-settings.mjs` on both environments **before** applying: production's
`display_name` was already `"Lanna Care for Animals"` and its `short_name` a typed `"LCA"`; UAT's
check flagged neither name column, so both were populated.

**So both statements matched zero rows on both environments** — a row-rewriting migration that
rewrote nothing. **Confirmed after applying:** both environments' output is byte-identical to the
before-picture, `"LCA"` included. No backup was needed and none is claimed.

### `0438` was read against the card rule, not trusted to its header

It lets a product administrator change which existing role a login holds, which is close enough to
the card rule to deserve a direct check rather than a reading of its own comments:

- **It writes only `user_roles`** — grepped for insert/update/delete against `roles`, `role_cards`
  and `card_grants`: no hits. So it adds no way to change what a role can *do*; a role is still
  exactly the set of cards it holds.
- **Six `is_product_admin()` calls across six functions**, plus aal2 inside each definer body.
- **No lock-out**: a change leaving the shelter with no live login holding its Admin role is refused
  (23514). Admin holds no cards, so the last Admin login is a one-way door.
- Remove is an **archive**, not a delete; audit comes from the existing `record_audit()` trigger.

## What was read rather than assumed

### A finding filed: seven definer functions outside the catalogue (`#tnycl`)

`0436` and `0438` add seven `security definer` functions and **neither carries an
`alter function … owner to` line**, so all seven keep the connecting role — `postgres`, which has
BYPASSRLS on Supabase — and **none appears in `ALLOWED` in `scripts/lib/tenancy-catalogue.mjs`**.

That catalogue's own header says why it exists: *Postgres cannot default an object's owner, so a
migration that forgets is back to BYPASSRLS silently.* The list is how a deliberate survivor is told
apart from a forgotten one.

**Measured, not estimated.** Production before applying: **123 flagged (47 views, 76 functions), 7
allowed by name, 0 stale.** After: **130 flagged (47 views, 83 functions), 7 allowed, 0 stale** —
**exactly the seven**, which is what makes the finding specific rather than a suspicion.

**Why it is not a blocker, written down so nobody re-raises it as urgent:** the lint is
report-only and always exits 0; 123 objects were already flagged before these migrations, so this is
the existing shape of incomplete re-own work; and every one of the seven is gated by
`is_product_admin()` plus aal2 inside its own body. Filed as `#tnycl` with the work split into
deciding the owner for the three that do not read `auth.users` and cataloguing whichever must stay.
