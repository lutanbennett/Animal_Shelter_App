### The silent-failure question answered *no*, on evidence

Sixth release of nine to answer `no`. Five migrations, two of them touching code
paths the live app uses on **every attachment**, so each was checked against what
the live `0.27.1` app actually does:

**`0189_bills.sql`** replaces all four `attachments_*_perm` policies — the
policies governing every resident photo, blood-test file, procedure file,
maintenance photo and project photo in the system. Its header describes the undo
as *"restore the four attachments_*_perm policies from 0152"*, which is a clear
statement that it replaces live policies and tells you nothing about whether it
changes them. So they were diffed against `0152`:

```
0152 →  when 'resident' then (select has_permission('resident.record', 'read')) and (select sees_all_residents())
0189 →  when 'resident' then (select has_permission('resident.record', 'read')) and (select sees_all_residents())
```

All five existing arms are **character-for-character identical** across all four
policies. The only change is the `else` branch, `false` → `bill_owner_can(…)`,
reachable only by the four owner types `0188` adds and which nothing in the live
app can produce. Strictly a widening.

**`0190_record_attachment_bills.sql`** replaces `record_attachment()`, which the
live app calls on four upload paths (`residents/[id]/photos/route.ts:191`,
`medical/residents/[id]/photos/route.ts:106`,
`blood-tests/[id]/attachments/route.ts:139`,
`procedures/[id]/attachments/route.ts:155`). Diffed against `0178`'s body: the
change is **four added `when` arms**, nothing else — signature, guards and every
existing arm untouched.

The remaining three are additive. **So the method `0.27.1` settled held for a
fifth file-pair and is worth stating as settled: read what the live app passes
in, and read how the thing it passes is produced.** A header that says "the
signature is unchanged", or "defence in depth", or "restore the old policies to
undo", is a description of intent, not evidence about behaviour.

Contrast `0181` three releases ago, which dropped what the live app called on
every request.

## Defects

### 1. `release-prs.mjs` exited 1 — one squash-merged PR, resolved by hand

`release-prs.mjs 3c7632ca b5fd020d` exited **1**, naming
`docs/test-plans/planner-handover-105.md` as belonging to no PR in its list. It
belongs to **#575**, squash-merged, so no merge commit carries its number —
matched by `gh pr list --state merged` and the commit subject's `(#575)`.

`0.27.1` had four of these and predicted this would be routine. It is: one this
time, resolved in a minute. **Accepted, not a fault in the script.**

**#575 is also the handover lesson repeating itself**: it merged *after* the
first PR list was built and *before* the cut merged. The list was rebuilt against
the release SHA after the merge, which is what caught it, and `unreleased` was
re-read on `main` afterwards and confirmed to hold only the one note. Expect this
every release.

### 2. The main checkout's dependencies were stale, and it would have shipped a Worker built off the lockfile

**The most important thing in this record.** The first test Worker build printed
`Next.js version : 16.3.5` while both Pi builds printed **16.3.8**, which is what
`package.json` and `package-lock.json` pin. The main checkout had `next@16.3.5`
installed: the lockfile had been bumped by a merged PR and `npm ci` had never
been re-run there.

**Caught by reading the build banner, not by any gate.** Nothing checks this.
`deploy.mjs` verifies the commit, the project ref and the env vars — every one of
which was *correct* — and says nothing about what is in `node_modules`. The
release SHA would have been right on all four builds and the claim "all four from
the release SHA exactly" would have been true and misleading.

The build was stopped, `npm ci` run in the main checkout (~4 min), and the test
Worker redeployed; the second build printed `16.3.8`. **The production Worker was
then built from the corrected install**, so what is live is consistent.

**For the next release: read the `Next.js version` line on the first Worker build
and compare it against `package.json`.** It costs nothing and it is the only
place this is visible. Better still, `npm ci` the main checkout as a release step
before any deploy — the Pi clones do it inside `deploy-pi.sh`, which is exactly
why they were right and the laptop was wrong.

### 3. The production migration apply was refused by the classifier, in its plain form

`node scripts/apply-migrations.mjs --env production` was refused with
`[Production Deploy]`. **This was already the plain form** — no timestamps, no
redirect, nothing wrapped round it — so `0.27.1`'s lesson 5 did not apply and
there was nothing to simplify. It was not retried blind. Lutan ran it himself and
all five applied `ok`.

**So the refusal is not reliably avoidable by shaping the command.** `0.27.1`
got the plain form through on the first attempt; this release did not.
Budget for the possibility that the apply is a hand-off, and hand it over the
moment it is refused rather than retrying — the dry-run, `--status` and `--drift`
all ran fine before and after, so it is not a production-access block.

**Cost: the apply's own output was not captured by this session**, so the file
order and timings here are read from Lutan's terminal rather than from a log.

### 4. The daily backup has not run since 2026-10-11

The crontab line is installed and `cron` is active, but the last backup it wrote
is `lannacare-production-2026-10-10T2000Z.dump.age` at 03:00 on 2026-10-11. There
is **no record of the job firing at 03:00 on 2026-10-12** — no log line, no file,
and the Pi has been up continuously since 2026-10-02. `backup.log` is 516 bytes
and holds exactly one run.

Raised with Lutan at the cut. **Not a release blocker** — his three hand-made
dumps from 2026-10-12 are newer than anything the cron would have produced — but
it wants a look after the next 03:00 run, and it is pointed: **this release ships
the System status backup tile whose entire job is to catch this**, and that tile
is itself unverified on production (`docs/test-plans/backup-daily.md`, carried
forward below).

### 5. `apply-migrations.mjs --drift` crashes on every run

`ReferenceError: unapplied is not defined` at `scripts/apply-migrations.mjs:226`,
on every environment, every time. Introduced by `e6df8b2b` — the `--upto` PR
(#570), **in this release**. `driftReport()` destructures the two arrays into its
own scope and returns only their total; the new explanatory block at the call site
reads them as though they were still in scope.

The crash lands *after* the comparison has printed, so the substance survives and
is quoted above; the verdict line and the exit code are lost. Nothing in CI runs
`--drift`, which is why it reached `main`.

Two-line fix, filed on the backlog rather than bolted onto a release already
cut. **Also noted there:** `--drift dev` is not a thing — the dev database is
`--env test`.

### 6. Two migrations in this release are both numbered `0191`

`0191_donation_channels.sql` (#572) and `0191_stock_receipts_update_policy.sql`
(#574). CLAUDE.md allows one in-flight migration at a time precisely to prevent
this. **Nothing is broken** — `schema_migrations` records each by its own
filename, they touch unrelated objects so order cannot matter, and applied files
are never edited, so renaming is not the answer.

Already on the backlog, found 2026-10-12, with the planner-side cause (a schema
slot released when the schema PR merged rather than when its app PR did). Its
first ask — that the release manager be told "0191" is ambiguous — is discharged
by this record and by `docs/release-handover.md`.
