### What is in it

write; a new Appointments page for vets, replacing My tasks for that role
entirely; the shelter's fixed monthly costs in the cashflow forecast; a printable

### The first double-digit version, and the mail proves it worked

`0.10.0` is the first release whose minor number reaches two digits. **A naive
string comparison puts `"0.10.0"` before `"0.9.1"`**, which would have made
`majorReleasesSince("0.9.1")` return `[]` and sent **no mail at all** — a major
release going out silently, nothing failing and no error to notice.

It did not happen, and there are now three independent confirmations:

1. **Assertions at the boundary** (#229's plan, §2): `compareVersions` is numeric,
   `compareVersions("0.10.0","0.9.1") === 1`, and the register's file order still
   matches a re-sort by it across all fifteen entries.
2. **An audit of every other version comparison in the codebase.**
   `compareVersions` has exactly one caller; everywhere else compares by
   equality, never ordering. The trap had no second place to fire.
3. **The deploys themselves.** Test printed
   `deploy: release mail for 0.10.0 [off]: sent 0, skipped 4` — the step engaged
   and was refused only by the environment guard — and production printed
   `deploy: release mail for 0.10.0 [UAT]: sent 1, skipped 1`. **The mail was
   actually sent.** `sent 1, skipped 1` is the expected shape and not a fault:
   Lutan confirmed on 2026-09-29 that he receives these.

### Migrations: the right outcome, reached the wrong way round

**This is the part of the release worth reading.** The plan required all four
migrations to be applied *before* the deploy, and said plainly that none was safe
in the other order — unlike `0.9.1`, where two of three were additive with
defaults. Here `0113` adds a column the resident screens read, `0114`+`0115`
create a table the cashflow page queries, and `0116` creates a function the vet
interface calls, so deploying first means four features **erroring**, not
degrading.

**The deploy was started before the migrations were applied.** It was found
because an unrelated `--drift` command could not write to `deploy.log`
(`Device or resource busy`) — the running deploy held it — and the log's tail
showed an OpenNext build in progress. A process check confirmed
`node scripts/deploy.mjs --env production`, PID 5312, started 05:49:44.

**No harm done, because a deploy spends its first several minutes building.** The
migrations were applied while the build ran, finishing with `No drift: production
matches origin/main` at 116 files while the deploy was 134 seconds in and still
compiling. The schema was therefore in place well before the Worker upload, which
is what actually matters — the ordering requirement is "before the new code
serves traffic", not "before the deploy command is typed".

Worth keeping, because the margin was luck rather than design: had the button been
pressed on a warm build, or had the apply needed a fix first, 0.10.0 would have
gone live against `0112` schema with four broken features and no error anywhere in
the deploy output to say so.

### The dry-run failed, and the file was not wrong

```
dry-run 0113_resident_microchip_number.sql … ok
dry-run 0114_fixed_outgoings.sql … ok
dry-run 0115_fixed_outgoings_grants.sql … FAILED
Failed to run sql query: ERROR:  42P01: relation "fixed_outgoings" does not exist
Stopped at 0115_fixed_outgoings_grants.sql; nothing from it was kept. Fix the file and re-run.
```

This is the caveat CLAUDE.md documents from `0075`/`0076` on 2026-09-24, hit again:
each file is dry-run in its own `begin … rollback`, so `0114`'s new table was
rolled back before `0115` ran. Both files were read before drawing a conclusion,
as the rule requires — `0114` creates `fixed_outgoings` at line 30, and `0115`
contains nothing but `grant`, `revoke` and `notify pgrst` on that table. So the
dependency is real, the file is correct, and **the correct action on a red
dry-run was to apply**, which is the opposite of what a red dry-run usually means.

It applied cleanly:

```
applying 0113_resident_microchip_number.sql … ok
applying 0114_fixed_outgoings.sql … ok
applying 0115_fixed_outgoings_grants.sql … ok
applying 0116_set_resident_microchip.sql … ok

Against origin/main d26103b: 116 file(s), 116 applied row(s).
No drift: production matches origin/main.
```

**Why `0115` exists at all** is worth recording beside this: `fixed_outgoings` was
created by `0114` without Data API grants, and since applied files are never
edited the grants had to be a separate migration. On production both applied in
one run, so the ungranted window never existed there. Had an apply stopped between
them, the table would have been present and unreachable through PostgREST, and the
cashflow page would have failed with a permission error rather than a
missing-column error — two failures that look nothing alike with the same cause.

`0116` is a security-definer function, chosen over widening the `residents` RLS
policy so that a vet's write surface is two columns of one row by construction
rather than by policy
(`docs/decisions/2026-09-29-vet-microchip-write-via-definer-function.md`).

### The date, and the seven hours that keep coming up

The register entry reads `2026-09-30`, **Lutan's explicit call** when the clock
rolled over mid-cut: the cut was made at `2026-09-29` and the gates ran past
midnight.

Which "today" was not a pedantic question. At the moment of the change it was
`00:10` on the 30th in Thailand and `17:10` on the **29th** in UTC, so an
assertion against `new Date().toISOString()` returned false — the entry was right
and the check was wrong, because dates in this project follow Thailand's clock
(release `0.1.0`'s first note). **This release was therefore cut inside the same
midnight-to-07:00 window that `0.8.1` and `0.9.0` both shipped fixes for** — the
fourth time those seven hours have caused trouble, and the first time it was the
release tooling rather than a feature.

### Worth doing before the next release

**`deploy.mjs` has no idea whether the schema it needs is applied.** It guards the
branch, the working tree, the version and `unreleased`, then builds and ships. It
does not ask whether `origin/main`'s migrations are on the target database, even
though `apply-migrations.mjs --drift <env>` answers exactly that and already shares
its implementation with Settings → System status. A `--drift` check at the top of a
guarded deploy would have refused this one in a second, with the four pending files
named. This release worked because a build takes minutes; that is not a guarantee,
and it is the cheapest gap on the list to close.

### The migration went on after the deploy, and the public site was broken until it did

**`0117` is `0.10.1`'s only migration, and it was applied roughly an hour after the
release went live.** It adds `is_microchipped` to `public_resident_profiles`, a
boolean derived from `residents.microchip_number`. The consumer shipped in the
release: `17c7f0d` ("Microchipped tick on /adopt/[id]") is an ancestor of the cut
merge, and both `src/app/adopt/[id]/page.tsx` and `src/lib/residents/public.ts`
select `is_microchipped`.

So between the deploy and the apply, **the public adoption profile was querying a
column that did not exist.** `/adopt` responds normally now that `0117` is on.
What cannot be said is how long that lasted or what a visitor saw, because the
deploy time is not recorded.

Two things let it happen, and neither is a one-off:

- **`docs/test-plans/cut-release-0-10-1.md` answers both of its migration lines
  `n/a: no migration`** (lines 46 and 126). That is true of the *cut PR* — #238
  carries no migration — but the plan is also where a release's apply plan lives,
  and `0117` had arrived in #232 two PRs earlier. Nothing joined the two up. Every
  other cut plan in this sequence has a §3 apply plan naming the release's pending
  files; this one has the honest answer to the narrower question instead.
- **`deploy.mjs` still does not check drift.** It guards the branch, the working
  tree, the version and `unreleased`, then builds and ships without ever asking
  whether the target database has the migrations its code needs — even though
  `apply-migrations.mjs --drift <env>` answers exactly that and shares its
  implementation with Settings → System status. **This is the second consecutive
  release it would have caught.** `0.10.0`'s record already recommended it: there,
  four migrations were applied while the deploy was still building and the margin
  was luck. Here the luck ran out. It is the cheapest gap on the list and it now
  has two real instances behind it.
