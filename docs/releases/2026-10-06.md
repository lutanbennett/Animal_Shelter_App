### A high advisory appeared, the designed backstop fired, and my first reading of it was wrong

While merging the cut, `gh pr checks` showed `audit  fail  14s` on a run whose
conclusion was `completed / success`. The finding is real:

```
source-map-js  1.0.0 - 1.2.1
Severity: high
source-map-js allows event-loop denial of service through indexed source-map section offsets
```

It arrives as `next → postcss@8.5.23 → source-map-js@1.2.1`, so it is in the
production dependency tree, and `npm audit fix` offers a fix. Lutan chose to
deploy and log it rather than fix it inside a release.

**What I got wrong, and a `/plan-day` session corrected the same evening.** The
backlog item as first written claimed the reporting was suppressed — that
`audit` being `continue-on-error` was the same mistake `CLAUDE.md` records for
`test-plan`, and that the distinction belonged inside the script. That
recommendation was wrong, and acting on it would have broken a deliberate
design:

- `docs/decisions/2026-10-02-scheduled-audit-fails-on-purpose.md` decides that the two audit paths differ **on purpose**, and says in terms: *"Do not 'tidy' the two to match, in either direction."* On a PR a red audit is *"noise standing on a change that did not cause it"*. The backstop is `advisories.yml`, a daily scheduled run that is **not** `continue-on-error`, so a finding fails it and GitHub emails a person where no PR exists to turn red.
- **It fired.** Run `37470137258`, event `schedule`, conclusion **`failure`**, 2026-10-06T13:21:23Z — the first failure after four consecutive successes on 10-02, 10-03, 10-04 and 10-05. Read from those runs, not inferred.
- So "red all day and nothing said so" was the wrong framing. A green scan going red is how a **newly published** advisory arrives, which those four prior successes support. What is left is a notification-routing question — the mail reaches whoever last edited the cron line — not a CI design fault.
- The `next@16.3.5 invalid` caveat was wrong too: `package.json` and `package-lock.json` both hold **16.3.8**, and only this machine's `node_modules` was stale for want of an `npm ci`. A local artefact, not a repo problem.

**The error worth recording is the method, not the advisory.** A change to a CI
workflow was recommended without first looking for a decision record about it,
in a repository whose `docs/decisions/` exists precisely so that settled
questions are not reopened by whoever next finds the behaviour surprising. The
corrected item reads: treat it as an ordinary dependency bump and leave both
workflows alone.

**And that is what happened, within hours.** `39a0f810` on `main` — *"Bump
source-map-js 1.2.1 -> 1.2.2 to clear GHSA-68fv-2mgg-jv7q"* — so the lockfile
now holds `1.2.2` and `audit` passes again, verified on a CI run of this
record's own branch (`37481312760`, `audit: success`).

The precise state, which matters because it is easy to state too generously:
**the advisory is cleared on `main`, not in what is deployed.** `0.19.3` was cut
at `082bf60b`, before the bump, so production and test are running the affected
version until the next release carries `39a0f810` out. Nothing here is urgent —
the DoS needs the app to parse untrusted source maps at runtime — but "fixed"
and "fixed in production" are different claims and only the first is true today.

### A correction to how CI is read here

After `0.19.2`, where a cut PR reported `MERGEABLE` / `CLEAN` with **no workflow
run at all**, the rule adopted was "judge CI on the run's own conclusion, not the
PR's mergeable status". This release shows that rule is not sufficient either:
the run's conclusion was `success` while a job inside it had failed.

The honest rule is **both** — the run's conclusion *and* the per-check
conclusions — knowing which jobs are `continue-on-error`. `CLEAN` can mean "no
checks exist"; `success` can mean "a check failed and was allowed to". Neither
signal alone distinguishes a healthy run from an unexamined one.

This stands on its own, and is separate from the misreading above: noticing the
red `audit` job was right, and the merge should not have gone through on the run
conclusion alone. What was wrong was the conclusion drawn afterwards about *why*
it was red.

What was done about it:

- **The test Pi was rebuilt pinned**, `./scripts/pi/deploy-pi.sh --env test --ref 082bf60b`, because the Pi is what serves users and "both Pis report the release SHA" is the evidence this record rests on. That is the third Pi build of the release.
- **The production Worker was not**, and built from `dca26d00`. It is the fallback; its SHA is not exposed anywhere, since `/api/version` is answered by the app and therefore reports the Pi's; and pinning it would have meant fighting the `deploys only from a clean, pushed main` guard over one documentation file.

So the deploy line reads `(dca26d00)` while every served version reports
`082bf60b`. Both are recorded above rather than one being presented as all four.
