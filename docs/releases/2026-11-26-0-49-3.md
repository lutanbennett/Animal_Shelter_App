## The headline is a measurement, not a feature

**The wrangler deploy failure that cost `0.49.2` four attempts and two wrong diagnoses is a
machine-wide DNS blackout lasting under a second. It is not a Cloudflare problem, it is not a
timeout, and it is not IPv6.**

`#wgdns` closed on 2026-11-26 having established what the fault is *not*, and ended with:
*"NOT established: why getaddrinfo fails intermittently on this machine; the next failing
deploy will print the facts."* #1898 landed `scripts/lib/wrangler-net-trace.cjs` for exactly
that. **This release's first Worker deploy was the next failing deploy, and it printed them.**

### What was measured

A `--env test` Worker deploy died after a complete nine-minute build on
`Unable to resolve Cloudflare's API hostname (api.cloudflare.com or dash.cloudflare.com)` —
the same message, verbatim, that Lutan saw three times on `0.49.2`. The trace recorded **six
failed lookups inside about 250 ms**, from 00:31:37.879Z to 00:31:38.102Z:

| host | elapsed | code |
| --- | --- | --- |
| `registry.npmjs.org` | 10 ms | `ENOTFOUND errno=-3008 getaddrinfo` |
| `api.github.com` | 41 ms | `ENOTFOUND errno=-3008 getaddrinfo` |
| `sparrow.cloudflare.com` | 1 ms | `ENOTFOUND errno=-3008 getaddrinfo` |
| `api.cloudflare.com` | 2 ms | `ENOTFOUND errno=-3008 getaddrinfo` |
| `api.cloudflare.com` | 1 ms | `ENOTFOUND errno=-3008 getaddrinfo` |
| `sparrow.cloudflare.com` | 4 ms | `ENOTFOUND errno=-3008 getaddrinfo` |

**Two things in that table settle it, and neither was available to any previous session.**

1. **`registry.npmjs.org` and `api.github.com` are not Cloudflare API hosts.** The fault hits
   every host at once. Cloudflare's name is in the error only because that is what wrangler
   happened to be asking for when the window opened. Every session that has chased this was
   sent at the one host the message named — `0.49.2` lost about an hour that way, and this
   release's manager repeated the mistake for a few minutes before reading the trace.
2. **1 to 41 ms is not a network timeout.** It is a resolver answering *no such host*
   immediately, which is the signature of a stack with no usable DNS server.

**And it had recovered within minutes.** On the same machine, in the same Node binary,
`dns.lookup`, `resolve4` and `resolve6` all returned addresses for both Cloudflare hostnames,
and a plain `fetch` to `api.cloudflare.com/client/v4/user/tokens/verify` returned **HTTP 400** —
a real answer from Cloudflare, not a network error. A `--skip-build` retry then deployed in
about a minute and printed the correct Server Actions key. **Lutan's production deploy, run
later the same hour with the VPN up, succeeded on its first attempt**, which is itself evidence
the fault is a brief window rather than a state.

### The mechanism, named as a hypothesis and not as a finding

`0.49.2` read NordLynx up with **no DNS servers configured on that interface**. A VPN
re-establishing or rotating its resolver would leave the stack briefly with nothing to ask,
which produces exactly this shape: instant `ENOTFOUND` on every host at once, for under a
second. That is consistent with the correlation across five deploys now, **but it does not
prove the VPN causes it.** The honest position: **scope established, timing established, cause
still inferred.** Anyone writing this up as "the VPN breaks deploys" is going further than the
evidence — and this release's production deploy succeeded with the VPN up.

### Why the remedy is now a retry, when `#wgdns` was right to refuse one

`#wgdns` said *"a retry that hides an unknown fault is worse than the fault"* and declined to
add one. That was correct then. **The fault is no longer unknown**: it is a sub-second,
machine-wide resolver gap whose only effect is to kill whatever was mid-flight. A retry hides
nothing — the trace prints every failed lookup either way — and the cost of not retrying is a
full eight-to-nine-minute rebuild, which on production is Lutan's time, three times over on
`0.49.2`. Filed as **`#dnsgp`**, with the shape spelled out: retry only on an `ENOTFOUND` the
trace saw inside that child, at most twice, reusing the build, printing each retry and its
reason, and keeping the fingerprint assertion on every attempt.

**The one thing worth testing next, because it removes the fault rather than papering over
it:** whether NordVPN can be made to keep a resolver on its interface, and whether the
blackout still happens with it off. Cheap to try now that the trace names what to watch for.

then production**, both `ok`, both reading `444 applied, 2 pending` beforehand and **zero

**`0445`'s `-- consumer: none` is now wrong, and that is a real finding rather than a typo.**
It was true when written; #1904 shipped a consumer in the same release, and `deploy.mjs` prints
its use on every deploy (*"attached hosts re-asserted as --domain: none (0 flagged in
shelter_hosts, the rest already in wrangler.jsonc routes)"*). The header is what feeds
`apply-migrations.mjs`'s warning that a migration's readers are not yet live, so a wrong `none`
means that warning **can never fire for this column** — `0445` reached production with no
warning printed, correct by luck rather than by check. Applied files are never edited, so the
fix is not to change `0445`; filed as **`#c0nhd`**, and the item is the choice between carrying
the real consumer forward and writing down that the header is only ever a snapshot.

## Costs that were the release manager's own

**One: the VPN was turned off for `0.49.2`'s deploy and nothing turned it back on.** This
release opened unable to reach the Pi at all and had to ask Lutan to switch NordVPN back on
before any Pi build could start — a request that would not exist if the previous release had
said "turn it back on afterwards". **The two pull in opposite directions**: the Pi is reachable
only over Meshnet, while the deploy failure correlates with Meshnet being up. That tension is
now written down rather than rediscovered, and `#dnsgp` is where it gets resolved.

**Two: a flag was invented and pointed at production.** `deploy.mjs --env production
--list-secrets` was run to read the secret names. **There is no such flag**; `deploy.mjs`
ignored it and began a full build toward a *second* production deploy. It was stopped during
`next build`, before any bundle or upload, so nothing reached Cloudflare and the live Worker
was untouched — but the correct order was to read the script's own usage block first, where the
flags are listed in the first twenty lines. This is exactly the standing instruction about
verifying the command rather than the change, broken on the one environment where it matters
most. **It also left `.next` in the main checkout mid-build, so the next deploy there must not
use `--skip-build`** until a full build has run.

**Three: `head` cost two commands.** Two `ssh` calls that piped a Pi log into `head` buffered
and were moved to the background having read nothing, and both had to be re-run. The handover
has said *"stop piping"* since `0.49.2`, where `tail` had already cost four faults. Writing the
rule down did not stop the next session reaching for it, which is worth knowing about how much
a handover line can carry.
