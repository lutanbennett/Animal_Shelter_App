### The CSP change is the story of this release

#431 moved the content security policy from **report-only to enforcing**. It was
raised with Lutan on its own rather than inside the count of unsigned plans,
because it is the one change here that fails **silently** — a blocked resource is
a missing photo, a dead map embed, a camera that will not open, with no error
anyone sees. He chose a **test hold** in place of `0.20.1`'s ship-and-record:
apply, deploy test, verify, then production.

**The finding that made the hold worth having, and nearly defeated it: the CSP
lives in the Worker, not the app.** `worker/security-headers.mjs` sets the
header; the Pi serves the page. So after the Pi test build succeeded,
`test.lannacare.org` was running `0.21.0` **and still sending
`content-security-policy-report-only`**, because the test *Worker* deploy had not
finished. Checking the policy at that moment would have reported "report-only,
nothing to see" and passed the gate without testing anything at all.

What caught it was asking `/api/releases/current` — which answers from the Worker
bundle — and reading `0.20.1` against the app's `0.21.0`. The two-endpoint check
`docs/release-procedure.md` already prescribes for *versions* turns out to be the
check for *headers* too. **Consequence for the next release: a Pi deploy cannot
change a security header, and CSP enforcement switches on in production at the
moment the Worker deploy runs — which is Lutan's command, not Claude's.**

Once the test Worker landed, test read `ENFORCING: 1 / report-only: 0`.

#### What was actually blocked

One thing, on every page checked, on both test and production:

```
[error] Loading the script 'https://static.cloudflareinsights.com/beacon.min.js/…'
violates the following Content Security Policy directive: "script-src 'self' 'unsafe-inline'".
The action has been blocked.
```

That is Cloudflare's Web Analytics beacon, **injected at the edge** — nothing in
the repo loads it. Blocking it is arguably a fix rather than a fault:
`/privacy` promises "no analytics tracking", and the 2026-09-26 decision chose
zone totals over Web Analytics for exactly that reason
(`docs/decisions/2026-10-07-csp-enforced.md`).

Item 4 is worth writing down because the plan asked the wrong question. Lutan
said he did not know what it meant and that site visits were never implemented,
and he was right: `countVisitors` in `src/lib/status/usage.ts` opens

```
const token = process.env.CLOUDFLARE_ANALYTICS_TOKEN;
const zone  = process.env.CLOUDFLARE_ZONE_ID;
if (!token || !zone) return { state: "off" };
```

Neither is set, so the tile on **System status** has always been off. And it
could never have been a CSP question in the first place: that figure is fetched
**server-side** from Cloudflare's GraphQL API, and CSP governs only what the
browser loads. The plan's phrasing — "still shows a number (or stays grey for the
same reason as before)" — allowed for it, but naming the tile as a CSP risk
pointed a check at something the policy cannot reach.

Three code checks were also done rather than guessed, which is why the residual
risk was low before Lutan looked: **photos** are served same-origin through
`/api/photos/[fileId]` (no `<img src="http…">` anywhere in `src/app` or
`src/components`), so `img-src 'self'` is satisfied; the **Google map** is
explicitly allowed by `frame-src https://www.google.com`; and the **camera** is
not governed by CSP at all.

### The silent-failure question was asked, and the answer was "no" this time

`0.21.0` established that a change which fails *quietly* gets named on its own
rather than inside a count of unsigned plans. Nine of this release's twelve
plans were unsigned, and two changes were candidates. Both were **read in code
before Lutan was asked**, so the question put to him carried an answer rather
than a worry:

- **Contact map links** (#461, #464) now judge whether a saved link still leads
  somewhere. It fails **open** by construction — `mapLinkLeadsSomewhere` returns
  `true` when Google cannot be reached, so a slow network never blocks a save,
  and a map is dropped only when Google answers without a redirect. The one
  degradation is transient: a 3-second timeout shows no map for that page view,
  and the failed lookup is deliberately **not** cached, so the next view retries.
- **Facility map uploads** (#465) serve plan images through a new route, behind
  sign-in *and* `loadPermissions()`, with an object name that must match
  `plans/<uuid>/<millis>-<random>.<ext>` or it 404s. Images are never deleted, so
  Undo always has something to restore, and the image is same-origin, so
  `0.21.0`'s enforced CSP is satisfied. A failure shows as a missing image —
  visible, not silent.

**He chose ship-and-record.** That is the right outcome to write down precisely
because it is the *opposite* of `0.21.0`'s: the rule is not "hold when plans are
unsigned", it is "look at whether anything fails quietly, and say so separately".
Here the looking produced a no.
