## The cron: cause, fix, and how it was finally settled

**Cause, read from the commits rather than inferred.** Two commits, four days apart, and the record
needs both with their roles named:

| | |
|---|---|
| **`942ea49f`** (2026-10-23 11:57 +07) | **The cause.** `Bump next 16.3.8 to 16.4.2 (fixes three advisories)`. Next 16.4 added `.next/server/preview-props.json` |
| **`244a1731`** (2026-10-27 22:29 +07, PR #1005) | **The fix.** `@opennextjs/cloudflare` 1.20.6 → 1.20.13. The 1.20.6 adapter **throws** on that file, so the Worker's `openNext.fetch` failed on every scheduled run |

Each environment kept running until its own deploy carried the broken build — test at 09:45:42Z,
production at 10:00:13Z on 2026-10-23, which is exactly where each one's last run stops.

**The Cloudflare trigger was never at fault, and that is now an observation rather than a deduction.**
It matters that the two are distinguished, because **this record's own author got it wrong in the other
direction eight hours earlier** (defect 1). What settled it was the unconditional heartbeat #999 added
to `scheduled()`: the old instrument read a row written by the **app's route**, so a dead trigger and a
trigger firing into a crashing Worker were indistinguishable. The heartbeat is written by the **Worker**,
before any guard, so the two cases separate.

Read at 16:53:45Z from this session, independently of the session that first reported it:

```
status alerts:    last REAL cron run 2026-10-27T16:45:10.984601+00:00 (written by the app's route)
worker heartbeat: last trigger fired 2026-10-27T16:45:09.684232+00:00 - heartbeat: fired (*/15 * * * *);
                  status-alerts: 200; calendar-sweep: 200
verdict: healthy: trigger firing and the app is writing real runs
```

**Both numbers are needed and neither alone would do.** The heartbeat proves the trigger fires; the
route's row proves the app did the work. The trigger fired at `16:45:09` on an **unchanged Cloudflare
configuration** with only the adapter changed, and the app wrote a real run **1.3 seconds later**. So
the trigger is exonerated **by the 16:45 fire**, not by anyone's reasoning, and should be dated to it.

**Downstream, checked rather than assumed:**

- **The six stuck vet visits have cleared.** `calendar-pending` now reads `No vet visit is waiting`.
- **Status-alert mail is flowing again**, silent since 2026-10-23. Lutan received one from that same
  16:45 run and reported it unprompted, which is corroboration from outside either session's reads.
- **The calendar loop fix (#1002) passed its first live test, at the worst possible moment.** That
  16:45 sweep was the first run after four days of backlog, with out-of-date past and completed visits
  queued. Under the pre-#1002 code it would have deleted their events, and the poll would then have
  read its own deletions back and cancelled real visits — the exact fault Lutan reported. **It deleted
  nothing.** `calendar-recent` shows no event lost at any `16:xx` timestamp, and the only cancelled row
  on production is still `59d892ee` (2026-10-20, event gone 2026-10-22, `cancel_reason` and
  `calendar_change_kind` both null — a person cancelled it deliberately). **The ordering rule that put
  the loop fix in the same release as the trigger's restoration was load-bearing today, not
  theoretical.**

**`main` moved twice inside the cut-to-deploy window, and that decided where the Pi was pinned.**
The cut merged at 16:24:20Z, the Worker version was created at 16:36:17Z, and #1006 and #1009 merged
at 16:39:59Z and 16:43:57Z — **after** the Worker was built. So the Worker shipped from `429229cd`,
and `git diff --name-only 429229cd..6d7fb250` excluding `docs/` and `.claude/` lists **seven real code
files**. Building the Pi from `main`'s tip would have put untested code on production that nothing had
deployed — the `0.38.1` trap. **Both the Worker and the Pi are on `429229cd`, so the served application
code is identical.** The window is now routinely long enough for two PRs to land inside it; that is
worth knowing rather than discovering again.

**Also now proven, and it was explicitly unproven when Lutan approved it:** `wrangler 4.153.0`
completes a real production deploy. #1005 pulled it forward with the adapter, along with
`@opennextjs/aws` 4.1.4 → 4.1.12, `workerd` and `esbuild`. He was told no deploy had been exercised on
that toolchain before he chose to go ahead. It then deployed without incident.
