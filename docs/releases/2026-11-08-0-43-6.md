### The dry-run's two failures are the documented non-fault, and the script now says so itself

`0336` and `0337` came back `FAILED: relation "suppliers" does not exist`. `suppliers` is created by
`0335`, which is pending in the same run, and the dry-run rolls each file back before the next starts.
`CLAUDE.md` names this exactly, and the trap is that **a red dry-run normally means "do not apply" and
here the correct action was to apply**. The script printed the reasoning unprompted:

```
NOT a fault in 0336_shelter_friends_supplier_subject.sql: it runs cleanly after 0330 … 0335.
The dry-run rolls each file back before the next, so it cannot see what they add.
A real apply commits each file first, so this one is expected to apply.
```

That text is new since the last time this bit a release, and it turned a two-file investigation into a
line of reading.

## The before-picture, and why it is a different picture this time

`0.43.5` needed `role-cards` and `role-cells` because three of its five migrations **rewrote card
grants**. **None of these eight does.** Read file by file rather than assumed: `0330` adds a view,
`0331` replaces a trigger function, `0332` drops one `not null`, `0333` adds one enum value, `0334`
adds a function, `0335` creates `suppliers` and fills it once, `0336` makes one column nullable and
adds another beside it, `0337` adds two columns and fills them from the columns already there. **No
existing row is rewritten and nothing is dropped.**

So the picture worth taking is the one these files actually touch: **policies and the activity
catalogue**, because `0335` and `0336` create tables with their own policies and `0335` claims, in its
header, to add **no new activity and no new card**.

**The ten activities are the state production was already in, not something this release causes**, and

backlog as `#av8rq`**, which names the three ways out and leans to the one that still fails when

### The six-minute silence, and a correction to how you test for it

The production Worker deploy sat on `Building server function: default...` with no output, exactly as
`0.43.5` recorded. **`0.43.5`'s handover said to measure it with
`find .open-next -type f -newermt '-20 seconds' | wc -l`, which returned 63 there. Here the same
command returned `0` on a perfectly healthy build** — the esbuild stage holds its work in memory and
writes in bursts, so a 20-second window lands in a gap.

**A 20-second window is too narrow to distinguish a pause from a stall.** What settled it in seconds:

```
 60s: 0        newest file in .open-next: 64 seconds ago
180s: 15       4 live node processes
600s: 213
```

So: widen the window to **two or three minutes**, or read the newest file's age directly. The advice to
measure rather than kill the build was right; the number in it was not. Corrected in the runbook by
this release's record PR rather than left for a fourth release manager to re-derive.

### THE PURGE NO LONGER COVERS TEST, AND THE RUNBOOK'S REASON WHY THAT WAS HARMLESS IS NOW FALSE

`docs/release-procedure.md` has said, as a standing fact, that *"The zone purge covers
`test.lannacare.org` as well as `lannacare.org`. They are one Cloudflare zone, so
`purge-cache.mjs --env production` clears both"*, and that `--env test` refusing is *"usually
irrelevant for exactly this reason"*.

**That stopped being true at the 2026-11-06 cutover and nobody noticed.** Production moved to its own
zone, so the script now reads `CLOUDFLARE_ZONE_ID_LANNACAREFORANIMALS` for production and
`CLOUDFLARE_ZONE_ID` for everything else. Measured here with `--dry-run`, which sends nothing:

```
--env production --dry-run   would purge everything for lannacareforanimals.org (zone 323637bc…)
--env test --dry-run         CLOUDFLARE_ZONE_ID and CLOUDFLARE_PURGE_TOKEN missing from .env.local.
```

So **`test.lannacare.org`'s edge cache is now purged by nothing**: production's purge no longer reaches
that zone, and `--env test` refuses because it looks for the values in `.env.local` while they live in
`.env.deploy.production`.

**It did not bite this release, and the reason is worth knowing rather than guessing:** every build
names its assets by content hash, so a new build's stylesheet has a name the edge has never seen. Both
after-checks say so — production `HIT` and test `MISS`, each *identical to the build*. The exposure is
to **stale HTML pointing at an old asset name**, which is the shape that produces the unstyled page.

**The runbook paragraph is corrected in this release's record PR**, because leaving a false standing
fact in it is how the next release manager concludes test needs no purge. Filed as a backlog item too,
since the fix is one value in one file and a line in the runbook.

### UAT NO LONGER REFUSES A DEPLOY, and re-measuring is the only reason anybody knows

`0.43.5`'s handover said UAT *"still refuses a deploy until Lutan fills `.env.deploy.uat`"*. **That is
no longer true.** Checked with `--plan`, which builds nothing and deploys nothing:

```
deploy: WARNING: could not ask uat which migrations it has applied (HTTP 403: Missing required
  permission(s): database_read).
deploy: WARNING: continuing WITHOUT the schema check. Verify by hand: apply-migrations.mjs --drift uat
deploy: release 0.43.6 "Other bills, Partner contacts, and photos you can save for later" (live now: unknown)
deploy: uat → Supabase project fsjagxmxjosauwmxwype (9b07b038)
deploy: --plan: would build, then run: wrangler deploy --env uat --tag v0.43.6 …
```

**Exit 0.** It resolves UAT's own project and says it *would* deploy. So the thing stopping UAT is no
longer a refusal — it is that nobody has chosen to.

**And it was still right not to, for a reason the refusal used to hide.** UAT's access token **cannot
read its database**: `--drift uat` dies with `Missing required permission(s): database_read`, and the
deploy's own first line says it could not ask which migrations are applied, so it reports `live now:
unknown`. **UAT's schema guard is therefore blind in the same way the Pi's is** — and unlike the Pi,
there is no way to verify UAT by hand from here either, because the same missing permission blocks the
drift check. Deploying `0.43.6` to UAT would mean shipping code that reads `0332`, `0333` and `0334`
to a database nobody can confirm has them. That is precisely what the guard exists to stop.

**So UAT stays on `0.43.3`, deliberately**, and the blocker is now *"UAT's token needs `database_read`,
and `uat.lannacare.org` needs a DNS record"* rather than *"`.env.deploy.uat` is unfilled"*. Both belong
to `#uat7p`, which is Lutan's own five steps at the Pi. **Not deployed, not attempted, and no
`--force`.**
