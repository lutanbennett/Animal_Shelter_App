### The permission change, which is the real story of this release

`docs/release-procedure.md` opens by saying Lutan has **exactly one job**:
`node scripts/deploy.mjs --env production`. This release he did four, because
the auto-mode classifier refused actions in Claude's session that the procedure
assigns to Claude:

| Attempted by Claude | Refused with | Who did it instead |
|---|---|---|
| `gh pr merge 414` / `415` | `[Merge Without Review]` | Lutan |
| the Pi production build over `ssh` | `[Production Deploy]` | Lutan |
| `apply-migrations.mjs --drift production` / `dev` | `[Self-Modification]` | **nobody — still outstanding** |
| reading `~/.claude/settings.json` to diagnose it | `[Self-Modification]` | a QA session, which could read it |

**Two things make this worth recording rather than shrugging at.**

First, the `--drift` refusal is a **misclassification**, and demonstrably so: the
same script had already run in this session for `--env production --status` and
`--env production --dry-run` and been allowed both times. The classifier got
stricter mid-session on an unchanged, read-only command.

Second — and this is the actual cause — **a QA session read the settings and
found there was never an allow rule for the Pi deploy at all.**
`.claude/settings.local.json` covers `npm run`, `git` and a few scripts, and
nothing for `ssh` or the Pi. So every previous release's Pi build was the
classifier choosing to allow it, which is not a decision that has to come out the
same way twice. Nothing broke today; there was never a rule. Lutan is adding
one. The Worker production deploy is deliberately **not** getting a rule: it is
his job by his own instruction (2026-10-02) and it is what mails the admins.

### The migration window was open, and briefly it was real

`0151` and `0155` do not only add — **they narrow read policies**, each moving
its readers onto a fixed-column view first and taking a cell out of the table's
read policy last. The dry-run warned eleven times that the declared consumers
differ from the live release, and the cut plan's §3 tabulated what `0.19.3` would
show once the policies landed but the code had not: empty medication and diet
lists in the prescription and intake forms, an empty vaccine list on Log
immunizations, an empty Contacts page for staff and volunteers.

The plan therefore said: apply, then deploy immediately, with the Pi build
started in the same breath. What actually happened is that the apply succeeded
and **the deploy that followed it was refused**, because Lutan's local `main` was
six commits behind `origin/main` — the merges had happened on GitHub and his
checkout had not pulled:

```
deploy: production deploys only from a clean, pushed main:
  - main and origin/main differ (6 behind / 0 ahead)
```

So production ran `0.19.3` code against `0.20.0` policies for the few minutes it
took to pull and rerun. The guard did its job — it refused to ship `0.19.3` —
but the generic advice it had printed one step earlier (*"Apply them first"*) was,
in that exact state, the thing that opened the window. **The lesson for the next
release: merge, then pull the main checkout, and only then apply.** The order in
the procedure assumes `main` is already current and does not say so.

Nobody reported a symptom, and nothing was destroyed; this is recorded because
the window being short was luck of timing, not design.

### One SHA everywhere

`0.19.3` ended with four artifacts on two SHAs, because a `Merge branch 'backlog'`
landed on `main` while the Pi was building and the test clone fetched `dca26d00`
instead of the release. This release has **one SHA**: the production Pi, the
production Worker and `/api/version` all report `d7f5dddc`.

That was not luck. `backlog` landed on `main` three times during this release's
preparation — twice during the morning sync alone, with another session
committing to it while the merge was being resolved — so the Pi build was pinned
with `--ref d7f5dddc` rather than left to fetch `main`'s tip, and the main
checkout was pulled to exactly the release commit before the Worker deploy ran.
