## The migration question, and why it mattered this time

This is the part worth reading next time, because the answer was fine and the
process that produced it nearly was not.

`main` carried two contradictory statements about production's schema:
`docs/releases/2026-09-24.md` said 80 applied / 0 pending, while
`docs/test-plans/anon-view-grants-schema.md:62`, written afterwards, said
production "sits at `0077`" so `0078`–`0081` still had to go. The second was
explicitly a presumption — that plan says production was never probed.

Normally that is a tidy-up. Here it was a release blocker, because of something
that changed underneath it:

- `0080_social_urls.sql` added `facebook_url` and `instagram_url` to
  `site_content` and shipped in `0.3.0` as **schema ahead of code**. The `0.3.0`
  record checked for an ordering trap and correctly found none: nothing read
  those columns yet.
- **#112 built the consumer.** `src/lib/site/content.ts:30` now lists both
  columns in `SITE_CONTENT_COLUMNS`, which is a PostgREST `select`. Against a
  database without them the select errors, and it is the shared site-content
  loader — so `/`, `/adopt`, `/donate`, `/foster`, `/volunteer`, `/our-work` and
  the admin Website page would have failed together.

So a migration that was safely ahead of code in one release became the thing the
next release depended on. **"Schema ahead of code" is a statement with an expiry
date**, and the release that builds the consumer is when it expires — not the
release that adds the column.

`node scripts/apply-migrations.mjs --drift production`, the check #114 added for
exactly this question, was run by Lutan (Claude's `--env production` reads are
refused) and answered:

```
Environment: production — project dbkodyyxxhtygxcxmfcu
Against origin/main 7bf0e9c: 82 file(s), 82 applied row(s).
  On origin/main, not applied here: 0
  Applied here, no file on origin/main: 0
No drift: production matches origin/main.
```

Production was at **82 of 82** — `0080` long since applied, and `0081`/`0082`
(the anon-grants lockdown) already live at the database level before this deploy.
The release record was right; the test plan's `0077` was wrong. **Nothing was
applied for this release.**

### The ordering constraint, and why it was the point

This release could not safely ship before its schema, and the reason is worth
keeping because it is the inverse of the usual worry:

- `0085` adds the `public_viewer` role. `0086` moves six owner-rights internal
  views into `private` behind a staff-role gate.
- This release carries the sign-in lock. A production holding `0085` **without**
  `0086` would have had an account type that signs in past the lock and reads
  what `0086` had not yet closed — on dev, 81 placements, 220
  `immunization_compliance` rows and 58 `translation_queue` rows to a role-less
  login.

So "apply both, then deploy" was a hard prerequisite, not hygiene. It held.

**The enum artefact was checked for and did not apply.** `0085` is
`alter type app_role add value`, the shape that made `0076` report a false
`FAILED` against `0075` on 2026-09-24. Here `0086` never names `public_viewer`
and gates on a positive allow-list of the five staff roles, so there was no
cross-file dependency: **a clean dry-run was the expectation, and it came back
clean.** Worth recording because the standing advice for that shape is the
opposite, and following it blindly would have meant treating a correct green as
suspicious.

### The first attempt did not take, and the state it left was the safe one

The production deploy was run twice. After the first attempt the site still
answered `0.4.0`, and this was established rather than assumed: the version
endpoint returns `Cache-Control: no-store` with `x-lanna-cache: BYPASS`, so it is
never a cached answer, and `/` came back `x-lanna-cache: MISS` with no lock page
and `/adopt` still 200 to a signed-out request. No `deploy.log` existed, so the
command had not run to completion in the repo root.

**The intermediate state was harmless, and predictably so.** Production sat on
`0.4.0` code with `0085` and `0086` already applied. `0.4.0` only ever reads
those internal views as staff, and staff still pass the new gate; `0085` adds a
role no account can hold until the admin UI ships. This is exactly the asymmetry
#132's plan called out under Rollback — the dangerous combination is the lock
without the migrations, and that direction never occurred. So there was no
urgency and nothing to undo, which is what made a calm re-run the right response
rather than a rollback.

### The release mail reached one person, and that person ran the deploy

`deploy: release mail for 0.5.0 [UAT]: sent 1, skipped 1`

```
sent     lutan.bennett2@gmail.com
skipped  lannacareforanimals@gmail.com: E_RECIPIENT_NOT_ALLOWED
```

Two things follow, and the second is a standing problem rather than a note about
this release.

**The environment label is `[UAT]`, not `[Production]`.** That is correct — the
site is a pre-go-live testing site, which is the very thing this release is
about — but it corrects an expectation stated in the `0.4.0` handover, which
assumed `[Production]` without checking.

**`lannacareforanimals@gmail.com` — the shelter's own admin address — was refused
by the mail provider**, and the same `sent 1, skipped 1` appears against `0.1.0`
and `0.2.0` in this file's earlier sections. So **every `major: true` release so
far has emailed only Lutan.** `E_RECIPIENT_NOT_ALLOWED` is the provider's code,
surfaced verbatim by `worker/release-mail.mjs:95`.

That deserves attention out of proportion to its size, because of what `major`
costs. Each major release is treated as irreversible precisely because the mail
cannot be unsent, and that judgement has been made carefully three times. If the
only recipient is the person running the deploy, the flag is currently buying
nothing it is being charged for. Either the recipient restriction gets fixed
before go-live, or `major` should be understood as "written down prominently"
rather than "admins were told".

### Findings for next time

- **Redirecting deploy output to a file makes the terminal look dead.** `> deploy.log 2>&1` was the right advice for capturing the evidence and the wrong advice to give without saying the screen will stay blank for several minutes. Say both together, or use `tee`.
- **A failed deploy is diagnosable from outside.** The version endpoint is
  `no-store` and page responses carry `x-lanna-cache`, so "is the new build
  actually live" is answerable in one command and never needs to be guessed at.
- **`major: true` is not currently doing what it is priced at.** See the mail
  section above. Worth settling before go-live, when the admin list stops being
  one person.
