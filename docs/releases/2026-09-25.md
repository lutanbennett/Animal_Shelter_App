## The migration question, and why it mattered this time

This is the part worth reading next time, because the answer was fine and the
process that produced it nearly was not.

`main` carried two contradictory statements about production's schema:
`docs/releases/2026-09-24.md` said 80 applied / 0 pending, while
`docs/test-plans/anon-view-grants-schema.md:62`, written afterwards, said
production "sits at `0077`" so `0078`–`0081` still had to go. The second was
explicitly a presumption — that plan says production was never probed.

Normally that is a tidy-up. Here it was a release blocker, because of something
that changed underneath it:

- `0080_social_urls.sql` added `facebook_url` and `instagram_url` to
  `site_content` and shipped in `0.3.0` as **schema ahead of code**. The `0.3.0`
  record checked for an ordering trap and correctly found none: nothing read
  those columns yet.
- **#112 built the consumer.** `src/lib/site/content.ts:30` now lists both
  columns in `SITE_CONTENT_COLUMNS`, which is a PostgREST `select`. Against a
  database without them the select errors, and it is the shared site-content
  loader — so `/`, `/adopt`, `/donate`, `/foster`, `/volunteer`, `/our-work` and
  the admin Website page would have failed together.

So a migration that was safely ahead of code in one release became the thing the
next release depended on. **"Schema ahead of code" is a statement with an expiry
date**, and the release that builds the consumer is when it expires — not the
release that adds the column.

`node scripts/apply-migrations.mjs --drift production`, the check #114 added for
exactly this question, was run by Lutan (Claude's `--env production` reads are
refused) and answered:

```
Environment: production — project dbkodyyxxhtygxcxmfcu
Against origin/main 7bf0e9c: 82 file(s), 82 applied row(s).
  On origin/main, not applied here: 0
  Applied here, no file on origin/main: 0
No drift: production matches origin/main.
```

Production was at **82 of 82** — `0080` long since applied, and `0081`/`0082`
(the anon-grants lockdown) already live at the database level before this deploy.
The release record was right; the test plan's `0077` was wrong. **Nothing was
applied for this release.**

## Findings for next time

- **Capture the deploy output even when someone else runs the deploy.** Four of
  the smoke test's checks live only in that output, and this record cannot tick
  three of them because the text was not kept. A paste into the session, or
  `npm.cmd run deploy:prod > deploy.log`, is enough.
- **"Schema ahead of code" expires.** A migration declared safely ahead of its
  consumer needs re-checking in the release that *builds* the consumer, not just
  in the one that adds the column. `0080` was correctly cleared in `0.3.0` and
  was a genuine blocker in `0.4.0` — same file, opposite answer, and nothing in
  the process would have re-asked the question. The prompt that caught it was
  grepping for who reads the new columns before deploying.
- **The browser items have now been outstanding for six releases.** They are
  listed honestly every time and done almost never. Either someone runs them
  once per release, or the list should say plainly that production sign-in is
  unverified as a standing position rather than as a per-release omission.
