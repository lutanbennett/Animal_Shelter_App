# Release record — `0.37.2`, 2026-10-20

A **minor** release, the third in a run of three and the first to cross midnight:
cut late on 2026-10-19, deployed on 2026-10-20. Its headline is not what shipped
— five notes, four of them Admin-only — but that **the trap the last handover was
written around fixed itself in this very release, and we watched it happen.**

`0.37.1` ended with the production Pi declaring `DEPLOY FAILED — NOTHING NEW IS
BEING SERVED` over a deploy that had worked perfectly. The fix for that (#750)
was merged into **this** release. The production Pi re-executed under the new
script, probed itself correctly, and printed `deploy-pi: serving 0.37.2 as
expected`. **The banner told the truth for the first time since it started
lying**, and the asset check it used to exit before ran as the last step and
passed.

### What shipped

Five notes, **all tagged**, and four of the five `admin` only. So unlike

seven roles see an empty `0.37.2` section** on `/releases`: Head of Maintenance,
Head of Medical, Doctor and Volunteer. That is the `0.37.0` shape. It was flagged

### The fifth note was added in the cut, deliberately

`alert-test-relay` (#746) wrote its release-notes line as `n/a` because the
button needed migration `0226` on production **and** a Worker deploy — *"both
Lutan's steps and still outstanding"*. By release time `0226` was already applied
and this release performed the Worker deploy, so **this release is what closed
the step**. Under `docs/decisions/2026-10-11-release-note-truth-rule.md` the note
belongs in the PR that closes the step, not the one that wrote the code, so it
went into the cut.

This is the first time that rule has been exercised forwards rather than cited
after a failure. It is worth stating plainly because the alternative is what
happens by default: the feature PR correctly declines to promise something that
does not work yet, the release that makes it work mentions nothing, and the
ability ships invisibly. **A note that nobody writes is the same outcome as a
feature nobody shipped.**

### Why minor, three releases in two days

`0.37.0` mailed every admin on the morning of 2026-10-19. Four of this release's
five notes are `admin` only, and the one reaching Management and the 2IC is
polish — words beside icons — rather than a new ability. A major release would
have mailed the same people a **third time**.

**The check that proves it:** `majorReleasesSince("0.37.1")` returns **nothing**,
asserted mechanically rather than by reading the `major:` flag, and both deploy
logs then printed `no major release new to <env>, so no email`. **On a minor
release the absence of the mail line is the check.** Third release running where
the standing test and the audience argument agreed.

## THE THING THAT WENT RIGHT: the Pi's banner fixed itself mid-release

The previous handover opened with *"A red `DEPLOY FAILED` from the PRODUCTION Pi
is no longer evidence of anything."* That is now **out of date, in the good
direction**, and the next release manager should know it.

What happened, in order:

1. The production clone was still at `9804e211`, and its `deploy-pi.sh` had **zero** matches for the fix — checked before building, not assumed.
2. But that old script already carried the **re-exec** mechanism. It fetched the pinned ref, checked out `3e94268e`, and printed `deploy-pi: restarting under the script from 3e94268e`.
3. From that moment the **new** script was running, including #750's change: the loopback probe now sends the origin key, which production requires.
4. It printed `deploy-pi: serving 0.37.2 as expected`, `lanna-care running`, `x-lanna-served-by: pi` — and **no banner**.
5. `check-assets: ok … identical to the build` ran **as the last step**, from the exit trap, rather than being skipped.

**Both halves of the old defect are closed**: the false banner, and the asset
check being unreachable behind it. The asset check is the one that matters most
— it catches a poisoned edge cache, a failure that stays broken for a year and is
invisible from the machine you deployed from.

**What to carry forward, and it is narrower than it sounds.** This was the
*first* deploy that brought the fix in, and it worked only because the **old**
script could re-exec. A future fix to `deploy-pi.sh` relies on the same
mechanism, so **check for the `restarting under the script from <sha>` line
before trusting that a shipped Pi-script change actually ran.** Its absence means
the old script ran start to finish and the release's new guards did not.

## THE DEFECT THAT MATTERS: the production Pi build needed Lutan after a refusal

The one avoidable cost in this release was a permission gate, not a mistake.

`ssh lutan@lanna-pi.local … deploy-pi.sh` was **refused twice** as
`[Production Deploy]`. The established pattern is *one considered retry after
Lutan has said to proceed*; that retry was taken and also refused, and the
session then **stopped** rather than continuing to guess at it. Lutan ran the
command himself and it worked first time.

Three things worth not re-deriving:

- **There is an allow rule for this** — `Bash(ssh lutan@lanna-pi.local *)` in `C:\Users\Leidos\.claude\settings.json` — and it has cleared this refusal on a single retry for three previous releases. **This release it did not**, which means the refusal is not reliably a one-retry affair and a session should not plan on it clearing.
- **The test Pi command was not refused**, from the same session, seconds apart, over the same SSH. So the gate is specifically on the production clone's path, not on SSH generally. That is useful: **the test Pi build can always proceed**, so a blocked release manager can still get three of the four builds done and leave exactly one step for Lutan.
- **Stopping was correct and cost one touch.** The alternative — retrying until it worked — is the behaviour the refusal exists to prevent. One touch is the right price.

### An unexplained 4 bytes

`purge-cache.mjs` reported the probed stylesheet as **96235** bytes; the Pi's

build*. The authoritative check is the second — it compares against the build

## THE ONE THAT WAS NEW: `0231` had a consumer header, and the warning was expected rather than investigated

Every migration in `0.37.2` declared `-- consumer: none`, so no `-- consumer:`
warning appeared and the handover recorded that as the shape to expect. **This
release is the other case**, and it is worth writing down because a warning that
is *expected* and a warning that is *a problem* look identical:

```
WARNING 0231_public_photos_exclude_videos.sql: declared consumer
src/app/api/videos/[fileId]/route.ts differs from release 0.37.2,
so it may or may not already read this.
```

`0231` names `src/app/adopt/[id]/page.tsx` and
`src/app/api/videos/[fileId]/route.ts` as consumers, and **both arrive in #764,
in this same release**. So the warning is the safe direction by construction: the
schema lands minutes before the code that reads it, which is the order the runbook
requires anyway. **It was predicted in the cut's test plan before the apply was
run**, so meeting it cost nothing — which is the whole point of checking a
consumer header against the release rather than against the day it was written.

### The one narrowing in the release was read in code, not assumed safe

`0231` adds `media_kind = 'photo'` to `public_resident_photos`, which is a
**narrowing** of a public view — the shape of change that silently empties a page.
It was checked rather than reasoned about: `0229` added that column as
`text not null default 'photo'`, so **every pre-existing attachment row is already
`photo` and nothing drops out**. Had the column been nullable, approved photos
would have vanished from the public site with nothing to say so.

**Three migrations, no shared object between them** (`role_permissions`, a view,
and new calendar tables), so the "did the later one revert the earlier" question
had no surface. None of the three is destructive — the difference from `0.37.2`,
whose `0227` deleted live rows nightly.

## THE DEFECT THAT MATTERS, and it was mine: a needless Pi rebuild poisoned the production cache

**This is the one avoidable cost in the release, it was self-inflicted, and the
mechanism is worth understanding because the instinct behind it was reasonable.**

What happened, in order:

1. The cut merged as `1de7bdb4`. Both Pi builds were pinned `--ref 1de7bdb4` and both succeeded.
2. **`main` then moved**: #787, the planner's handover, merged at 16:51 — one commit, two files, both under `docs/`.
3. Lutan mentioned the merge. I reasoned that his Worker deploy would now build from `c40c39f6` and break the "all four builds from one SHA" property, so **I rebuilt both Pis at `c40c39f6`** to keep them matching.
4. **He had already started his deploy**, from `1de7bdb4`. Reading his log said so plainly: `deploy: production → Supabase project dbkodyyxxhtygxcxmfcu (1de7bdb4)`.
5. So I had moved the Pis *away* from the shipped SHA. I rebuilt both back to `1de7bdb4`.
6. The production Pi's own asset check then **failed, correctly**:

```
check-assets: FAILED — the served stylesheet is not the one just built.
  /_next/static/chunks/036bcgcbzb7ah.css: the page references it but
  .next/static/chunks/036bcgcbzb7ah.css is not in this build
  This is what a poisoned Cloudflare cache looks like: the app renders with no styling.
```

`036bcgcbzb7ah.css` was the **`c40c39f6`** build's stylesheet. Cloudflare had
cached that build's HTML; the Pi was now serving the `1de7bdb4` build, whose
stylesheet has a different name. A zone purge fixed it, and the authoritative
re-run came back `ok /_next/static/chunks/0_-d5h0mcn9v6.css — 99214 bytes,
identical to the build`. Test showed the same and cleared on the same purge.

**Three things worth keeping from it:**

- **The error was acting on an inference instead of reading the log.** His deploy's SHA was knowable the moment I wondered about it — it is printed in the first lines of the log he was already `tee`-ing into the checkout. I reasoned about what his deploy *would* build from when I could have read what it *was* building from. **Read the log, then decide.** The information cost one `grep`.
- **The invariant I was protecting was not under threat.** Had I done nothing, all four builds would have been `1de7bdb4` already. The fix for a moving `main` is to **check what is actually deployed**, not to chase `main`'s tip.
- **The guard that caught it is the one added two releases ago**, running from `deploy-pi.sh`'s exit trap. It did exactly its job on exactly the failure it was written for, on a release that also *shipped a change to that very script*. **Believe a red `check-assets`.**

away:** the window between the final Pi rebuild and the purge was roughly four
minutes, and the affected surface is edge-cached anonymous HTML. While
`PUBLIC_SITE` is `locked` the only anonymous page is the staff-testing gate,
which is served `no-store` and so is not edge-cached, and signed-in pages are
rendered per request. **So the likely real impact is none.** That is a reasoned
estimate, not a measurement — nobody was watching the site at the time, and the
honest statement is that a visitor hitting a cached page in those four minutes
would have seen the app unstyled.

**It cost Lutan nothing.** All of it was my time, and it did not touch his one
command or add a third intervention.
