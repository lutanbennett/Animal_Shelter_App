# Search engine audit of the public website — 2026-10-14

Done by a Fable session (`claude/seo-audit-fable`) on a local dev server against the **dev**
database, signed out, in English and Thai, at phone width (375 px) and laptop width (1280 px).
Production was not opened and nothing was changed on it. The public site stays **locked** to
search engines until go-live; nothing here unlocks it, and nothing was submitted to Google.

This repository is public. Every example below uses dev data (test animals, a test business) and
the report names no donor, adopter, carer or private person.

## The five-minute version

**What someone searching will find once the site is open.** A person who types *dog rescue
Chiang Mai*, *adopt a dog Chiang Mai* or *ศูนย์ช่วยเหลือสุนัข เชียงใหม่* into Google will see the home
page listed as **"Lanna Care for Animals — dog and cat rescue, Mae Wang, Chiang Mai"** with the
Director's tagline under it, and each animal as **"Panda · Lanna Care for Animals"** with the
animal's own hook line. Every public page already had a title and a description of its own in
both languages, so the words were right before this audit started.

**What was wrong.** Three things, all machine-facing, none of them visible to a visitor:

1. **Google's own test tool could not see the descriptions.** Next.js sends a page's title and
   description *after* the page, as a speed trick, and only puts them at the top for user agents it
   recognises as crawlers. Lighthouse (the tool behind Google's PageSpeed Insights) no longer
   announces itself as one, so it reported "no meta description" on every page and scored the
   site **92** instead of 100. Googlebot itself reads the page fully and is not fooled, but a score
   Lutan can check is worth more than a claim, and tools that only read the raw page (link
   checkers, some social previewers) were getting the same half-page. **Fixed** by telling Next to
   send the title and description at the top for everyone.
2. **No page said which address is its own.** Without a canonical tag, Google has to guess whether
   `/adopt`, `/adopt?ready=1` and `/our-work?category=Rescues` are three pages or one. **Fixed**:
   every public page now names its own address, built from the site's address setting, so the
   move to `lannacareforanimals.org` changes nothing here.
3. **Photos came in one size.** The hero, the featured animal and the big photo on each animal
   and story page were always the 1200 px copy, even on a phone that needs half that. **Fixed**:
   the site now offers 400, 800 and 1200 px copies and the browser picks one by screen size.

**The numbers Lutan asked for.** Lighthouse's SEO score went from **92 to 100 on every public page
type, in English and in Thai**; accessibility from 94–100 to 100 everywhere; the speed score on a
simulated slow-4G phone from 61–72 to 70–81. Measured, not estimated: the Scores table below.

**What is right and was left alone**: the sitemap (every public page, every public animal and
story, nothing private), robots.txt, `/r/` and `/e/` pages and the not-found page marked
*noindex*, one `h1` on every page, alt text on every photo, the share previews (Open Graph and
Twitter cards with a picture on every page), the `AnimalShelter` schema on the home page, the
breadcrumb schema on inner pages, and no broken internal links (20 checked, all 200).

**What is not code and waits for Lutan** — the numbered list at the end: a Google Business
Profile, Search Console for `lannacareforanimals.org`, and some Thai wording for the Director.

**The one thing search engines still cannot do**: find the Thai site. English and Thai share one
address and the language comes from a cookie, so Google only ever sees English. That is the
*Give the Thai site its own addresses* backlog item (sized L, after the domain cutover), and this
audit does not change it. The Thai titles and descriptions exist and are correct; they are
waiting for an address of their own.

## What was checked, and what was found

### (a) Technical

| | Checked | Found |
|---|---|---|
| T1 | Title and description on every page, both languages | Present and unique on all 12 page types in English; Thai titles and descriptions present on 8, English on 4 (see C2). But Lighthouse could not see the description: Next streams metadata into the `<body>` for any user agent not on its bot list, and Lighthouse 12 dropped "Chrome-Lighthouse" from its user agent. Verified by fetching the home page three ways: with "Chrome-Lighthouse" in the UA the description sits at byte 2,621 inside `<head>`; as Googlebot or plain Chrome it sits at byte 25,000+ in the body. **Fixed: streaming metadata off** (`htmlLimitedBots: /.*/`), so every reader gets it at the top. The public pages' metadata reads the same rows the page reads, so nothing waits longer than it already did. |
| T2 | One `h1`, sensible order | Exactly one `h1` on every page, both widths, both languages. |
| T3 | Canonical | None on any page. **Fixed**: `alternates.canonical` on every public page, the bare path (no `?ready=`, no `?category=`), made absolute by `metadataBase`, which is `getSiteOrigin()`. |
| T4 | Heading order | `/adopt/international`, `/donate`, `/foster`, `/volunteer`, `/friends/join` go `h1 → h3`: the body text's "## " sub-headings rendered as `h3` because the same renderer serves the home page, where they sit under an `h2`. **Fixed**: the renderer takes a heading level; a page body uses `h2`, the home story keeps `h3`. |
| T5 | `hreflang` | None, correctly: there is no Thai address to point at. Adding `hreflang` to one URL would tell Google the English page *is* the Thai page. Waits for the Thai-addresses item. `<html lang>` is right (`en` / `th`) and `og:locale` follows it. |
| T6 | Sitemap | Lists the 10 static pages, every public animal and every published story; nothing under `/r/`, `/e/`, `/login` or the staff app; empty while locked. Animals carry no `lastmod` (the view has no `updated_at`; one small schema PR if wanted). Nothing to fix. |
| T7 | Private pages stay out | `/r/<code>` and `/e/<id>` carry `noindex`; so does the not-found page (which answers 200, a known limit of the root loading file). While locked, every response also carries `X-Robots-Tag: noindex, nofollow`. `/login` is linked from every public page as *Staff login* and had no `noindex`. **Fixed**: `/login` is `noindex`. |
| T8 | Broken internal links | 20 distinct internal links across all pages, all answer 200. Fragments (`#ways-to-give`, `#how-to-adopt`) resolve to a real `id`. |
| T9 | Image alt text | Every `<img>` has an `alt`. Photos carry the animal's or story's name; decorative logos and gallery thumbnails (whose buttons are labelled "Show photo n of N") carry `alt=""`, which is right. The hero's alt is the Director's sentence from Settings → Website in both languages. |
| T10 | Photo sizes | Every big photo was the 1200 px copy whatever the screen; the home page could save 209 KiB on a phone, an animal page 113 KiB, a story 170 KiB (Lighthouse "properly size images"). Cards were always 400 px, which is slightly soft on a phone at 3× pixel density. **Fixed**: an 800 px size is added to the photo route's allowed set, and `next/image` is given a loader that writes `srcset` with 400/800/1200 so the browser chooses. Thumbnails stay 160. Format stays JPEG: Drive serves the renditions and the Worker has no image library, so WebP/AVIF is out of scope. |
| T11 | Speed and Core Web Vitals | CLS 0 on every page (every photo sits in a fixed-ratio box). LCP element is the hero / main photo, already `priority` (preloaded, eager). See the Scores table for production-build numbers. |

### (b) Structured data

Measured on every page. The home page carries an `AnimalShelter` schema built from Settings → Website
(name, description, URL, logo, hero as image, address as typed, phone, email, map link, visiting
hours as typed, Facebook). Inner pages carry a `BreadcrumbList`. Both parse.

- **LINE.** schema.org has no LINE property; the LINE "add friend" link now goes in `sameAs`
  beside Facebook, which is where a profile page belongs. **Fixed.**
- **`WebSite` schema** on the home page (name, URL, language) so Google shows *Lanna Care for Animals*
  as the site name in results rather than guessing from the domain. **Fixed.**
- **Stories as `Article`**: headline, date, cover picture, publisher (name and logo). Google has
  a rich result for this. **Fixed.**
- **Each adoptable animal as structured data: not done, on purpose.** schema.org has no type for
  an animal for adoption that any search engine shows as a rich result; the nearest (`Product`,
  `Offer`) would describe a dog as goods for sale, which is wrong on every level. The animal pages
  keep the breadcrumb and their `profile` share tags.
- **Address and opening hours stay as the Director typed them.** `openingHours` as free text is
  allowed by schema.org; turning "Every day 9:00–16:00" into the `Mo-Su 09:00-16:00` form would
  be a guess dressed as data, and the Thai address column does not exist yet (the §5.5 item).
- **Rich Results Test**: Google's tool needs a public URL, and the site is locked, so it could not
  be run. The four blocks (`AnimalShelter`, `WebSite`, `BreadcrumbList`, `Article`) were sent to
  schema.org's validator (`validator.schema.org/validate`, the endpoint its page uses) after the
  fixes: **0 errors, 0 warnings** on each. The Rich Results Test is a **go-live day step** below.

## What was fixed in this PR (all machine-facing)

Nothing here changes a word a visitor reads. The strings a visitor *can* see are unchanged: every
title, description and heading text is what it was; only where the tags sit, what they point at,
and which size of photo arrives have changed.

| | Fix | Where |
|---|---|---|
| 1 | Title, description, canonical and share tags are sent in `<head>` for every reader (streaming metadata off) | `next.config.ts` (`htmlLimitedBots`) |
| 2 | A `rel=canonical` on every public page, the bare path, absolute through the site's address setting | each public page's `generateMetadata` |
| 3 | Photos offered at 400, 800 and 1200 px with a `sizes` hint per layout; the first photo keeps its preload hint and high fetch priority | `src/components/PublicPhoto.tsx`, `PHOTO_WIDTHS` + 800, the home hero and featured animal, both galleries, the three card types |
| 4 | `WebSite` schema on the home page; `Article` schema on every story; the LINE page in the shelter's `sameAs` | `src/lib/site/share.ts`, `src/app/page.tsx`, `src/app/our-work/[id]/page.tsx` |
| 5 | The JSON-LD `<` escape, which was a no-op, now really escapes | `jsonLdString()` in `share.ts` |
| 6 | `/login` and its two sub-pages are `noindex` | `src/app/login/layout.tsx` |
| 7 | Page bodies from Settings → Website render their sub-headings as `h2` under the page's `h1` (the home story keeps `h3` under its `h2`) | `SiteBody` `headingLevel`, `SitePageView` |
| 8 | The "ready for adoption" filter chip marks itself with `aria-current`, as the species chips do, not `aria-pressed` | `src/app/adopt/page.tsx` |

Not changed, on purpose: `robots.ts` and `sitemap.ts` (right as built this morning), the locked
branch, any dictionary string, any Settings → Website text.

**Follow-up worth a line, not this PR**: the header logo is served at 781 × 746 px for a 40 px
box, about 32 KiB on every public page. A 160 px copy would need to be added to the proxy's two
public-path lists beside `/lca-logo.jpg`. And Drive can serve the renditions as WebP (the photo
route asks for JPEG so the PDF archive can embed them); serving WebP to browsers would cut photo
bytes roughly in half but needs content negotiation and a second cache key per size.

6. Share the home page, one animal and one story in a LINE chat and on Facebook and look at the
   preview (picture, title, description). Facebook's Sharing Debugger (`developers.facebook.com/tools/debug`)
   shows the same and lets you re-scrape.
7. After the Business Profile is verified, add its Maps link to Settings → Website → Map link so
   the schema's `hasMap` points at it.

## Method and limits

- **Crawl.** A throwaway Playwright script (kept in the session's scratchpad, not committed —
  `scripts/check-phone-width.mjs` is the repo's lasting browser check) loaded 14 addresses × 2
  languages × 2 widths = 56 renders on `next dev` at port 3008, recorded title, description,
  robots, canonical, `hreflang`, Open Graph, Twitter, `<html lang>`, every heading, every image
  (alt, size, loading), every link and every JSON-LD block, then fetched each internal link once.
- **Lighthouse 12.8** installed into the scratchpad with npm and run against the same server
  with the installed Chrome, mobile preset, SEO + performance + accessibility + best practices,
  English, with a `locale` cookie; after the fixes, all twelve page types in Thai too.
- **Production-build speed**: `next build` at the before and after commits, `next start` on a
  spare port, same Lighthouse settings.
- **Word counts**: body text of ten pages in each language, counted for the phrase list in P3.
- **Structured data**: the rendered JSON-LD of the home page and a story, posted to
  `validator.schema.org/validate` and the returned error and warning counts read.
- **Not possible from here**: Rich Results Test, PageSpeed Insights, Facebook and LINE preview
  tools — all need a public URL and the site is locked. They are go-live day steps.
- **Not a phone**: Chrome's emulation stands in for a handset; the Web Share sheet and LINE's
  hand-off were read from the links, not tapped.
