# 2026-10-03: `role_can()`, a boolean about another role, and who may ask it

`0133_role_can.sql` (`schema-role-can`). The function half of the backlog item
"Recurring-job eligibility asks about another person's role". The app half, the
RPC wiring, `canDoJob` taking its answer and the rota form's picker, is
`role-can-app`. **Added, read by nothing yet.**

## What it is

`role_can(role_key text, activity text, level text default 'edit') returns boolean`,
`security definer`, `search_path = ''` (exactly `has_permission()`'s hygiene). It
answers for the role with that key, not for the caller. It returns one boolean
about one cell and there is deliberately **no** "list what this role can do"
variant: that is the admin-only read `0132` withheld, and a rota form needs only
the narrow answer.

## Who may call it, and why that boundary

`security definer` bypasses RLS, so the check is inside the function. It answers:

1. **A caller who may set up rotas**: `has_permission('recurring.manage', 'edit')`.
   Management holds it in the seed and Admin is yes by `has_permission()`'s own
   rule. Asking the permission, not naming the role, means a shelter that edits the
   matrix moves the door with it, and the function never lists roles itself.
2. **Anyone, about their own role.** That reveals nothing `has_permission()` does
   not already; it lets `my-tasks` call the same RPC as the form.
3. **The service role**, which reads the tables directly anyway.

Everyone else (staff, vet, volunteer, public viewer, a login with no role, an
archived person, the holder of an archived role, anon) is **refused with
`insufficient_privilege`, not answered "no"**. A volunteer must not enumerate what
other roles can do, and a quiet "no" would also hide an app bug: an app that
called it as the wrong person would read as "nobody can do this job".
`execute` is revoked from `public` and `anon` as well.

## The four "answers no" cases, and Admin

For the target role the function answers exactly as `has_permission()` does for a
login of that role: a **missing cell**, an **unknown activity**, an **archived
role** and a **person with no role** all answer no (the last is the has_permission
side: a login with no live role cannot be a target, and asking about an unknown
role key is no). So do a null argument and a level other than `read` / `edit`.

**Admin has no rows** (§6) and is yes before any cell is read, an activity the
catalogue does not know included. The predicate is the same one,
`roles.key = 'admin'`; there is no second rule to drift. The line between the two
functions is held by `scripts/check-role-can.mjs`, which compares `role_can` with
`has_permission` under each role's own login on every role x activity x level
(660 answers). Run by hand against dev, as `check-permission-tables.mjs` is, since
it needs the database; it is not in `npm run lint`.

## What the harness found

The first run failed on a **null role key from a caller who should be refused**:
`not (false or false or null)` is null, so the refusal was skipped and the
function answered `false`. Fixed with a `coalesce` in `0133`. It is the refused
caller's case, the one that is easy to leave out, that found it.
