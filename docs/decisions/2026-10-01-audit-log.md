# 2026-10-01 — Audit log: whole-row images, admin-only, append-only; soft delete deferred

Backlog DB-6, schema half (`0121_audit_log.sql`). No code reads the log yet.

## What it is

`audit_log(id, table_name, row_id, op, actor, old_row, new_row, at)`, one row
per insert, update and delete on `residents`, `contacts`, `prescriptions`,
`vet_appointments`, `weight`, `attachments` and `immunization_records`. Written
by one `security definer` after-trigger function, `record_audit()`.

## Whole rows, with one exclusion

Images are `to_jsonb(row)`, minus columns passed as trigger arguments. Only
`residents` passes any: `microchip_number` and `microchip_implanted_on`
(0113, staff-only by design). Reasons:

- The log is admin-only, so a copy is not a leak. It is a second place the data
  lives, and it widens the blast radius of any later mistake on one table.
- Excluding a column is one trigger argument, so it is cheap, and the chip
  number has no undo value: nobody recovers from a bad edit by pasting it back
  from a log (a chip is set through `set_resident_microchip()`, 0116).
- Contacts keep phone, address and map URL. Restoring a contact edit is the
  whole point of the log, and DB-5/DB-8 narrow who can *read* contacts, not
  what the admin-only log may hold. If a future column is as sensitive as the
  chip, add it to the trigger's arguments in a new migration; old rows keep
  what they had.
- A no-change update (after exclusions) writes nothing, so `touch_updated_at`
  style writes do not flood the log, and a chip-only edit leaves no trace in
  it, which is the intent.

## Access: three layers

1. **Read:** RLS policy `current_user_role() = 'admin'` only. Management is not
   included.
2. **No API writes:** no insert/update/delete policy, and `INSERT`, `UPDATE`,
   `DELETE`, `TRUNCATE` revoked from `anon`, `authenticated` and `service_role`.
   `service_role` bypasses RLS, so the grant is what stops it.
3. **No owner writes:** `BEFORE UPDATE OR DELETE` (row) and `BEFORE TRUNCATE`
   triggers raise `insufficient_privilege` for everyone, the table owner
   included. Someone with the database password can still drop the trigger;
   this stops mistakes and the API, not a determined superuser.

`record_audit()` runs as its owner with `search_path = public`, inserts only
into `audit_log`, and takes from its caller nothing but the column names fixed
when the trigger was created. `actor` is `auth.uid()` read inside the function,
so it cannot be supplied; it is null for the service role, migrations and
console work. Execute is revoked from `public`, `anon` and `authenticated`
(trigger firing does not need it).

`row_id` and `actor` carry **no foreign key**. `on delete set null` on `actor`
would be an UPDATE of a history row, and a key on `row_id` would defeat the log
of a delete.

## Soft delete: not in this migration

The brief asked to prefer `archived_at` over hard delete for medical rows. It is
left for its own item, for three reasons found by reading the schema:

- **Unique keys collide with an archived row.** `weight_one_per_day` (0106) and
  `weight_one_per_visit` would stop a corrected reading being entered after the
  wrong one is archived. `immunization_records` has `unique (resident_id,
  immunization_type_id, date_administered)`, and 0002 and 0007 write
  `on conflict (resident_id, immunization_type_id, date_administered)`, which
  only works against a full unique constraint. Making them partial changes
  those functions too.
- **Every reader would have to skip archived rows,** or an archive un-deletes
  something: the cashflow, stock-usage, status-alert and shelter-today
  functions, the resident page, the vet scoping policies. The exact failure
  0101/0103/0109/0117 exist to prevent for photos.
- **`attachments` already has a delete story.** #252 checks the row count and
  moves the Drive file to trash; an archived row that still satisfied
  `public_resident_photos` or `is_public_drive_file` would keep a deleted photo
  public. `attachments` gets the audit log only.

What this PR does give: **every hard delete leaves its full before-image**, so
an accidental delete is recoverable by hand today, and the later soft-delete work
can be judged against what staff actually delete. Follow-up filed on the
`backlog` branch with the list above as its starting point. `contacts` already
archives (0075) and is unchanged.

`scripts/check-audit-log.mjs` (dev, rollback): all seven tables, the three ops,
actor, the chip exclusion, no-change updates, per-role read, and every refusal

asserts anon is refused GET, POST, PATCH and DELETE on the real Data API.
