# Dev's extra `0422_keep_an_admin_per_shelter.sql` row: a renumbered file, cleared with `--forget`

**Date:** 2026-11-26 · **Item:** `#d422o` · **Branch:** `claude/dev-migration-0422`

## What the row actually was

Dev's `--status` reported 446 applied rows against 445 files on `origin/main`, with 0 files unapplied and one
row with no file: `0422_keep_an_admin_per_shelter.sql`. The item read that as an abandoned branch nobody reverted.
It was not:

- `git log --follow` on `0423_keep_an_admin_per_shelter.sql` shows `7662c25f8` creating it as `0422`, then
  `fb16692ed` "Renumber the last-Admin guard fix to 0423: #1746 took 0422".
- Dev held both rows: `0422_…` applied 2026-11-19 17:47 UTC, `0423_…` 18:10 UTC.
- `public.user_roles_keep_an_admin()` exists on dev and its body is `0423`'s (it reads `is_admin`).
- The file is `create or replace function`, so running it twice under two names was harmless.

So no object was orphaned. The schema matched `main`; one bookkeeping row did not.

## Why a down-migration would have been wrong

The item prescribed a down-migration for `0422` and warned against deleting the row. A down-migration would have
dropped or reverted `user_roles_keep_an_admin()`, the guard that stops a shelter losing its last Admin, and the
very function `0423` exists to provide. `dev-signin.mjs` (its `-- consumer:`) would then have broken for every
stream. The warning is right when the file really created something nothing else recreates; here the object
is recorded under the number that is on `main`, so deleting the stale row is the whole fix.

It was done with the existing `node scripts/apply-migrations.mjs --forget 0422_keep_an_admin_per_shelter.sql`,
which already refuses production and UAT, a name with a file on `origin/main`, and an unrecorded name.

## The general shape

**A migration renumbered after it was applied is recorded twice on dev, and the second record — the one under the
number on `main` — is the one that counts.** The old row looks exactly like an abandoned branch's migration, but
the object it names exists on purpose. Before reverting anything for a "no file on origin/main" row, look for a
file on `main` with the same name after the number. If that file is applied, `--forget` the old row; nothing else.

## The recurrence guard, and what was rejected

**Built:** `--status` and `--drift` (`driftReport()` in `scripts/apply-migrations.mjs`, helper `renumberedRows()`
in `src/lib/migration-drift.ts`, tested in `migration-drift.test.mjs`) now add, under any no-file row whose name
after the number matches exactly one file that is itself applied, a line saying so and the `--forget` command.
It is said only when the new name is applied, because until then the old row is the object's only record. Every
release reads `--status` before applying, so the explanation appears exactly where this row was first found
(the `0.47.6` record already called it renumbered, and six release records carried it forward unfixed: the
diagnosis existed, but nothing at the point of reading said what to do).

**Rejected:**

- *A line in `CLAUDE.md`'s migrations section.* Free, but relies on being read at the moment of renaming, and the
  renaming stream has no reason to think of dev's rows then.
- *A warning in `check-migration-numbers.mjs` at rename time.* It runs while the branch is being renumbered, when
  the new name is usually not yet applied, so the right advice then is "apply the new one first", and the old row
  only becomes safe to clear later. The drift line sees the settled state, which is when the answer is certain.
