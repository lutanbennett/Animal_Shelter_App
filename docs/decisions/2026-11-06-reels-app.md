# Reels library, app half (`#8bz78`, with `#v9t4m` folded in) — 2026-11-06

Branch `claude/reels-app`, on top of `0322_reels.sql` (PR #1325, applied to dev). **No migration in this PR**: the slot

## Step zero

`src/app/reels` did not exist; nothing in `src/` read `reels` or `reel_residents`; the only reel decision file was
`2026-11-06-reels-schema.md`. The gap was present, so this was built.

## What the migration says the app must satisfy (read end to end; quoted by line)

PR #1325's body and the schema decision file agree with `0322` everywhere I checked. Where they differ, the migration
wins; the one difference is in the migration's own header (last item below).

- **`video_uploads` and `owner_kind`, lines 63-70.** `alter table video_uploads alter column resident_id drop not null;`
  then `add column … owner_kind text not null default 'resident'` and the check
  `owner_kind in ('resident', 'reel') and (owner_kind <> 'resident' or resident_id is not null)`. The app must therefore
  write a reel's upload with `owner_kind = 'reel'` and `resident_id = null`, and must let a resident's upload keep taking
  the default. `src/app/api/reels/start/route.ts` does the first; `src/app/api/residents/[id]/videos/start/route.ts` is
  untouched and still inserts no `owner_kind`, so it takes `'resident'` from the default and still names its resident.
  `attachment_id` stays null for a reel (a reel is not an attachment); the row closes with `state = 'complete'` and
  `finished_at`, which the table's own check (`state <> 'complete' or attachment_id is not null or finished_at is not null`,
  `0229`) allows.
- **`description` plus `tags`, lines 28-30.** `description text not null default ''` and
  `tags text[] not null default '{}' check (cardinality(tags) <= 30)`, with the comment *"Free-word hashtags that did NOT
  match a resident … Residents live in reel_residents."* The app owns the parsing: `src/lib/reels/form.ts`
  `splitDescription()`. A resident is linked only when picked from the list (the same picker and the same
  `NoteTag`/`tagsPresentIn` the resident notes use) **and** its `#name` is still in the text; every other `#word` is a free
  hashtag, lower-cased, at most 40 characters, at most 30 of them, deduplicated. The app caps at 30 before the database's
  check could refuse the row.
- **`date_taken`, line 33.** `date not null default shelter_today()`, typed by a person. The form defaults it to today and
  the server refuses anything that is not a real `yyyy-mm-dd`.
- **Which policy guards each write.**
  - `reels`: `reels_select_perm` (line 163) `has_permission('social.library', 'read')`; `reels_write_perm` (line 165) is
    `for all` on `has_permission('social.library')`: it covers add, change, archive.
  - `reel_residents`: `reel_residents_select_perm` (171) at Read; `reel_residents_write_perm` (173) `for all` at Edit.
  - `social_shares` with `owner_type = 'reel'`: select (182) at Read; insert (192), update (202) and delete (220) at Edit.
  - `video_uploads`: service role only, as before (`0229`); that is why the two new upload routes use the service-role
    client, after `can(perms, "social.library")`.
- **A fact neither the migration's comments nor the PR mention:** `can_see_drive_file()` (`0286`) does not list `reels`, so
  `/api/videos/[fileId]`, the existing video route, answers "not found" for a reel. See *Found, not fixed*, item 1.
- **Migration header.** Line 1 is `-- consumer: none` and says *"the app half adds the real consumer header"*. An applied
  file is never edited (`CLAUDE.md`), so it cannot be corrected here; `apply-migrations.mjs` only warns on that header.

  Management → Home → Meme library → Reels → Add a reel: picked a 4 KB `video/mp4` test file, typed a description with
  `#adopted` and `#An`, picked Angsumalin from the `#` list, saved. Rows on dev afterwards: one `reels` row (description as
  typed, `tags = {adopted}`, `date_taken` 2026-11-06), one `reel_residents` row naming Angsumalin, one `video_uploads` row
  with `owner_kind = 'reel'`, `resident_id` null, `state = 'complete'`. Then: recorded a Facebook post with a link, edited
  the description (tags became `{rescued}`, the link to Angsumalin stayed), archived and brought it back.
- **Regression, deliverable 6: a RESIDENT video still uploads and still records its owner.** Signed in with
  `--cards residents`, opened Angsumalin → Photos, attached a 4 KB `video/mp4`, which uploaded through the shared
  `sendToDrive()`. Dev rows afterwards: `video_uploads` with `owner_kind = 'resident'`, `resident_id` = Angsumalin,
  `state = 'complete'`, `attachment_id` set; the `attachments` row is `owner_type = 'resident'`, `media_kind = 'video'`.
  `/api/videos/<file id>` (now through `streamDriveVideo()`) answered 206, `video/mp4`, `private, no-store`.
- **Refusals.** A login holding only `view_residents`: `/reels` and `/reels/new` stream a redirect to the no-access page,
  `/api/reels/start` and `/finish` answer 403, `/api/reels/<id>/video` answers 404. Signed out: all three API paths 307 to
  the sign-in page (the app's gate) and `check-public-views.mjs` already refuses anon every method on `reels` and
  `reel_residents` (#1325).
- **Limits of that proof.** The test files are not decodable video (no `ffmpeg` here), so the `<video>` element's decoding,
  the length badge (`duration_ms` is null for them) and the browser Download were not exercised; the stream's status,
  type, range and cache headers were. No card holds `social.library` at Read alone, so the Read-only view (no Add, Edit,
  Archive or Record control) could not be built with `dev-signin --cards`; those controls all read the one `canEdit`
  boolean, as the memes page does.

## Found, not fixed (for the planner to file; none is a backlog edit here)

1. **`can_see_drive_file()` does not know reels, so the existing video route cannot serve one.** This PR adds
   `/api/reels/[id]/video`, which asks the `reels` row as the caller and then streams, the same shape the meme photo route
   had before `0286` folded memes into the function. It is correct, but it is a second decision point, which `0286` removed
   once already. The fold-in is one branch; the SQL below is the whole of it, for the next schema PR. When it lands, the
   reel route can go and `check-can-see-drive-file.mjs` gains `["reels", "drive_file_id"]` in its list.

   ```sql
   -- 0323 (or next free): reels in can_see_drive_file(). Body is 0286's, plus one branch. Still security invoker: the
   -- reels row is answered by its own RLS (reels_select_perm, social.library at Read), so no activity is chosen here.
   create or replace function can_see_drive_file(p_drive_file_id text)
   returns boolean language sql stable security invoker set search_path = public
   as $$
     select exists (
       select 1 from attachments where drive_file_id = p_drive_file_id
       union all select 1 from project_photos where drive_file_id = p_drive_file_id
       union all select 1 from maintenance_photos where drive_file_id = p_drive_file_id
       union all select 1 from community_outing_photos where drive_file_id = p_drive_file_id
       union all select 1 from shelter_friends where logo_drive_file_id = p_drive_file_id
       union all select 1 from medication where label_drive_file_id = p_drive_file_id
       union all select 1 from stock_medications where label_drive_file_id = p_drive_file_id
       union all select 1 from pending_photos where drive_file_id = p_drive_file_id
       union all select 1 from memes where drive_file_id = p_drive_file_id
       union all select 1 from reels where drive_file_id = p_drive_file_id
       union all select 1 from donation_receipts where drive_file_id = p_drive_file_id
       union all select 1 from residents where deceased_summary_drive_file_id = p_drive_file_id
       union all select 1 from residents where deceased_index_drive_file_id = p_drive_file_id
     );
   $$;
   notify pgrst, 'reload schema';
   ```
2. **No card opens `/reels`.** `meme_library` has `opens: "/memes"` and a card opens one page, so a login holding it sees a
   Meme library tile and nothing for Reels. This PR adds a Reels link on the meme library page (drawn on the same Read the
   page already needs) and a Meme library link back. Whether Reels gets its own tile is a card question, which is `#i7qkz`
   and the cards stream's files (`cards.ts`, `catalogue.ts`), so it is left.
3. **The `#` picker needs `resident.record` at Read; `meme_library` holds `resident.who_and_where` at Read, not that.**
   `/api/residents/tag-search` asks `resident.record` Read (and `reel_residents_write_perm` asks only `social.library`),
   so a login holding just `meme_library` gets a plain description box and **cannot link a resident at all**. I did not
   change the search route or the card. The proofs above used `meme_library` plus `view_residents`. The fix is a card
   question (does the Reel card carry a resident read?) or a search that asks the activity the link write asks.
4. **The resident's own page does not list its reels.** `#8bz78`'s *Done when* ends with *"the link visible from the
   resident as well as from the Reel"*; `meme_residents` has the same shape on the resident hub (`loadResidentMemes`),
   and this PR does not add the reel one. `#8bz78` is therefore annotated, not ticked.
5. **Two more service-role files**, `/api/reels/start` and `/finish`, are on the ESLint allow-list and recorded in
   `docs/hard-coded-security-registry.json` under `serviceRoleSites`, because `video_uploads` is service-role only and a
   reel's upload has to be bookkept there. Each checks `can(perms, "social.library")` before it touches the client.
6. **The hint under the description** reads *"Type # and a name to link another resident"* because it reuses the resident
   notes' string; the reel's own line under the box says what `#` does here.
