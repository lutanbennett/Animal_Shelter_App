# A photo on the report-an-animal form (#w7nde), 2026-11-14

**Lutan's decision, 2026-11-14, in chat,** asked whether to build an anonymous upload surface at all: *"Yes, build it properly."* The rest is technical and is recorded here.

## Why an uncarded write path is allowed at all
A stranger reporting an injured animal has no login, so no card can guard this. What replaces the card is: (1) the file can only arrive through one server action, which checks and rewrites it; (2) the bucket has **no storage policy**, so neither `anon` nor `authenticated` can read or write it directly; (3) the row can name exactly one object, `<report id>.jpg`, by a check constraint; (4) staff read it only through a route that asks `animal_report.manage`. This is not a precedent for any other uncarded write path.

## The five answers
1. **Where the file lands.** A private Supabase Storage bucket `animal-report-photos` (made by 0376), never Drive. Precedent read: `src/lib/facility-map/plan-store.ts` (private bucket, service role only, no policies). **"Not read" proved on dev** with the anon key: download of a real object = `Object not found`; list = empty; direct upload = `new row violates row-level security policy`; `select` on `animal_reports` = 42501. The anon insert with `photo_path = '../evil.jpg'` is refused by `animal_reports_photo_check`.
2. **Limits and where they live.** All server-side, in `src/lib/animal-reports/photo.ts`: type read from the file's first bytes (JPEG, PNG, WebP; the browser's `accept` is a courtesy only), 8 MB raw, 50 megapixels decoded (`limitInputPixels`), re-encoded to JPEG at 2000 px long side. The bucket itself also caps objects at 3 MB and `image/jpeg`, a second wall. HEIC (iPhone default) is refused with a plain message, because sharp's prebuilt binary cannot decode it; iPhones normally convert to JPEG on upload from a web form.
3. **Metadata strip, proved.** sharp writes no metadata unless asked, and `.rotate()` applies EXIF orientation first so the picture is not left sideways. Proof: a 3000x2000 JPEG built with EXIF carrying Make `SecretPhoneCo`, Model, Orientation and GPS latitude/longitude; run through the same chain. Before: `exif true`, the string `SecretPhoneCo` present in the bytes. After: `exif false`, no `Exif` marker and no `SecretPhoneCo` in the bytes, resized to 2000x1333. The real submission through the form stored an object whose metadata also read `exif: false`.
4. **A report nobody actions.** It stays `new`, with its photo, until staff set it resolved or dismissed or delete it; nothing expires. That is the leak the item feared. **For the planner to file (not built, as the brief says):** a scheduled job that removes the photo object of any report that is `resolved` or `dismissed` for more than 90 days, and any object in `animal-report-photos` whose report row no longer exists (a staff delete leaves the file behind; a failed insert after a successful upload leaves one too).
5. **Abuse bound.** One file per report (named by the report's own id, `upsert: false`), 8 MB, and the report is already replay-guarded by #1568's row-keyed id (23505). There is **no per-visitor rate limit**, same as the report itself; a flood would be a flood of reports and the volume limit for that is Cloudflare, not this code. Said plainly rather than implied.

## Choices worth knowing
- **Service role is used** (registered in `docs/hard-coded-security-registry.json`, `src/lib/animal-reports/photo-store.ts`), because the alternative, a storage insert policy for `anon`, would let a stranger bypass the cleaning by calling the storage API directly. No policy means nothing to bypass.
- **Upload happens before the insert**, so a row never points at a missing file. The cost is the orphan described in (4).
- **No new card.** The staff photo route asks `animal_report.manage` at read, the same activity the page asks.
- **Production:** 0376 is unapplied there. It creates the bucket itself, so no hand step is needed beyond the normal migration apply, which must run before the deploy.
- The Thai wording is unreviewed.
