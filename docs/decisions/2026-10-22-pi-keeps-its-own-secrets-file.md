# Each Pi clone keeps its own secrets file, so a Worker secret does not reach it (2026-10-22)

Found at the `0.39.2` cut. The production Pi was missing
`GOOGLE_CALENDAR_REFRESH_TOKEN` and `GOOGLE_CALENDAR_ID`, so
`calendarConfigured()` (`src/lib/clinics/calendar-sync.ts`) was **false on the box
that serves the live site**. Two of that release's six notes would have shipped
false: the "Calendar entries to confirm" list would never have appeared and every
coming visit would have said the calendar was not switched on — while the Worker's
quarter-hourly poll and sweep, which **did** hold the values, worked correctly
behind them.

## The mechanism

- The Pi's `.env.production.local` is generated by `scripts/pi/write-env.mjs`,
  which writes a `PI_OPTIONAL` name **only when it is present in the values file
  it loads**. Both calendar names are `where: "both", required: false` in
  `scripts/lib/runtime-config.mjs` — optional on a Pi, and explicitly **not**
  `neverOnPi`, so the Pi is a sanctioned place for them.
- The values file is `.env.deploy.production`, and **each clone keeps its own
  hand-maintained, gitignored copy.** It is not deployed, not committed and not
  synced from this machine.
- `0.39.1` added the two values to the **main checkout's** copy, which is what
  `scripts/deploy.mjs` reads for the Worker. Nothing updated the Pi's. The Worker
  got them; the Pi did not.
- `systemctl show -p EnvironmentFiles -p Environment lanna-care` returns only
  `NODE_ENV=production PORT=3000`, so the generated file in the clone is the whole
  story — there is no second source to fall back on.

## Why nothing caught it

- **Test holds all four values**, so every check on `test.lannacare.org` passes
  while production is broken. This class of fault is invisible to test by
  construction, which is the part worth carrying.
- `docs/decisions/2026-10-22-vet-calendar-on-production.md` says "the Pi's
  `.env.production.local` is regenerated by `deploy-pi.sh`". That is true, and it
  was read as sufficient. It regenerates from a values file that was never given
  the two names, so the sentence is correct and the conclusion drawn from it was
  not.
- No guard covers it. `deploy.mjs` and `deploy-pi.sh` verify the commit, the
  project ref and the **required** env names; an absent *optional* name is by
  definition not an error, and `write-env.mjs` omits it silently.

## The rule

**A value added to `.env.deploy.production` for the Worker reaches the Pi only if
the Pi's own copy is given it too.** When a release adds a runtime value that
`runtime-config.mjs` marks `where: "both"`, updating one copy is half the job.
Check the Pi by name — never by value:

```bash
ssh lutan@lanna-pi.local 'cd ~/Animal_Shelter_App && grep -oE "^GOOGLE_[A-Z_]+" .env.deploy.production | sort -u'
```

And check the generated file the app actually reads, which is the one that decides
behaviour:

```bash
ssh lutan@lanna-pi.local 'cd ~/Animal_Shelter_App && grep -oE "^GOOGLE_[A-Z_]+" .env.production.local | sort -u'
```

## Two notes for whoever automates this

- **Do not make `write-env.mjs` fail on a missing optional name.** Optional means
  optional: `BACKUP_DRIVE_FOLDER_ID` and the Cloudflare analytics pair are
  legitimately absent on most deploys, and a hard failure would block every Pi
  build to catch a case that only matters when a release note depends on it.
  The check belongs in the release's pre-deploy gate, where it now is, or in a
  warning that names the environment.
- **A release note that depends on a runtime value needs the value checked in
  every runtime that renders it**, not only the one that was changed. The Worker
  and the Pi both run this app, and the Pi is what users see — the Worker is the
  fallback. `0.39.1` checked the Worker and shipped; the gap was on the other box
  all along.
